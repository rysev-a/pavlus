## Die Idee in einer Minute

Eine `.pavlus`-Datei wird zur Laufzeit nicht interpretiert. Ein **Compiler** liest sie einmal, beim Build, und schreibt ein normales JavaScript-Modul. Deine Anwendung importiert dieses Modul wie jedes andere. Der Browser sieht den Template-Text nie und braucht nie einen Template-Parser.

Das Modul exportiert drei Dinge. Zusammen heißen sie ein **view**:

- `render(state)` gibt das ganze Template für einen State zurück, als Liste einfacher Objekte. Diese Objekte heißen **vnodes** (virtuelle Knoten).
- `diff(prev, next)` gibt die kleinste Liste von DOM-Änderungen zurück, die die Seite von `prev` in die Seite von `next` überführt. Diese Änderungen heißen **Patches**.
- `meta` ist ein kleines Objekt, das sagt, welche Kind-views und welches `+outlet` das Template enthält.

Hier ist das kleinste Template, das überhaupt etwas berechnet. Es begrüßt eine Person mit Namen.

Lies das Ergebnis von oben. Das HTML hat `render` erzeugt. Der erste Schritt zeigt `diff`, nachdem sich `name` von `Ann` zu `Bob` geändert hat: ein Patch, `{"op":"text","id":"1","text":"Hello, Bob"}`. Der zweite Schritt zeigt zweimal denselben State: gar keine Patches. Öffne das Modul: Es hat etwa dreißig Zeilen, und jede Zeile hat einen Grund. Der Rest dieser Seite erklärt sie.

## Die Stufen

Der Compiler ist eine kurze Pipeline. Jede Stufe ist eine einfache Funktion, die die Ausgabe der Stufe davor übernimmt.

| Stufe | Funktion | Eingabe | Ausgabe |
| --- | --- | --- | --- |
| Parse | `parse` | Template-Text | `TemplateAst`: Imports und ein Baum aus Knoten |
| Analyze | `nodeDeps` | ein Knoten | die Menge der State-Felder, die der Knoten liest |
| Generate | `generate` | der AST | JavaScript-Quelltext für `meta`, `render` und `diff` und die Liste der Runtime-Helfer, die er benutzt |
| Assemble | `compileTemplate` | Template-Text | das fertige ES-Modul als String |

Die Analyse ist kein eigener Durchlauf über den ganzen Baum. Der Codegenerator fragt `nodeDeps` nach den Abhängigkeiten jedes Knotens in dem Moment, in dem er den Guard für diesen Knoten schreibt (und das Ergebnis wird pro Knoten zwischengespeichert). Sie ist trotzdem eine eigene Stufe, weil ihre Antwort bestimmt, wie `diff` aussieht. Die Seiten nach dieser behandeln die Stufen der Reihe nach: [Parsing](page:compiler-parser), [Abhängigkeitsanalyse](page:compiler-analysis) und das generierte [render](page:compiler-render) und [diff](page:compiler-diff).

Im Quelltext macht `compileTemplate(source, { filename, runtime })` Folgendes:

1. Es ruft `parse(source)` und `generate(ast)` auf. Wirft eine von beiden einen `TemplateError` und du hast einen `filename` angegeben, bekommt die Meldung den Dateinamen vorangestellt: `app.pavlus: Unclosed { (line 1, col 8)`.
2. Es schreibt einen einzeiligen Kopfkommentar: `// Generated by pavlus from app.pavlus. Edit the template, not this file.`
3. Es schreibt eine `import`-Zeile für die Runtime-Helfer, die der Code benutzt, und eine `import`-Zeile pro `import`-Zeile des Templates. Kind-views werden vom echten Modulsystem importiert, sodass dein Bundler sie sieht.
4. Es schreibt den generierten Code, dann `export { render, diff, meta };` und `export default { render, diff, meta };`.

> [!NOTE] Zwei Wege zu kompilieren
> `compileTemplate` gibt das Modul als Text zurück. Das Vite-Plugin benutzt es, und diese Dokumentationsseite ebenfalls, wenn sie dir "das generierte Modul" zeigt. `compileToView` kompiliert denselben Code und führt ihn sofort mit `new Function` aus, sodass du einen fertigen view bekommst. Er ist für Tests und Tools gedacht. Die Demos auf diesen Seiten nutzen beides: das Modul, das du aufklappen kannst, und einen live view, der das HTML und die Patches erzeugt.

## Ein Template ohne etwas, das sich ändert

Nicht jedes Template hat ein `diff`, das sich zu lesen lohnt. Dieses liest nichts aus dem State.

::demo static open=module

Das Modul hat keine `import`-Zeile, weil es keinen Helfer benutzt. `render` baut jedes Mal dieselben vnodes. `diff` hat keine Vergleiche: nur die Abkürzung `if (prev === next) return patches;` und das abschließende `return patches;`. Der Compiler hat gesehen, dass kein Knoten den State liest, also hat er nichts weiter geschrieben. Die vnodes haben auch keine `id`: Eine id gibt es nur, damit ein Patch einen Knoten benennen kann, und hier wird nie etwas gepatcht.

Das ist die erste große Idee des Compilers: **Er gibt nur dort Code aus, wo sich etwas ändern kann**.

## Vom Text zum AST zum Code

Jetzt ein Template mit einem dynamischen Attribut, einem Klassen-Umschalter und einer Interpolation. Wir öffnen jeden Abschnitt, den die Demo zeigen kann: das Modul, den AST und die vnodes.

::demo stages open=module,ast,vnodes

Gehe die drei Abschnitte in der Reihenfolge durch, in der der Compiler gearbeitet hat.

**Der AST** hat zwei Knoten: das Element `a` (Knoten `#0`) und seinen Text (Knoten `#1`). Neben jedem Knoten steht `reads:`, die Menge der State-Felder, die der Knoten braucht. Das Element liest `active`, `title` und `url`, weil seine Attribute und seine Kinder sie lesen. Der Text liest nur `title`. Die Zahlen `#0` und `#1` sind **Knoten-ids** (`nid`). Der Parser vergibt sie in Dokumentreihenfolge.

**Das Modul** hat zuerst `render`. Es schreibt die Kinder vor dem Element, sodass zuerst der Text gebaut und in `aChildren` gepusht wird. Dann baut es das Attributobjekt `aAttrs`, eine Zeile pro dynamischem Attribut, und pusht das Element. Dann kommt `diff`. Für das Element schreibt es einen Guard, `if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title)`. Innerhalb des Guards wird jedes Attribut für `prev` und für `next` berechnet, und ein Patch wird nur gepusht, wenn sich die beiden Werte unterscheiden. Für den Text gibt es einen zweiten, kleineren Guard nur auf `title`.

**Die vnodes** sind das, was `render` zurückgegeben hat. Das Element und der Text tragen beide eine `id` (`"0"` und `"1"`), die Knoten-id als String. Sie haben ids, weil `diff` sie ansprechen kann. Der Patch im Schritt, `{"op":"attr","id":"0","name":"class","value":"link active"}`, benutzt die id des Elements. Nur die `class` wird gepatcht: `href` und der Text haben sich nicht geändert.

## Was du bekommst, wenn du eine .pavlus-Datei importierst

In einem Vite-Projekt kompiliert das `pavlus()`-plugin jede Datei, die auf `.pavlus` endet. Das plugin überspringt einen Import, der auf `?raw`, `?url` oder `?inline` endet, weil diese die Datei selbst verlangen. Bei jedem anderen Import bekommst du das Modul, das der Compiler geschrieben hat.

```ts main.ts
import view from "./counter.pavlus";
import { render, diff, meta } from "./counter.pavlus";

const vnodes = render({ count: 1 });
const patches = diff({ count: 1 }, { count: 2 });
```

Der Default-Export und die drei benannten Exporte sind dieselben Objekte. Der Default-Export ist der **view**, und das erwartet anderer Code: Das DOM-plugin nimmt einen view zum Mounten, und ein eingebettetes Kind (`+Badge#status`) ist ein view. Beide Funktionen sind **rein**. Sie lesen ihre Argumente und sonst nichts, ändern nichts und geben für dieselbe Eingabe dieselbe Antwort. Darum können sie auf einem Server, in einem Test oder im Browser laufen, und darum können die Demos auf dieser Seite sie für dich ausführen.

Ein view hat diese Parameter, aus dem generierten Code:

```ts
function render(state, idSuffix = "", messagePrefix = "", env)
function diff(prev, next, idSuffix = "", messagePrefix = "", env)
```

Ein view auf oberster Ebene nutzt die Defaults. Die letzten drei Parameter gibt es fürs **Einbetten**. Wenn ein Template `+Badge#status` enthält, ruft der Parent `Badge.render` mit einem längeren `idSuffix` auf (`"/3"`, damit die Knoten-ids des Kindes nicht mit denen des Parents kollidieren), einem längeren `messagePrefix` (`"status."`, damit die Nachrichten des Kindes nach seiner Instanz benannt sind) und einem `env`, also dem Komponentenobjekt, dem der view gehört. Anwendungscode übergibt sie nie.

## Der Vertrag zwischen render, diff und dem DOM-plugin

Das DOM-plugin ist der einzige Code des Frameworks, der das DOM anfasst. Es verlässt sich auf drei Zusicherungen, die der generierte Code einhält. Sie sind der Grund, warum `render` und `diff` zusammen aus einem AST generiert werden.

1. **Das erste render erstellt die Karte.** Wenn das plugin einen view mountet, ruft es `render(state)` einmal auf und baut aus den vnodes echtes DOM. Für jeden vnode mit einer `id` merkt es sich den DOM-Knoten unter dieser id.
2. **Ein Patch nennt nur ids, die render erzeugt hat.** Ein Patch wie `{ op: "text", id: "1", text: "Hello, Bob" }` wird als "finde den Knoten unter `1` und setze seinen Text" angewendet. Wäre die id unbekannt, würde das plugin `unknown node id` werfen. Der Compiler stellt sicher, dass jeder Knoten, den `diff` patchen kann, in `render` eine `id` hat.
3. **Die nächsten States werden per diff verglichen, nicht neu gerendert.** Wenn sich der State ändert, ruft das plugin `diff(oldState, newState)` auf und wendet die Patches der Reihe nach an. Ein neuer Teil der Seite (ein neuer `if`-Zweig, ein neues Listenelement) kommt in einem `insert`-Patch als fertige vnodes an, und das plugin registriert auch deren ids.

Die vnodes sind also nicht nur ein Bild der Seite. Sie sind ein Bild plus ein Inhaltsverzeichnis. Die nächste Demo macht das konkret. Ein `button` hat ein Event; sieh dir an, welche Teile des vnode eine id tragen, und die zwei Patches des Schritts.

::demo events open=vnodes

Der `button` hat eine `id`, weil sein Event ein Argument hat, das sich ändern kann (`add(step)`). Der Patch `{"op":"handler",...}` gibt dem plugin die neue Nachricht, sodass der Klick `{ id: "add", payload: 5 }` sendet. Das plugin entfernt und ergänzt nie einen Listener: Es behält einen Listener pro Element und Event-Typ und tauscht die Nachricht aus, die dieser Listener liest.

> [!WARNING] Der Compiler vertraut auf Identität
> `diff` vergleicht Werte mit `!==`. Ein neues Objekt mit demselben Inhalt zählt als Änderung. Dasselbe Objekt mit neuem Inhalt, an Ort und Stelle geändert, zählt als keine Änderung. Gib dem nächsten State immer neue Objekte für die Teile, die sich geändert haben (spread, `map`, `filter`), und bearbeite nie den vorherigen State.

## Warum beim Build kompilieren

Du könntest eine Bibliothek schreiben, die den Template-Text zur Laufzeit liest und durchläuft. So arbeiten viele Template-Engines. Der pavlus-Compiler erledigt die Arbeit früher, und die Vorteile sind konkret.

- **`diff` ist spezifisch für dein Template.** Das generierte `diff` enthält genau die Vergleiche, die dein Template braucht, und keine anderen. Es gibt keinen generischen Baumdurchlauf und keinen Vergleich zweier vollständiger vnode-Bäume. In der Demo `static` enthält es gar keine.
- **Nichts auszuliefern außer deinem Code.** Der Browser bekommt einfache Funktionen plus eine kleine Menge Helfer. Er bekommt keinen Parser, keinen Ausdrucks-Interpreter und keine Template-Strings.
- **Fehler kommen beim Build.** Ein Tippfehler in einem Template stoppt den Build mit Dateiname, Zeile und Spalte. Er wartet nicht, bis ein Benutzer die Seite öffnet.
- **Die Ausgabe ist lesbar.** Der generierte Code hat Kommentare mit der Quellzeile jedes Knotens (`// line 1: <a.link>`), Namen aus deinen Tags (`aChildren`, `liAttrs`) und eine Anweisung pro Idee. Du kannst ihn lesen, wenn dich etwas überrascht.
- **Reine Funktionen sind überall leicht einzusetzen.** Server-Rendering ruft `view.render(state)` auf und macht aus den vnodes HTML. Ein Unit-Test ruft `diff(a, b)` auf und prüft die Patches. Ein Browser ist nicht beteiligt.

Der Preis ist, dass ein Template in seinen Ausdrücken nur eine kleine, reine Teilmenge von JavaScript benutzen kann (siehe [Ausdrücke und Interpolation](page:syntax-expressions)). Der Compiler muss jeden Ausdruck verstehen, um zu wissen, was er liest. Diese Grenze ist Absicht.

## Die Runtime-Helfer

Sieh dir die erste Zeile des Moduls `stages` an: `import { joinClasses, setAttr, toAttr, toText } from "@service-laboratory/pavlus/runtime";`. Der generierte Code enthält keine eigene Kopie dieser kleinen Funktionen. Sie liegen einmal in `runtime/helpers.ts`, und der Compiler importiert genau die, die ein Template benutzt. Ein Template ohne dynamische Teile importiert nichts (siehe `static`). Der Importpfad ist der Default der Option `runtime`, und du kannst ihn ändern.

Jeder Helfer nimmt dem generierten Code eine Entscheidung ab, sodass der generierte Code kurz bleibt und jedes Template die Randfälle gleich behandelt.

| Helfer | Was er tut | Verwendet für |
| --- | --- | --- |
| `toText(value)` | `null`, `undefined` und `false` werden zum leeren String, alles andere `String(value)` | `{expr}` in Text und in Strings |
| `toAttr(value)` | `null`, `undefined`, `false` ergeben `null` (kein Attribut), `true` ergibt `""`, alles andere seinen String | `attr=expr` |
| `joinClasses(list)` | verbindet die wahrheitsgemäßen Namen mit Leerzeichen, ergibt `null`, wenn nichts übrig bleibt | das Attribut `class` |
| `setAttr(attrs, name, value)` | setzt das Attribut, außer der Wert ist `null` | alle dynamischen Attribute in `render` |
| `sameValues(a, b)` | gleiche Werte oder Arrays mit gleichen Elementen | Event-Payloads mit mehreren Argumenten |
| `diffKeyedList(...)` | berechnet Entfernen, Einfügen und Verschieben für eine Liste mit key | `for ... key` in `diff` |
| `asView(value)` | macht aus einer Komponente oder einem view im State ihren view, oder `null` | `+{expr}#name`-Embeds |
| `childEnv`, `resolveOutlet` | finden die Komponente hinter einem Embed und das geroutete Kind eines `+outlet` | Embeds und outlets |

Die nächste Demo nutzt die Attribut-Helfer. Beachte, wie sich `null`, `false` und `true` verhalten.

::demo helpers open=module

`checked=done` mit `done: true` wird zu `checked=""`, so schreibt HTML ein boolesches Attribut. `disabled=locked` mit `locked: false` wird gar nicht geschrieben. `{note}` mit `note: null` ist ein leerer Text, nicht das Wort `null`. Im Schritt geht `done` von `true` auf `false`, also verschwindet `checked` (`rmAttr`), und die Klasse ebenfalls (`rmAttr`): `joinClasses` hat `null` zurückgegeben, weil kein Klassenname übrig blieb.

> [!TIP] Du importierst Helfer nie selbst
> Der Kommentar in der ersten Zeile von `helpers.ts` sagt es deutlich: Anwendungscode braucht sie nicht. Wenn du doch einmal einen lesen willst: Sie sind kurz. Die Tests in `runtime/helpers.test.ts` dokumentieren ihre Randfälle.

## Kind-views und der Modulgraph

Ein Template kann ein anderes Template einbetten. Die `import`-Zeile wird zu einem echten ES-Import, und das Embed wird zu einem Aufruf von `render` und `diff` des Kindes.

::demo embed open=module

Drei Dinge sind im Modul zu sehen. Die Zeile `import Badge from "./badge.pavlus";` stammt direkt aus dem Template. Der Wert `meta` sagt `embeds: ["status"]`: die Instanznamen der Kinder. Und der Textknoten des Kindes hat die id `1/3`: seine eigene id `1`, gefolgt vom Suffix `/3`, das der Parent hinzugefügt hat (`3` ist die Knoten-id des Embeds beim Parent). Im Schritt ruft das `diff` des Parents `Badge.diff` mit den alten und neuen Props auf, und die Antwort ist ein Patch für den Text des Kindes. Der Parent musste nicht wissen, was in `Badge` steckt.

## Ein größeres Template, von Anfang bis Ende

Zum Schluss eine kleine To-do-Liste mit Titel, einer Bedingung und einer Schleife mit key. Sie benutzt alles, was die Pipeline kennt: statische Knoten, dynamischen Text, einen Klassen-Umschalter, ein Event, ein `if`/`else` und ein `for`. Öffne zuerst den AST und lies die Spalte `reads:`, dann sieh dir die zwei Schritte an.

::demo todo open=ast

Ein paar Dinge, die du darin finden kannst.

- Der `else`-Zweig (`p.empty`) liest nichts, also haben seine Knoten keine ids und keinen Code in `diff`.
- Das `li` liest `item`, eine Schleifenvariable. Das `for` liest nur `items`, weil der Compiler Schleifenvariablen aus den Abhängigkeiten der Schleife entfernt (siehe [Abhängigkeitsanalyse](page:compiler-analysis)).
- Schritt eins markiert ein Element als erledigt. Das Ergebnis ist ein einziger `attr`-Patch auf der id `6#1`: Knoten `6`, Element-key `1`. Der Titel, die Fußzeile und das andere Element erzeugen keine Patches.
- Schritt zwei leert die Liste. Das `if` wechselt den Zweig, also lautet die Antwort des Compilers: alles zwischen den Markern `3s` und `3e` per `clear` entfernen, dann den neuen Zweig per `insert` einfügen, plus ein `text`-Patch für die Fußzeile.

## Was du gelernt hast

- Der Compiler macht aus einem Template einmal beim Build ein Modul mit `render`, `diff` und `meta`. Das kann er, weil Template-Ausdrücke eine kleine, reine Sprache sind.
- Die Stufen sind Parse, Analyze, Generate und Assemble. Der AST sagt, was jeder Knoten liest, und das generierte `diff` prüft nur, was ein Knoten liest.
- Ein view ist ein Paar reiner Funktionen. Das DOM-plugin rendert einmal, merkt sich Knoten per id und wendet danach die Patches an, die `diff` zurückgibt.
- Runtime-Helfer werden importiert, nie kopiert. Ein Template importiert nur die, die es benutzt.
