## 一分钟看懂核心思想

Pavlus 是一个用来构建 Web 界面的框架。它只遵守一条规则：**你写的代码不接触外部世界。** 它从不读取 DOM，不调用 `fetch`，不查询时间，也不往控制台写东西。它只反复回答一个问题：

> 给定这条 **message** 和这个 **state**，应该发生哪些 **effect**？

*message* 是一小块纯数据，说明刚刚发生了什么：`{ id: "inc" }` 表示“用户点了加号按钮”。*state* 是一个纯对象，保存屏幕上显示的全部内容。*effect* 同样是纯数据，它描述一件应该去做的事，例如“把字段 `count` 设为 3”或“发送这个 HTTP 请求”。你的代码只返回这份描述，并不亲自去做。

真正干活的是 **plugin**。每个 plugin 负责一类副作用：DOM、HTTP、定时器、浏览器地址、保存 state 的 store。当外部世界发生了什么（一次点击、一个响应、一次定时器触发），plugin 会把它变成 message 交给你的代码。当你的代码返回 effect 时，core 会把每个 effect 交给它所指向的 plugin。

第三部分是**模板语言**。你用简短的、基于缩进的 `.pavlus` 文件写出组件的 HTML 结构。编译器把它变成两个普通函数：`render(state)` 返回要显示的节点，`diff(prev, next)` 则在 state 从一个值变成另一个值时，返回所需的一小份变更列表（patch）。

```text
 click, reply, timer tick
          |   a plugin turns it into a message
          v
 your code:  (message, state)  ->  effects          pure, no side effects
          |   effects are plain data
          v
 plugins:    store, dom, http, time, router, ...    the only code that does things
          |   the store changed the state
          v
 template:   diff(prev, next)  ->  patches           pure, generated by the compiler
          |
          v
 the dom plugin applies the patches to the page
```

这和 Elm 语言是同一个循环，只是多了一个让模板部分变快的编译器。本系列的下一页 [快速开始](page:quick-start) 会搭建一个可运行的示例。[架构：纯代码与副作用](page:concepts-architecture) 一页则详细解释这个循环。

## 为什么要保持代码纯净

纯函数对相同的输入总是返回相同的结果，并且不改变自身以外的任何东西。仅这一个性质就能带来一些通常代价很高的好处：

- **不用浏览器就能测试。** 测试一个 handler，只需用一条 message 和一个 state 调用它，再用普通断言把返回的 effect 与期望值比较。没有任何东西需要 mock。
- **同一份代码可在服务端运行。** 渲染成字符串不需要 DOM，所以在浏览器里运行的组件也能在 Node 里运行。[服务端渲染](page:concepts-ssr) 一页会展示做法。
- **回放与历史。** state 是纯数据，每次变更都是一条被记录的 effect，所以你可以撤销一次变更，或回到更早的时刻。store plugin 会为你保存这份历史。
- **看得懂的 bug。** 出问题时，你可以直接打印 message 和 effect。它们都是普通对象。

代价是一条你必须自己遵守的规则：**框架不会检查你的代码是否纯净。** 如果某个 handler 偏要调用 `Date.now()`，没有任何东西会阻止它，上面这些好处也就没了。约定很简单：如果 handler 需要时间，就返回一个 `time` effect，并以 message 的形式收到答案。

## 一个完整的小程序

下面是一个完整的计数器，分四个部分。先是模板。它是组件的 HTML 结构，其中 `{count}` 读取 state 的字段 `count`，`@click=inc` 表示点击时发送 message `inc`。

::demo counter

上面的 demo 由真实的编译器在你的浏览器里编译。底部的两个步骤显示了 `count` 从 2 变到 3 再变回来时，`diff` 返回的 patch。只有文本节点发生变化。提示段落在条件 `count > 2` 变为真时被插入，变为假时被清除。

第二部分是组件。它是一个类，每个 message 对应一个方法。每个方法接收 message 和 state，并返回一个 effect 列表。这里的 effect 由 store plugin 的辅助函数 `store.set(path, value)` 构造，它返回纯对象 `{ plugin: "store", type: "set", path, value }`。

```ts counter.ts
import { Component, type Message } from "@service-laboratory/pavlus";
import { storeEffector as store } from "@service-laboratory/pavlus/plugins";
import view from "./counter.pavlus";

export interface CounterState {
  count: number;
}

export class Counter extends Component<CounterState> {
  view = view;

  inc(_msg: Message, state: CounterState) {
    return [store.set("count", state.count + 1)];
  }

  dec(_msg: Message, state: CounterState) {
    return [store.set("count", state.count - 1)];
  }
}

export const counter = new Counter();
```

第三部分是接线。`createApp` 把组件与它的 plugin 连接起来。store plugin 保存 state，DOM plugin 把组件的 view 渲染到元素 `#app` 中，并把点击作为 message 上报。

```ts main.ts
import { createApp } from "@service-laboratory/pavlus";
import {
  createDomPlugin,
  createStorePlugin,
} from "@service-laboratory/pavlus/plugins";
import { counter, type CounterState } from "./counter.ts";

createApp<CounterState>({
  app: counter,
  plugins: [createStorePlugin<CounterState>({ count: 0 }), createDomPlugin()],
  mount: "#app",
});
```

第四部分：没有别的了。没有 `useState`，没有订阅，没有 `setCount`。一次点击变成 `{ id: "inc" }`，`inc` 返回一个 `set` effect，store 替换 state，`diff` 比较新旧 state 并返回一个 `text` patch，DOM plugin 应用它。

> [!NOTE] state 不保存在组件里
> `Counter` 对象没有会变化的字段。state 保存在 store plugin 中，并被传给每个 handler。组件实例被所有 message 共享，所以它必须不含可变数据。[组件与状态](page:concepts-components) 一页解释了原因。

## pavlus 与虚拟 DOM 框架的比较

许多流行的框架使用*虚拟 DOM*：每次更新时，组件代码重新运行，构建一棵新的轻量节点树，框架再把它与前一棵树比较，找出变化的地方。对于 view 部分，pavlus 走的是另一条路。下表比较的是总体思路，而不是某个具体产品；它既说明 pavlus 得到了什么，也说明它放弃了什么。

| 问题 | 典型的虚拟 DOM 框架 | Pavlus |
| --- | --- | --- |
| 如何发现变化？ | 框架比较新旧两棵节点树。 | 编译器生成 `diff(prev, next)`，用 `===` 比较 state 字段。不比较任何树。 |
| 无关的变化要做多少工作？ | 取决于框架；通常组件函数会重新运行。 | 不读取任何已变字段的子树，一次检查就会被跳过。 |
| 更新逻辑放在哪里？ | 放在组件代码中，常常借助 hook 或 setter。 | 放在返回 effect 的 handler 中。view 里没有关于更新的逻辑。 |
| 副作用放在哪里？ | 组件代码的任何地方。 | 只放在 plugin 中。应用代码返回数据。 |
| 事件处理器是什么？ | 一个函数。 | 数据：`{ id, payload }`。`diff` 按值比较 handler。 |
| state 如何变更？ | 常通过 setter，有时直接修改。 | store 替换 state。你绝不能原地修改它，因为 `diff` 信任 `===`。 |
| 如何测试应用逻辑？ | 通常需要渲染器或 mock。 | 调用 handler，比较 effect。 |
| 模板用什么语言？ | 常是 JSX，和代码在同一个文件里。 | 单独的 `.pavlus` 文件，有自己的小型语法和表达式语言。 |
| 成熟度 | 庞大的生态、很多库、很多开发者。 | 一个年轻的框架，表面积很小。slot、递归模板和带类型的 props 尚未实现。 |

> [!WARNING] 这是一种取舍，并非处处更好
> 编译期 diff 对它所了解的内容很快，但模板语言比 JavaScript 小。表达式是一个小的纯子集，所以模板里没有箭头函数。需要真正代码的派生值，要在 handler 中计算后存进 state。Pavlus 还要求自律，因为纯净只是一种约定，没有任何东西强制执行。

## 你学到了什么

- 应用代码是纯的：输入 `(message, state)`，输出一个 effect 列表。effect 和 message 都是纯数据。
- Plugin 完成所有副作用，并把外部世界变成 message。core 用一个循环把它们连接起来。
- 模板编译成 `render` 和 `diff`。`diff` 通过比较每个节点读取的 state 字段来返回 patch。
- 一个完整的应用由模板、组件类，以及带有 store plugin 和 DOM plugin 的 `createApp` 调用组成。
- Pavlus 用一个小型模板语言和一条纯净约定，换来了简单的测试和廉价的更新。
