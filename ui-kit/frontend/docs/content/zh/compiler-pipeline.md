## 一分钟讲清思路

`.pavlus` 文件不会在运行时被解释。**编译器**在构建时读取它一次，然后写出一个普通的 JavaScript 模块。你的应用像导入其他模块一样导入这个模块。浏览器永远看不到模板文本，也不需要模板解析器。

这个模块导出三样东西。它们合在一起称为一个 **view**：

- `render(state)` 针对一个 state 返回整个模板，形式是一组普通对象。这些对象称为 **vnode**（虚拟节点）。
- `diff(prev, next)` 返回最小的 DOM 变更列表，把 `prev` 对应的页面变成 `next` 对应的页面。这些变更称为 **patch**。
- `meta` 是一个小对象，说明模板包含哪些子 view 以及哪个 `+outlet`。

请从上往下读结果。HTML 是 `render` 产生的。第一步展示了 `name` 从 `Ann` 变成 `Bob` 之后的 `diff`：一个 patch，`{"op":"text","id":"1","text":"Hello, Bob"}`。第二步展示了同一个 state 出现两次：完全没有 patch。打开模块来看：它大约有三十行，每一行都有它的理由。本页的其余部分会逐一解释。

## 各个阶段

编译器是一条很短的流水线。每个阶段都是一个普通函数，接收前一个阶段的输出。

| 阶段 | 函数 | 输入 | 输出 |
| --- | --- | --- | --- |
| 解析 | `parse` | 模板文本 | `TemplateAst`：import 和一棵节点树 |
| 分析 | `nodeDeps` | 一个节点 | 该节点读取的 state 字段集合 |
| 生成 | `generate` | AST | `meta`、`render` 和 `diff` 的 JavaScript 源码，以及它用到的运行时 helper 列表 |
| 组装 | `compileTemplate` | 模板文本 | 完整的 ES 模块字符串 |

分析并不是对整棵树单独做的一遍处理。代码生成器在为每个节点写守卫条件的时候，才向 `nodeDeps` 询问该节点的依赖（结果会按节点缓存）。它仍然是一个独立的阶段，因为它的答案决定了 `diff` 的样子。本页之后的几页会按顺序讲解各阶段：[解析](page:compiler-parser)、[依赖分析](page:compiler-analysis)，以及生成的 [render](page:compiler-render) 和 [diff](page:compiler-diff)。

在源码中，`compileTemplate(source, { filename, runtime })` 做了这些事：

1. 它调用 `parse(source)` 和 `generate(ast)`。如果其中任何一个抛出 `TemplateError`，并且你提供了 `filename`，错误信息前面会加上文件名：`app.pavlus: Unclosed { (line 1, col 8)`。
2. 它写入一行头部注释：`// Generated by pavlus from app.pavlus. Edit the template, not this file.`
3. 它为代码用到的每个运行时 helper 写一行 `import`，并为模板中的每个 `import` 行各写一行 `import`。子 view 通过真正的模块系统导入，所以你的打包器能看到它们。
4. 它写入生成的代码，然后是 `export { render, diff, meta };` 和 `export default { render, diff, meta };`。

> [!NOTE] 两种编译方式
> `compileTemplate` 以文本形式返回模块。Vite 插件使用它，本文档站点在向你展示“生成的模块”时也使用它。`compileToView` 编译同样的代码，并立即用 `new Function` 运行，直接给你一个现成的 view。它是为测试和工具准备的。这些页面上的 demo 两者都用：你可以展开的模块，以及产生 HTML 和 patch 的实时 view。

## 没有任何变化的模板

并不是每个模板都有值得一读的 `diff`。下面这个模板不从 state 读取任何东西。

::demo static open=module

这个模块没有 `import` 行，因为它没有用到任何 helper。`render` 每次都构建相同的 vnode。`diff` 里没有任何比较：只有快捷判断 `if (prev === next) return patches;` 和最后的 `return patches;`。编译器发现没有任何节点读取 state，所以什么都没有多写。这些 vnode 也没有 `id`：id 的存在只是为了让 patch 能指明某个节点，而这里没有任何东西会被 patch。

这是编译器的第一个重要思路：**只在可能发生变化的地方花费代码**。

## 从文本到 AST 再到代码

现在来看一个带有一个动态属性、一个 class 切换和一处插值的模板。我们展开 demo 能显示的所有部分：模块、AST 和 vnode。

::demo stages open=module,ast,vnodes

请按编译器工作的顺序来看这三个部分。

**AST** 有两个节点：元素 `a`（节点 `#0`）和它的文本（节点 `#1`）。每个节点旁边是 `reads:`，也就是该节点需要的 state 字段集合。元素读取 `active`、`title` 和 `url`，因为它的属性和子节点读取了它们。文本只读取 `title`。数字 `#0` 和 `#1` 是**节点 id**（`nid`）。解析器按文档顺序分配它们。

**模块**里先是 `render`。它先写子节点，再写元素，所以文本先被构建并推入 `aChildren`。然后它构建属性对象 `aAttrs`，每个动态属性一行，再推入元素。接下来是 `diff`。对于元素，它写了一个守卫：`if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title)`。在守卫内部，每个属性分别针对 `prev` 和 `next` 计算，只有两个值不同时才推入 patch。对于文本，另有一个更小的守卫，只检查 `title`。

**vnode** 是 `render` 返回的内容。元素和文本都带有一个 `id`（`"0"` 和 `"1"`），也就是字符串形式的节点 id。它们有 id，是因为 `diff` 可以指明它们。这一步里的 patch `{"op":"attr","id":"0","name":"class","value":"link active"}` 使用的就是元素的 id。只有 `class` 被 patch：`href` 和文本没有变化。

## 导入 .pavlus 文件时你得到什么

在 Vite 项目中，`pavlus()` 插件会编译每个以 `.pavlus` 结尾的文件。插件会跳过以 `?raw`、`?url` 或 `?inline` 结尾的导入，因为这些导入要的是文件本身。对于其他任何导入，你得到的是编译器写出的模块。

```ts main.ts
import view from "./counter.pavlus";
import { render, diff, meta } from "./counter.pavlus";

const vnodes = render({ count: 1 });
const patches = diff({ count: 1 }, { count: 2 });
```

默认导出和三个具名导出是同样的对象。默认导出是 **view**，其他代码期望的正是它：DOM plugin 接收一个 view 来挂载，被 embed 的子组件（`+Badge#status`）也是一个 view。这两个函数都是**纯函数**。它们只读取自己的参数，不读取别的东西，不改变任何东西，并且对相同的输入给出相同的结果。这就是它们可以在服务器、测试或浏览器中运行的原因，也是本站的 demo 能为你运行它们的原因。

下面是生成代码中 view 的参数：

```ts
function render(state, idSuffix = "", messagePrefix = "", env)
function diff(prev, next, idSuffix = "", messagePrefix = "", env)
```

顶层 view 使用默认值。最后三个参数是为 **embed** 而存在的。当模板包含 `+Badge#status` 时，父级会调用 `Badge.render`，传入更长的 `idSuffix`（`"/3"`，这样子级的节点 id 就不会与父级的冲突）、更长的 `messagePrefix`（`"status."`，这样子级的 message 就以它的实例命名），以及一个 `env`，即拥有该 view 的组件对象。应用代码从不传入它们。

## render、diff 与 DOM plugin 之间的约定

DOM plugin 是框架中唯一接触 DOM 的代码。它依赖生成的代码所遵守的三个承诺。这三个承诺就是 `render` 和 `diff` 要从同一个 AST 一起生成的原因。

1. **第一次 render 建立映射。** plugin 挂载一个 view 时，会调用一次 `render(state)`，并根据 vnode 构建真实的 DOM。对于每个带 `id` 的 vnode，它会把对应的 DOM 节点记在这个 id 之下。
2. **patch 只会指明 render 产生过的 id。** 像 `{ op: "text", id: "1", text: "Hello, Bob" }` 这样的 patch，其应用方式是“找到存放在 `1` 下的节点，并设置它的文本”。如果 id 未知，plugin 会抛出 `unknown node id`。编译器保证 `diff` 能 patch 的每个节点在 `render` 中都有一个 `id`。
3. **后续的 state 是做 diff，而不是重新 render。** 当 state 改变时，plugin 调用 `diff(oldState, newState)` 并按顺序应用 patch。页面的新片段（新的 `if` 分支、新的列表项）会以现成的 vnode 放在 `insert` patch 里到达，plugin 也会注册它们的 id。

所以 vnode 不只是页面的一幅图。它是一幅图加上一份目录。下一个 demo 把这一点具体化。一个 `button` 带有一个事件；请看 vnode 的哪些部分带有 id，以及这一步的两个 patch。

::demo events open=vnodes

`button` 有一个 `id`，因为它的事件有一个可能变化的参数（`add(step)`）。patch `{"op":"handler",...}` 把新的 message 交给 plugin，因此点击时会发送 `{ id: "add", payload: 5 }`。plugin 从不移除再重新添加监听器：它为每个元素和事件类型只保留一个监听器，并替换这个监听器所读取的 message。

> [!WARNING] 编译器信任对象的同一性
> `diff` 用 `!==` 比较值。内容相同的新对象算作变化。同一个对象被原地修改了内容，则算作没有变化。对于发生变化的部分，务必给下一个 state 提供新对象（展开、`map`、`filter`），并且永远不要修改前一个 state。

## 为什么要在构建时编译

你也可以写一个库，在运行时读取模板文本并遍历它。许多模板引擎就是这样工作的。pavlus 编译器把工作提前完成，好处是实实在在的。

- **`diff` 专属于你的模板。** 生成的 `diff` 只包含你的模板需要的那些比较，不多也不少。没有通用的树遍历，也不会对两棵完整的 vnode 树做比较。在 `static` demo 中，它一个比较都没有。
- **除了你的代码，没有别的要发送。** 浏览器收到的是普通函数加上一小组 helper。它不会收到解析器、表达式解释器或模板字符串。
- **错误在构建时出现。** 模板里的拼写错误会让构建停下来，并给出文件名、行号和列号。它不会等到用户打开页面。
- **输出是可读的。** 生成的代码带有注释，标明每个节点的源码行（`// line 1: <a.link>`），名称取自你的标签（`aChildren`、`liAttrs`），并且每个想法一条语句。遇到意外时，你可以阅读它。
- **纯函数很容易在各处使用。** 服务端渲染调用 `view.render(state)`，把 vnode 转成 HTML。单元测试调用 `diff(a, b)` 并检查 patch。不需要任何浏览器。

代价是，模板的表达式只能使用 JavaScript 中一个很小的、纯粹的子集（见[表达式与插值](page:syntax-expressions)）。编译器必须理解每个表达式，才能知道它读取了什么。这个限制是有意为之的。

## 运行时 helper

看一下 `stages` 模块的第一行：`import { joinClasses, setAttr, toAttr, toText } from "@service-laboratory/pavlus/runtime";`。生成的代码里不包含这些小函数的副本。它们只在 `runtime/helpers.ts` 中存在一份，编译器只导入模板实际用到的那些。没有动态部分的模板什么都不导入（见 `static`）。这个导入路径是 `runtime` 选项的默认值，你可以修改它。

每个 helper 的存在都是为了从生成的代码中去掉一个决定，这样生成的代码保持简短，并且每个模板处理边界情况的方式都相同。

| Helper | 作用 | 用于 |
| --- | --- | --- |
| `toText(value)` | `null`、`undefined` 和 `false` 变成空字符串，其他都变成 `String(value)` | 文本和字符串中的 `{expr}` |
| `toAttr(value)` | `null`、`undefined`、`false` 得到 `null`（没有属性），`true` 得到 `""`，其他得到它的字符串 | `attr=expr` |
| `joinClasses(list)` | 用空格连接真值的名称，什么都不剩时得到 `null` | `class` 属性 |
| `setAttr(attrs, name, value)` | 设置属性，除非值是 `null` | `render` 中的所有动态属性 |
| `sameValues(a, b)` | 值相等，或者数组的各项相等 | 带多个参数的事件 payload |
| `diffKeyedList(...)` | 为带 key 的列表计算移除、插入和移动 | `diff` 中的 `for ... key` |
| `asView(value)` | 把 state 中的组件或 view 转成它的 view，否则得到 `null` | `+{expr}#name` embed |
| `childEnv`、`resolveOutlet` | 找到 embed 背后的组件，以及 `+outlet` 的路由子级 | embed 和 outlet |

下一个 demo 用到了属性 helper。请注意 `null`、`false` 和 `true` 的表现。

::demo helpers open=module

`checked=done` 在 `done: true` 时变成 `checked=""`，这就是 HTML 书写布尔属性的方式。`disabled=locked` 在 `locked: false` 时完全不会被写出。`{note}` 在 `note: null` 时是空文本，而不是单词 `null`。在这一步中，`done` 从 `true` 变成 `false`，所以 `checked` 消失了（`rmAttr`），class 也消失了（`rmAttr`）：`joinClasses` 返回了 `null`，因为没有剩下任何 class 名称。

> [!TIP] 你永远不需要自己导入 helper
> `helpers.ts` 第一行的注释说得很明白：应用代码不需要它们。如果你想读其中某一个，它们都很短。`runtime/helpers.test.ts` 中的测试记录了它们的边界情况。

## 子 view 与模块图

一个模板可以 embed 另一个模板。`import` 行会变成真正的 ES import，embed 则变成对子级 `render` 和 `diff` 的调用。

::demo embed open=module

模块里有三点值得注意。`import Badge from "./badge.pavlus";` 这一行直接来自模板。`meta` 的值是 `embeds: ["status"]`：即子级的实例名。而子级的文本节点的 id 是 `1/3`：它自己的 id `1`，加上父级添加的后缀 `/3`（`3` 是父级中该 embed 的节点 id）。在这一步中，父级的 `diff` 用旧的和新的 props 调用 `Badge.diff`，得到的结果是针对子级文本的一个 patch。父级不需要知道 `Badge` 内部有什么。

## 一个更大的模板，从头到尾

最后，来看一个小小的待办列表，带有标题、一个条件和一个带 key 的循环。它用到了流水线所知道的一切：静态节点、动态文本、class 切换、事件、`if`/`else` 和 `for`。请先打开 AST，读一读 `reads:` 这一列，然后再看这两个步骤。

::demo todo open=ast

可以在里面找到这几点。

- `else` 分支（`p.empty`）不读取任何东西，所以它的节点没有 id，在 `diff` 里也没有代码。
- `li` 读取 `item`，这是一个循环变量。`for` 节点只读取 `items`，因为编译器会从循环的依赖中去掉循环变量（见[依赖分析](page:compiler-analysis)）。
- 第一步把一个条目标记为完成。结果是对 id `6#1` 的单个 `attr` patch：节点 `6`，条目 key `1`。标题、页脚和另一个条目都不产生 patch。
- 第二步清空列表。`if` 切换了分支，所以编译器给出的答案是：`clear` 标记 `3s` 和 `3e` 之间的所有内容，然后 `insert` 新分支，再加上页脚的一个 `text` patch。

## 你学到了什么

- 编译器在构建时一次性把模板变成带有 `render`、`diff` 和 `meta` 的模块。它之所以能做到，是因为模板表达式是一门小而纯粹的语言。
- 各阶段是解析、分析、生成和组装。AST 说明每个节点读取什么，而生成的 `diff` 只检查节点读取的内容。
- view 是一对纯函数。DOM plugin 只 render 一次，按 id 记住节点，然后应用 `diff` 返回的 patch。
- 运行时 helper 是导入的，从不复制。模板只导入它用到的那些。
