## The compiler is a function from text to text

You have seen what the compiler generates. This page is about how to run it. At its core the compiler is one function: it takes the text of a template and returns the text of a JavaScript module. It does not read files, it does not touch the DOM, and it does not need a browser. The same input always gives the same output.

Here is the smallest example. Open the generated module and read it from the top.

::demo smallest open=module

A compiled module always has the same parts, in the same order:

1. A header comment: `// Generated by pavlus from smallest.pavlus. Edit the template, not this file.`
2. One `import` of the runtime helpers the module uses (here only `toText`). A template that uses no helper has no import at all.
3. One `import` for every template your template imports with its own `import` line.
4. `const meta`, which lists the instance names of the embedded children and says whether the template has an `+outlet`.
5. The two functions, `render` and `diff`, each with a comment that says it is pure.
6. Two exports: the names `render`, `diff` and `meta`, and a default export, an object `{ render, diff, meta }`. That object is a **view**, the thing the DOM plugin mounts.

## compileTemplate

The function is exported from `@service-laboratory/pavlus/compiler`. It takes the source and an options object, and returns the module text.

```ts
import {
  compileTemplate,
  DEFAULT_RUNTIME,
} from "@service-laboratory/pavlus/compiler";

const source = "p Hello, {name}";
const code = compileTemplate(source, { filename: "src/hello.pavlus" });

console.log(DEFAULT_RUNTIME); // "@service-laboratory/pavlus/runtime"
```

There are two options, and both are optional.

| Option | Default | What it does |
| --- | --- | --- |
| `filename` | none | Put in front of every error message, and used for the header comment. Only the last part of the path is written in the header, so the output does not depend on where your project is. |
| `runtime` | `DEFAULT_RUNTIME` | The module the helpers are imported from. |

The `runtime` option changes one line. With `{ runtime: "/src/runtime/helpers.ts" }` the module starts with:

```ts
// Generated by pavlus from a template. Edit the template, not this file.
import { toText } from "/src/runtime/helpers.ts";
```

The helpers (`toText`, `toAttr`, `joinClasses`, `setAttr`, `sameValues`, `asView`, `diffKeyedList`, `resolveOutlet`, `childEnv`) live in the runtime, once, and are not pasted into every template. The compiler imports **only the helpers a template uses**, sorted by name. When the line would be longer than 100 characters, it is written with one name per line.

::demo many-helpers open=module

Look at the first lines of the module. Five helpers are used, so the import is a block. A loop with a key needs `diffKeyedList`, a class toggle needs `joinClasses` and `setAttr`, a dynamic attribute needs `toAttr`, and the text needs `toText`.

When a template imports another template, the compiler copies the path as you wrote it into an `import`, and the bundler resolves it.

::demo with-child open=module

The first two lines after the header are `import { childEnv, toText } from ...` and `import Badge from "./badge.pavlus";`. The second one is from your template, the first one is from the compiler. The `meta` line says `embeds: ["badge"]`: the instance names of the children. Because `./badge.pavlus` is itself a `.pavlus` file, it is compiled by the same plugin when the bundler reaches it.

## compileToView

Sometimes you want a working view and not a text: in a test, in a script, or in a documentation page like this one. `compileToView` compiles the source and then runs the code, with the runtime helpers passed in as arguments, and returns the view.

```ts
import { compileToView } from "@service-laboratory/pavlus/compiler";

const view = compileToView("p Hello, {name}");
view.render({ name: "Ann" });
view.diff({ name: "Ann" }, { name: "Bob" });
```

If the template has `import` lines, the views must be given by their local name:

```ts
const badge = compileToView("span.badge {label}");
const row = compileToView(
  `import Badge from "./badge.pavlus"
li +Badge#badge(label=role)`,
  { components: { Badge: badge } },
);
```

A value in `components` is a view, or an object that has a `view`. If a name is missing, the call stops with this message:

```text
pavlus: template imports "Badge" but no view was given in { components }
```

`compileToView` builds the function with `new Function`, so it needs a page that allows it. Use `compileTemplate` and a bundler for an application, and `compileToView` for tests and tools.

## The Vite plugin

In an application you do not call the compiler yourself. A Vite plugin calls it for you for every template that your code imports. It is exported from `@service-laboratory/pavlus/vite` as `pavlus()`.

```ts vite.config.ts
import { defineConfig } from "vite";
import { pavlus } from "@service-laboratory/pavlus/vite";

export default defineConfig({
  plugins: [pavlus()],
});
```

The plugin is small, and everything it does can be said in a few lines:

- It runs `transform` with `enforce: "pre"`, before the other plugins.
- It handles a module when the path, without its query string, ends in `.pavlus`. All other modules return `null` and are left alone. The option `extension` changes the suffix (`pavlus({ extension: ".pv" })`).
- It skips the queries `?raw`, `?url` and `?inline`, so `import source from "./card.pavlus?raw"` gives you the text of the template and not the compiled module. This is how the golden tests below read their input.
- It calls `compileTemplate(code, { filename, runtime })`. The `filename` is the full path of the file, and `runtime` is the option you gave it.
- It returns the module with `map: { mappings: "" }`, which means "no source map". This is a decision and not a gap: Vite would invent a map that points the generated code to itself, which is big and says nothing. Without a map, the browser's DevTools shows the generated `render` and `diff`, and that is what you want to debug.
- When the compiler throws, it calls Vite's `this.error` with the message, so the build stops and shows the error with the file name.

There is no code for hot updates in the plugin and no `import.meta.hot` in the generated module. A saved template is transformed again, like any other module, and Vite applies its usual rule for modules that do not accept updates.

### Where the runtime comes from

A compiled module imports `@service-laboratory/pavlus/runtime`, so the package must be installed, like for any other import. If the helpers are somewhere else, for example in a monorepo where the package is the source, you have two ways. Use the `runtime` option, or use a Vite alias. The framework's own tests use an alias:

```ts
export default defineConfig({
  plugins: [pavlus()],
  resolve: {
    alias: {
      "@service-laboratory/pavlus/runtime": "/path/to/src/runtime/helpers.ts",
    },
  },
});
```

### Using a template

A template is a module like any other. Import the default export, which is the view, and give it to a component.

```pavlus counter.pavlus
section.counter
  h1 {count}
  button(@click=inc) Add one
```

```ts main.ts
import {
  Component,
  createApp,
  type Effect,
  type Message,
} from "@service-laboratory/pavlus";
import { createDomPlugin } from "@service-laboratory/pavlus/plugins/dom";
import {
  createStorePlugin,
  storeEffector as store,
} from "@service-laboratory/pavlus/plugins/store";
import view from "./counter.pavlus";

interface State {
  count: number;
}

class Counter extends Component<State> {
  view = view;
  inc(_msg: Message, state: State): Effect[] {
    return [store.set("count", state.count + 1)];
  }
}

createApp<State>({
  app: new Counter(),
  plugins: [createStorePlugin<State>({ count: 0 }), createDomPlugin()],
  mount: "#app",
});
```

The `@click=inc` of the template is the message `inc`. The method `inc` of the component handles it and returns an effect as data. The store plugin changes the state, the DOM plugin calls `view.diff` and applies the patches.

### Types for template imports

TypeScript does not know what a `.pavlus` file is. The package ships a declaration file for that, `@service-laboratory/pavlus/env`. Reference it once, in a `.d.ts` file that your `tsconfig.json` includes:

```ts env.d.ts
/// <reference types="vite/client" />
/// <reference types="@service-laboratory/pavlus/env" />
```

After that, `import view from "./counter.pavlus"` has the type `View`, and the named exports `render`, `diff` and `meta` have types too. The declaration says that `render(state: any, ...)` and `diff(prev: any, next: any, ...)` take any state, so TypeScript does not check the state against the template. Types for `?raw` imports come from `vite/client`.

## Errors

A template that cannot be compiled throws a `TemplateError`. Its message ends with the position, `(line 3, col 5)`, with 1-based numbers, and the error object also has the fields `line` and `col`. When you pass a `filename` (the Vite plugin always does) the message starts with the file name.

Here are the errors you will meet most often. Each block shows a template and the exact message that the compiler returns for it with the file name `card.pavlus`.

A tab in the indentation:

```pavlus-invalid
ul
	li Item
```

```text
card.pavlus: Tabs are not allowed, use spaces (line 2, col 1)
```

A brace that is not closed:

```pavlus-invalid
p Hello, {name
```

```text
card.pavlus: Unclosed { (line 1, col 8)
```

An expression that is not finished, or has a character that is not part of the expression language:

```pavlus-invalid
div
  p {total +}
```

```text
card.pavlus: Unexpected end of expression (line 2, col 13)
```

```pavlus-invalid
p {price # 2}
```

```text
card.pavlus: Unexpected character "#" (line 1, col 10)
```

An `else` that has no `if` before it. Note that `else` also cannot follow a `for`:

```pavlus-invalid
div
  p one
else
  p two
```

```text
card.pavlus: `else` without matching `if` (line 3, col 1)
```

A child that was not imported. The message tells you both ways to fix it:

```pavlus-invalid
div
  +Card#card(title=title)
```

```text
card.pavlus: "Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

A handler that is not a message name:

```pavlus-invalid
button(@click=1+2) Go
```

```text
card.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

A line under an element that cannot have children:

```pavlus-invalid
input(value=x)
  p inside
```

```text
card.pavlus: This line cannot have children (line 2, col 1)
```

A dynamic embed with no instance name, a late `import`, a class toggle with a string, and `+outlet` with arguments:

```text
card.pavlus: A dynamic component needs an instance name: +{expr}#name(...) (line 1, col 9)
card.pavlus: `import` lines must be at the top of the file (line 2, col 1)
card.pavlus: "class:on" needs an expression value (line 1, col 4)
card.pavlus: `+outlet` takes nothing after it (line 2, col 10)
```

In a Vite build, the message arrives inside the build error. This is what a Vite 8 build prints, shortened, for a template that has the line `  li {name`:

```text
Build failed with 1 error:

[plugin pavlus] /project/src/bad.pavlus
RolldownError: /project/src/bad.pavlus: Unclosed { (line 2, col 3)
```

> [!WARNING] Some typos are not errors
> The compiler recognizes `if`, `else`, `for` and `+` by the form of the whole line. A line that almost matches is a normal element. `if` alone, with no condition, is the element `<if>`. `for item of items` (with `of` instead of `in`) is the element `<for>` with the text `item of items`. Neither one is an error, and the page renders without the block you wanted. When something that should be a block shows up as a tag, check the line against the syntax.

## The golden files

How can the authors of the compiler change it with confidence? The test suite has two layers.

The first layer, `output.test.ts`, checks **properties** of the output: the helpers are imported and not pasted, only the used helpers are imported, the variables have names that come from the template (`userList`, `prevUserKeys`, `liChildren`), the comments say which line and which dependencies a block has, and the code has no very long lines.

The second layer pins **every byte**. In the folder `framework/src/compiler/__fixtures__` there are eleven small templates, and in `__goldens__` the exact JavaScript that the compiler must produce for each one:

| Fixture | What it exercises |
| --- | --- |
| `static` | Nothing depends on the state, so `diff` is empty. |
| `text` | Text lines, interpolation, escaped braces. |
| `element` | Dynamic attributes, class toggles, events with arguments and modifiers. |
| `names` | Loop variables named like JavaScript keywords or generated names. |
| `if` | `if`, `else if`, `else`, a loop without a key, a second `if`. |
| `for` | Keyed loops with an index, nested loops, an `if` inside a loop. |
| `embed-static` | Imported children, props, spread, an embed inside a loop. |
| `embed-dynamic` | `+{expr}` under an `if`, with spread props. |
| `outlet` | The `+outlet` node. |
| `shell`, `dashboard` | Two real pages: a menu with a long class expression, and a dashboard. |

The golden test reads each fixture with `?raw` (which works because the plugin skips that query), compiles it with `compileTemplate(source, { filename: "<name>.pavlus" })`, and compares the result to the file with `toMatchFileSnapshot`. A last test checks that the fixtures together use every kind of node: elements, text, `if` with `else if` and `else`, keyed and unkeyed `for`, static and dynamic embeds, `+outlet`, class toggles, and the `prevent`, `stop` and many-arguments forms of events. If you add a new feature to the syntax, that test fails until a fixture uses it.

If a change of the compiler alters the output on purpose, you run the tests with `-u` and read the diff of `__goldens__/` in the review. If it was a refactor, the diff must be empty. That is the point of pinning the bytes: a change in the output cannot go unnoticed.

### How to read a golden

The goldens are the best documentation of the output, because they are always correct. To read one, start from the template, and find these landmarks:

- The comments `// line N: <tag>` map a block to a line of the template. The same line appears in `render` and in `diff`.
- In `render`, find the variables `xChildren` and `xAttrs`. They are built first, bottom up, and the element is pushed last.
- In `diff`, find the comment with `(reads: ...)`. The next line is its guard.
- Find `idSuffix`. Every id is the number of a node plus the suffix, so you can follow one node through `render` and `diff`.
- For a loop, find `diffKeyedList`, and read its four functions.

## Testing a view

A view is made of two pure functions, and a test for a view is a normal test. You do not need a browser for the first kind.

```pavlus todos.pavlus
ul
  for todo in todos key todo.id
    li(class:done=todo.done @click=toggle(todo.id)) {todo.title}
p {todos.length} todos
```

```ts todos.test.ts
import { expect, test } from "vitest";
import view from "./todos.pavlus";

const write = { id: 1, title: "Write", done: false };

test("finishing a todo changes only its class", () => {
  const patches = view.diff(
    { todos: [write] },
    { todos: [{ ...write, done: true }] },
  );
  expect(patches).toEqual([
    { op: "attr", id: "2#1", name: "class", value: "done" },
  ]);
});

test("nothing changed, nothing to patch", () => {
  expect(view.diff({ todos: [write] }, { todos: [write] })).toEqual([]);
});
```

These two tests run in plain Node. The test runner needs the plugin, so the Vite or Vitest configuration must have `pavlus()` in `plugins`.

For a test that includes the DOM, the package has `@service-laboratory/pavlus/testing`. Its function `mountView(viewOrComponent, initialState, document?)` mounts the view in a fresh container with the real DOM plugin, without the rest of the application. It returns the container (`root`), the DOM plugin, the list of messages that the user's events produced (`messages`), and the functions `set(nextState)` and `unmount()`. Mount a component, and not only its view, when the template has an `+outlet`, because the outlet needs the component's `routing`.

```ts todos.dom.test.ts
// @vitest-environment jsdom
import { expect, test } from "vitest";
import { mountView } from "@service-laboratory/pavlus/testing";
import view from "./todos.pavlus";

test("the DOM follows the state, and a click sends a message", () => {
  const write = { id: 1, title: "Write", done: false };
  const check = { id: 2, title: "Test", done: false };
  const h = mountView(view, { todos: [write, check] });

  h.set({ todos: [write, { ...check, done: true }] });
  expect(h.root.querySelectorAll("li")[1].className).toBe("done");

  h.root.querySelector("li")!.click();
  expect(h.messages).toMatchObject([{ id: "toggle", payload: 1 }]);

  h.unmount();
  expect(h.root.innerHTML).toBe("");
});
```

The `messages` array holds what the DOM plugin dispatched. The click on the first item produced `{ id: "toggle", payload: 1, event: { type: "click" } }`: the message id and the payload come from the template, and the `event` field is added by the plugin. `h.root.innerHTML` right after `mountView` is:

```text
<!--pavlus--><ul><!----><!----><li>Write</li><!----><!----><li>Test</li><!----><!----></ul><p>2 todos</p><!--/pavlus-->
```

That is a good way to see the markers: each item sits between two empty comments, and the list between two more. The comments `pavlus` and `/pavlus` delimit the whole render.

## What you learned

- `compileTemplate(source, { filename, runtime })` returns the text of an ES module with `render`, `diff`, `meta` and a default view. `compileToView` returns a working view and is meant for tests and tools. `DEFAULT_RUNTIME` is where the helpers come from.
- The Vite plugin `pavlus()` compiles every `.pavlus` import, skips `?raw`, `?url` and `?inline`, ships no source map on purpose, and reports a template error with its file, line and column.
- `@service-laboratory/pavlus/env` gives `.pavlus` imports their types. The state is typed as `any`.
- Compiler errors are `TemplateError`s with 1-based positions, and a few typos make elements and not errors.
- Golden files pin the exact output of eleven fixtures, so a change in the generated code is always visible in a review. A view can be tested as two pure functions, or mounted with `mountView`.
