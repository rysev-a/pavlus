## The idea in one minute

Pavlus is a framework for building web interfaces. It rests on one rule: **the code you write does not touch the outside world.** It never reads the DOM, calls `fetch`, asks for the time or writes to the console. Instead it answers one question, again and again:

> Given this **message** and this **state**, which **effects** should happen?

A *message* is a small piece of plain data that says what just happened: `{ id: "inc" }` means "the user clicked the plus button". The *state* is a plain object that holds everything the screen shows. An *effect* is also plain data. It describes something that should be done, such as "set the field `count` to 3" or "send this HTTP request". Your code only returns the description. It does not do the work.

The work is done by **plugins**. A plugin owns one kind of side effect: the DOM, HTTP, timers, the browser location, the store that holds the state. When something happens in the outside world (a click, a reply, a timer tick), a plugin turns it into a message and gives it to your code. When your code returns effects, the core hands each effect to the plugin it is addressed to.

The third part is the **template language**. You write the HTML structure of a component in a short, indentation-based `.pavlus` file. A compiler turns it into two plain functions: `render(state)`, which returns the nodes to show, and `diff(prev, next)`, which returns the small list of changes (patches) needed when the state moves from one value to another.

```text
 click, reply, timer tick
          |   a plugin turns it into a message
          v
 your code:  (message, state)  ->  effects          pure, no side effects
          |   effects are plain data
          v
 plugins:    store, dom, http, time, router, ...    the only code that does things
          |   the store changed the state
          v
 template:   diff(prev, next)  ->  patches           pure, generated by the compiler
          |
          v
 the dom plugin applies the patches to the page
```

This is the same loop as in the Elm language, with a compiler that makes the template side fast. The next page of this series, [Quick start](page:quick-start), builds a running example. The page [Architecture](page:concepts-architecture) explains the loop in detail.

## Why keep code pure

A pure function always returns the same result for the same input, and changes nothing outside itself. That one property gives you things that are usually expensive:

- **Tests without a browser.** To test a handler you call it with a message and a state and compare the returned effects with plain asserts. There is nothing to mock.
- **The same code on the server.** Rendering to a string needs no DOM, so the components you run in the browser also run in Node. The page [Server-side rendering](page:concepts-ssr) shows how.
- **Replay and history.** A state is plain data and every change is a recorded effect, so you can undo a change or go back to an earlier moment. The store plugin keeps that history for you.
- **Readable bugs.** When something goes wrong, you can print the message and the effects. Both are ordinary objects.

The price is a rule you must follow yourself: **the framework does not check that your code is pure.** If a handler calls `Date.now()` anyway, nothing stops it, and you lose the benefits above. The convention is simple. If a handler needs the time, it returns a `time` effect and receives the answer as a message.

## A tiny whole program

Here is a complete counter, in four parts. First the template. It is the HTML structure of the component, with `{count}` reading the field `count` of the state, and `@click=inc` saying that a click sends the message `inc`.

::demo counter

The demo above is compiled by the real compiler in your browser. The two steps at the bottom show the patches `diff` returns when `count` goes from 2 to 3 and back. Only the text node changes. The hint paragraph is inserted when the condition `count > 2` becomes true, and cleared when it becomes false.

Second, the component. It is a class with one method per message. Each method receives the message and the state and returns a list of effects. Here the effects are built with the store plugin's helper `store.set(path, value)`, which returns the plain object `{ plugin: "store", type: "set", path, value }`.

```ts counter.ts
import { Component, type Message } from "@service-laboratory/pavlus";
import { storeEffector as store } from "@service-laboratory/pavlus/plugins";
import view from "./counter.pavlus";

export interface CounterState {
  count: number;
}

export class Counter extends Component<CounterState> {
  view = view;

  inc(_msg: Message, state: CounterState) {
    return [store.set("count", state.count + 1)];
  }

  dec(_msg: Message, state: CounterState) {
    return [store.set("count", state.count - 1)];
  }
}

export const counter = new Counter();
```

Third, the wiring. `createApp` connects the component to its plugins. The store plugin holds the state, and the DOM plugin renders the component's view into the element `#app` and reports clicks as messages.

```ts main.ts
import { createApp } from "@service-laboratory/pavlus";
import {
  createDomPlugin,
  createStorePlugin,
} from "@service-laboratory/pavlus/plugins";
import { counter, type CounterState } from "./counter.ts";

createApp<CounterState>({
  app: counter,
  plugins: [createStorePlugin<CounterState>({ count: 0 }), createDomPlugin()],
  mount: "#app",
});
```

Fourth, there is nothing else. No `useState`, no subscriptions, no `setCount`. A click becomes `{ id: "inc" }`, `inc` returns a `set` effect, the store replaces the state, `diff` compares the old and the new state and returns one `text` patch, and the DOM plugin applies it.

> [!NOTE] The state does not live in the component
> The `Counter` object has no fields that change. The state lives in the store plugin and is passed to every handler. The component instance is shared by all messages, so it must stay free of mutable data. The page [Components and state](page:concepts-components) explains why.

## The pieces and where they live

Pavlus is small enough that each piece has one clear job. This table is the map of the framework. The last column says which page of this documentation covers it.

| Piece | What it does | Read |
| --- | --- | --- |
| Template language | Indentation-based markup with `{expressions}`, `if`, `for`, events and embedded child views. | [Elements, text and attributes](page:syntax-elements) |
| Compiler | Turns a `.pavlus` file into readable JavaScript with `render` and `diff`. Knows which state each node reads. | [The compilation pipeline](page:compiler-pipeline) |
| Vite plugin | Runs the compiler for every `.pavlus` import, in development and in the build. | [Quick start](page:quick-start) |
| Components | A function or a class with one handler per message. May have a `view`, `children` and `routing`. | [Components and state](page:concepts-components) |
| Messages | Plain data `{ id, payload, event }`. Routed to child components by the prefix of the id. | [Messages and child components](page:concepts-messages) |
| Core | `createApp`: a message queue, the plugin registry, and the loop that calls your code and the plugins. | [Architecture](page:concepts-architecture) |
| Routing | A table of paths and child components, and an `+outlet` in the template. | [Routing](page:concepts-routing) |
| SSR | `renderToString` on the server, hydration in the browser. | [Server-side rendering](page:concepts-ssr) |
| Plugins | `store`, `dom`, `http`, `ws`, `time`, `logger`, `router`, and the ones you write. | [How plugins work](page:plugins-overview) |
| Testing | Handlers are plain functions. `mountView` mounts a view in a test without the core. | [Architecture](page:concepts-architecture) |

## How pavlus compares to virtual DOM frameworks

Many popular frameworks use a *virtual DOM*: on each update the component code runs again, builds a new tree of lightweight nodes, and the framework compares it with the previous tree to find what changed. Pavlus takes a different route for the view part. The table compares the approach in general, not any one product, and it states what pavlus gives up as well as what it gains.

| Question | Typical virtual DOM framework | Pavlus |
| --- | --- | --- |
| How is a change found? | The framework compares the old and the new tree of nodes. | The compiler generates a `diff(prev, next)` that compares state fields with `===`. No tree is compared. |
| How much work for an unrelated change? | Depends on the framework; often the component function runs again. | A subtree that reads none of the changed fields is skipped by one check. |
| Where does the update logic live? | In the component code, often with hooks or setters. | In handlers that return effects. The view has no logic about updating. |
| Where do side effects live? | Anywhere in the component code. | Only in plugins. Application code returns data. |
| What is an event handler? | A function. | Data: `{ id, payload }`. `diff` compares handlers by value. |
| State changes | Often by setters, sometimes by mutation. | The store replaces the state. You must never mutate it in place, because `diff` trusts `===`. |
| Testing application logic | Usually needs a renderer or mocks. | Call the handler and compare the effects. |
| Language of templates | Often JSX, in the same file as the code. | A separate `.pavlus` file with its own small syntax and expression language. |
| Maturity | Large ecosystems, many libraries, many developers. | A young framework with a small surface. Slots, recursive templates and typed props are not built yet. |

> [!WARNING] A different trade, not a better one in every case
> Compiled diffing is fast for what it knows, but the template language is smaller than JavaScript. Expressions are a small pure subset, so there are no arrow functions in templates. Derived values that need real code are computed in a handler and stored in the state. Pavlus also asks for discipline, because purity is a convention that nothing enforces.

## What you learned

- Application code is pure: `(message, state)` in, a list of effects out. Effects and messages are plain data.
- Plugins do every side effect, and turn the outside world into messages. The core connects them in a loop.
- A template compiles to `render` and `diff`. `diff` returns patches by comparing the state fields each node reads.
- A whole app is a template, a component class, and a `createApp` call with a store plugin and a DOM plugin.
- Pavlus trades a small template language and a purity convention for simple testing and cheap updates.
