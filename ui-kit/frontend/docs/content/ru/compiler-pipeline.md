## Идея за одну минуту

Файл `.pavlus` не интерпретируется во время выполнения. **Компилятор** читает его один раз, во время сборки, и пишет обычный JavaScript-модуль. Ваше приложение импортирует этот модуль как любой другой. Браузер никогда не видит текст шаблона и ему не нужен парсер шаблонов.

Модуль экспортирует три вещи. Вместе они называются **view**:

- `render(state)` возвращает весь шаблон для одного state в виде списка обычных объектов. Эти объекты называются **vnodes** (виртуальные узлы).
- `diff(prev, next)` возвращает наименьший список изменений DOM, который превращает страницу `prev` в страницу `next`. Эти изменения называются **patches**.
- `meta` — небольшой объект, который говорит, какие дочерние view и какой `+outlet` содержит шаблон.

## Стадии

Компилятор — это короткий конвейер. Каждая стадия — обычная функция, которая берёт результат предыдущей стадии.

| Стадия | Функция | Вход | Выход |
| --- | --- | --- | --- |
| Parse | `parse` | текст шаблона | `TemplateAst`: imports и дерево узлов |
| Analyze | `nodeDeps` | один узел | набор полей state, которые читает узел |
| Generate | `generate` | AST | исходный код JavaScript для `meta`, `render` и `diff` и список runtime-хелперов, которые он использует |
| Assemble | `compileTemplate` | текст шаблона | готовый ES-модуль в виде строки |

Анализ — это не отдельный проход по всему дереву. Генератор кода спрашивает у `nodeDeps` зависимости каждого узла в тот момент, когда пишет guard для этого узла (а результат кэшируется для каждого узла). Но это всё равно отдельная стадия, потому что её ответ определяет, как выглядит `diff`. Следующие страницы разбирают стадии по порядку: [разбор](page:compiler-parser), [анализ зависимостей](page:compiler-analysis) и сгенерированные [render](page:compiler-render) и [diff](page:compiler-diff).

В исходниках `compileTemplate(source, { filename, runtime })` делает вот что:

1. Вызывает `parse(source)` и `generate(ast)`. Если любой из них выбрасывает `TemplateError` и вы передали `filename`, перед сообщением ставится имя файла: `app.pavlus: Unclosed { (line 1, col 8)`.
2. Пишет однострочный комментарий-заголовок: `// Generated by pavlus from app.pavlus. Edit the template, not this file.`
3. Пишет одну строку `import` для runtime-хелперов, которые использует код, и по одной строке `import` на каждую строку `import` шаблона. Дочерние view импортируются настоящей модульной системой, поэтому ваш бандлер их видит.
4. Пишет сгенерированный код, затем `export { render, diff, meta };` и `export default { render, diff, meta };`.

> [!NOTE] Два способа компиляции
> `compileTemplate` возвращает модуль в виде текста. Его использует plugin для Vite, а также этот сайт документации, когда показывает вам «сгенерированный модуль». `compileToView` компилирует тот же код и сразу выполняет его через `new Function`, давая вам готовое view. Он предназначен для тестов и инструментов. Демо на этих страницах используют оба: модуль, который можно развернуть, и живое view, которое производит HTML и patches.

## Шаблон, в котором нечему меняться

Не в каждом шаблоне есть `diff`, который стоит читать. Этот ничего не читает из state.

::demo static open=module

В модуле нет строки `import`, потому что он не использует ни одного хелпера. `render` каждый раз строит одни и те же vnodes. В `diff` нет сравнений: только короткий путь `if (prev === next) return patches;` и завершающий `return patches;`. Компилятор увидел, что ни один узел не читает state, и ничего больше не написал. У vnodes тоже нет `id`: id существует только для того, чтобы patch мог назвать узел, а здесь ничего никогда не патчится.

Это первая большая идея компилятора: **он тратит код только там, где что-то может измениться**.

## От текста к AST и к коду

Теперь шаблон с одним динамическим атрибутом, одним переключателем класса и одной интерполяцией. Мы раскроем все разделы, которые может показать демо: модуль, AST и vnodes.

::demo stages open=module,ast,vnodes

Пройдите по трём разделам в том порядке, в каком работал компилятор.

**AST** состоит из двух узлов: элемента `a` (узел `#0`) и его текста (узел `#1`). Рядом с каждым узлом стоит `reads:` — набор полей state, которые нужны узлу. Элемент читает `active`, `title` и `url`, потому что их читают его атрибуты и его дочерние узлы. Текст читает только `title`. Числа `#0` и `#1` — это **id узлов** (`nid`). Парсер выдаёт их в порядке документа.

**В модуле** первым идёт `render`. Он пишет дочерние узлы раньше элемента, так что текст строится первым и добавляется в `aChildren`. Затем он строит объект атрибутов `aAttrs`, по одной строке на каждый динамический атрибут, и добавляет элемент. Потом идёт `diff`. Для элемента он пишет guard, `if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title)`. Внутри guard каждый атрибут вычисляется для `prev` и для `next`, и patch добавляется, только если два значения различаются. Для текста есть второй, поменьше guard только по `title`.

**Vnodes** — это то, что вернул `render`. И у элемента, и у текста есть `id` (`"0"` и `"1"`) — id узла в виде строки. У них есть id, потому что `diff` может на них ссылаться. Patch в шаге, `{"op":"attr","id":"0","name":"class","value":"link active"}`, использует id элемента. Патчится только `class`: `href` и текст не изменились.

## Что вы получаете, когда импортируете файл .pavlus

В проекте на Vite plugin `pavlus()` компилирует каждый файл, оканчивающийся на `.pavlus`. Plugin пропускает импорт, оканчивающийся на `?raw`, `?url` или `?inline`, потому что они просят сам файл. Для любого другого импорта вы получаете модуль, который написал компилятор.

```ts main.ts
import view from "./counter.pavlus";
import { render, diff, meta } from "./counter.pavlus";

const vnodes = render({ count: 1 });
const patches = diff({ count: 1 }, { count: 2 });
```

Экспорт по умолчанию и три именованных экспорта — это одни и те же объекты. Экспорт по умолчанию — это **view**, и именно его ожидает остальной код: plugin для DOM принимает view для монтирования, и встроенный (embed) дочерний компонент (`+Badge#status`) — это view. Обе функции **чистые**. Они читают свои аргументы и больше ничего, ничего не меняют и дают один и тот же ответ на один и тот же вход. Поэтому они могут работать на сервере, в тесте или в браузере, и поэтому демо на этом сайте могут запускать их для вас.

У view такие параметры, из сгенерированного кода:

```ts
function render(state, idSuffix = "", messagePrefix = "", env)
function diff(prev, next, idSuffix = "", messagePrefix = "", env)
```

View верхнего уровня использует значения по умолчанию. Последние три параметра нужны для **embedding**. Когда шаблон содержит `+Badge#status`, родитель вызывает `Badge.render` с более длинным `idSuffix` (`"/3"`, чтобы id узлов дочернего компонента не пересекались с id родителя), более длинным `messagePrefix` (`"status."`, чтобы message дочернего компонента назывались по его экземпляру) и `env` — объектом компонента, которому принадлежит view. Код приложения их никогда не передаёт.

## Контракт между render, diff и plugin для DOM

Plugin для DOM — это единственный код фреймворка, который трогает DOM. Он полагается на три обещания, которые выполняет сгенерированный код. Они — причина, по которой `render` и `diff` генерируются вместе, из одного AST.

1. **Первый render строит карту.** Когда plugin монтирует view, он один раз вызывает `render(state)` и строит настоящий DOM из vnodes. Для каждого vnode, у которого есть `id`, он запоминает DOM-узел под этим id.
2. **Patch называет только те id, которые произвёл render.** Patch вроде `{ op: "text", id: "1", text: "Hello, Bob" }` применяется как «найди узел, сохранённый под `1`, и задай его текст». Если бы id был неизвестен, plugin выбросил бы `unknown node id`. Компилятор гарантирует, что у каждого узла, который может патчить `diff`, есть `id` в `render`.
3. **Следующие state сравниваются через diff, а не рендерятся заново.** Когда state меняется, plugin вызывает `diff(oldState, newState)` и применяет patches по порядку. Новая часть страницы (новая ветка `if`, новый элемент списка) приходит внутри patch `insert` в виде готовых vnodes, и plugin регистрирует и их id.

Так что vnodes — это не просто картинка страницы. Это картинка плюс оглавление. Следующее демо делает это конкретным. У `button` есть событие; посмотрите, какие части vnode несут id, и на два patch шага.

::demo events open=vnodes

У `button` есть `id`, потому что у его события есть аргумент, который может измениться (`add(step)`). Patch `{"op":"handler",...}` даёт plugin новое message, так что клик отправит `{ id: "add", payload: 5 }`. Plugin никогда не удаляет и не добавляет заново слушатель: он держит один слушатель на элемент и тип события и меняет message, которое этот слушатель читает.

> [!WARNING] Компилятор доверяет идентичности
> `diff` сравнивает значения через `!==`. Новый объект с тем же содержимым считается изменением. Тот же объект с новым содержимым, изменённый на месте, считается отсутствием изменений. Всегда давайте следующему state новые объекты для изменившихся частей (spread, `map`, `filter`) и никогда не редактируйте предыдущее state.

## Зачем компилировать во время сборки

Можно было бы написать библиотеку, которая читает текст шаблона во время выполнения и обходит его. Так работают многие шаблонизаторы. Компилятор pavlus делает работу раньше, и выгоды вполне конкретные.

- **`diff` специфичен для вашего шаблона.** Сгенерированный `diff` содержит ровно те сравнения, которые нужны вашему шаблону, и никаких других. Нет общего обхода дерева и нет сравнения двух полных деревьев vnode. В демо `static` их нет совсем.
- **Нечего поставлять, кроме вашего кода.** Браузер получает обычные функции и небольшой набор хелперов. Он не получает ни парсера, ни интерпретатора выражений, ни шаблонных строк.
- **Ошибки приходят во время сборки.** Опечатка в шаблоне останавливает сборку с именем файла, строкой и колонкой. Она не ждёт, пока пользователь откроет страницу.
- **Результат читаем.** В сгенерированном коде есть комментарии с исходной строкой каждого узла (`// line 1: <a.link>`), имена, взятые из ваших тегов (`aChildren`, `liAttrs`), и один оператор на каждую идею. Вы можете прочитать его, когда что-то вас удивляет.
- **Чистые функции удобно использовать везде.** Серверный рендеринг вызывает `view.render(state)` и превращает vnodes в HTML. Юнит-тест вызывает `diff(a, b)` и проверяет patches. Браузер не нужен.

Цена в том, что шаблон может использовать в выражениях только небольшое чистое подмножество JavaScript (см. [выражения](page:syntax-expressions)). Компилятор должен понимать каждое выражение, чтобы знать, что оно читает. Это ограничение сделано намеренно.

## Runtime-хелперы

Посмотрите на первую строку модуля `stages`: `import { joinClasses, setAttr, toAttr, toText } from "@service-laboratory/pavlus/runtime";`. Сгенерированный код не содержит собственной копии этих маленьких функций. Они живут один раз, в `runtime/helpers.ts`, и компилятор импортирует ровно те, которые использует шаблон. Шаблон без динамических частей не импортирует ничего (см. `static`). Путь импорта — это значение по умолчанию опции `runtime`, и вы можете его изменить.

Каждый хелпер существует, чтобы убрать из сгенерированного кода одно решение, поэтому сгенерированный код остаётся коротким, а все шаблоны обрабатывают крайние случаи одинаково.

| Хелпер | Что делает | Для чего используется |
| --- | --- | --- |
| `toText(value)` | `null`, `undefined` и `false` становятся пустой строкой, всё остальное — `String(value)` | `{expr}` в тексте и в строках |
| `toAttr(value)` | `null`, `undefined`, `false` дают `null` (атрибута нет), `true` даёт `""`, всё остальное — свою строку | `attr=expr` |
| `joinClasses(list)` | объединяет пробелами истинные имена, даёт `null`, когда ничего не осталось | атрибут `class` |
| `setAttr(attrs, name, value)` | задаёт атрибут, если значение не `null` | все динамические атрибуты в `render` |
| `sameValues(a, b)` | равные значения или массивы с равными элементами | payload событий с несколькими аргументами |
| `diffKeyedList(...)` | вычисляет удаления, вставки и перемещения для списка с key | `for ... key` в `diff` |
| `asView(value)` | превращает компонент или view в state в его view или в `null` | embed вида `+{expr}#name` |
| `childEnv`, `resolveOutlet` | находят компонент за embed и дочерний компонент маршрута для `+outlet` | embed и outlet |

Следующее демо использует хелперы атрибутов. Обратите внимание, как ведут себя `null`, `false` и `true`.

::demo helpers open=module

`checked=done` при `done: true` становится `checked=""`, именно так HTML записывает булев атрибут. `disabled=locked` при `locked: false` не записывается вообще. `{note}` при `note: null` — это пустой текст, а не слово `null`. В шаге `done` меняется с `true` на `false`, поэтому `checked` исчезает (`rmAttr`), и класс тоже (`rmAttr`): `joinClasses` вернул `null`, потому что не осталось ни одного имени класса.

> [!TIP] Хелперы вы никогда не импортируете сами
> Комментарий в первой строке `helpers.ts` говорит об этом прямо: коду приложения они не нужны. Если захотите прочитать один из них, они короткие. Тесты в `runtime/helpers.test.ts` документируют их крайние случаи.

## Дочерние view и граф модулей

Шаблон может встроить (embed) другой шаблон. Строка `import` становится настоящим ES-импортом, а embed становится вызовом `render` и `diff` дочернего компонента.

::demo embed open=module

В модуле нужно увидеть три вещи. Строка `import Badge from "./badge.pavlus";` берётся прямо из шаблона. Значение `meta` говорит `embeds: ["status"]`: имена экземпляров дочерних компонентов. А у текстового узла дочернего компонента id `1/3`: его собственный id `1`, за которым идёт суффикс `/3`, добавленный родителем (`3` — это id узла embed у родителя). В шаге `diff` родителя вызывает `Badge.diff` со старыми и новыми props, и ответ — один patch для текста дочернего компонента. Родителю не нужно было знать, что внутри `Badge`.

## Большой шаблон от начала до конца

Наконец, небольшой список дел с заголовком, условием и циклом с key. Он использует всё, что знает конвейер: статические узлы, динамический текст, переключатель класса, событие, `if`/`else` и `for`. Сначала откройте AST и прочитайте колонку `reads:`, затем посмотрите на два шага.

::demo todo open=ast

Несколько вещей, которые в нём нужно найти.

- Ветка `else` (`p.empty`) ничего не читает, поэтому у её узлов нет id и нет кода в `diff`.
- `li` читает `item` — переменную цикла. `for` читает только `items`, потому что компилятор убирает переменные цикла из зависимостей цикла (см. [анализ зависимостей](page:compiler-analysis)).
- Шаг один отмечает элемент выполненным. Результат — единственный patch `attr` на id `6#1`: узел `6`, key элемента `1`. Заголовок, подвал и другой элемент не дают patches.
- Шаг два опустошает список. `if` меняет ветку, поэтому ответ компилятора — `clear` всего между маркерами `3s` и `3e`, затем `insert` новой ветки, плюс patch `text` для подвала.

## Что вы узнали

- Компилятор превращает шаблон в модуль с `render`, `diff` и `meta` один раз, во время сборки. Он может это делать, потому что выражения шаблона — это маленький чистый язык.
- Стадии: parse, analyze, generate и assemble. AST говорит, что читает каждый узел, а сгенерированный `diff` проверяет только то, что узел читает.
- View — это пара чистых функций. Plugin для DOM выполняет render один раз, запоминает узлы по id, а затем применяет patches, которые возвращает `diff`.
- Runtime-хелперы импортируются, а не копируются. Шаблон импортирует только те, которые использует.
