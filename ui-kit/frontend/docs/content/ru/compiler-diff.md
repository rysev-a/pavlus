## Для чего нужен diff

Шаблон pavlus компилируется в две чистые функции. `render(state)` возвращает весь шаблон для одного state в виде обычных объектов, называемых **vnodes**. `diff(prev, next)` берёт два state, старый и новый, и возвращает список **patches**: маленьких обычных объектов вроде «задать тексту узла 4 значение `Bob`». Plugin для DOM — единственный код, который их применяет.

Идея проста: когда state меняется, никто не перестраивает страницу. Компилятор уже знает, какую часть state читает каждая часть шаблона, поэтому `diff` смотрит только на те части, которые могли измениться.

Простейший случай — шаблон, который ничего не читает.

::demo static open=module

Посмотрите на сгенерированный `diff`. В нём две строки: `if (prev === next) return patches;` и `return patches;`. Компилятор увидел, что шаблон не читает state, поэтому сравнивать нечего. Какими бы ни были два state, ответ — пустой список.

## Форма каждого diff

Теперь шаблон, читающий два поля state.

::demo text open=module

Первый шаг меняет `count`, и `diff` возвращает один patch. Второй шаг меняет оба поля, и всё равно один patch: текст абзаца — это один узел, поэтому один patch заменяет его. Третий шаг ничего не меняет, и список пуст. Вот сгенерированная функция:

```ts
function diff(prev, next, idSuffix = "", messagePrefix = "", env) {
  const patches = [];
  if (prev === next) return patches;
  // line 1: <p> (reads: name, count)
  if (prev.name !== next.name || prev.count !== next.count) {
    // line 1: text
    const prevText = "Hello, " + toText(prev.name) + "! You have " + toText(prev.count) + " items.";
    const nextText = "Hello, " + toText(next.name) + "! You have " + toText(next.count) + " items.";
    if (prevText !== nextText) patches.push({ op: "text", id: "1" + idSuffix, text: nextText });
  }
  return patches;
}
```

Читайте строка за строкой, потому что у каждого diff одна и та же форма:

1. `const patches = [];` — это ответ, который будет возвращён.
2. `if (prev === next) return patches;` — самый дешёвый выход. Часто объект state вообще не изменился, и вызов заканчивается здесь.
3. Комментарий `// line 1: <p> (reads: name, count)` говорит, из какой строки шаблона пришёл блок и от каких частей state он зависит.
4. **Guard** `if (prev.name !== next.name || prev.count !== next.count)` — это проверка зависимостей. Если ни одно из полей, которые читает абзац, не изменилось, весь блок пропускается.
5. Внутри guard текст вычисляется дважды, один раз из `prev` и один раз из `next`, одним и тем же выражением. Patch существует, только если две строки различаются.

В этом коде стоит остановиться на двух вещах. Во-первых, guard сравнивает через `!==`, то есть по ссылке, и это почти ничего не стоит. Сравнение текста внутри — это сравнение строк, и оно происходит только когда guard пройден. Во-вторых, текст сравнивается после того, как построен. Если `count` меняется с `2` на `"2"`, guard пройден, но оба текста — `You have 2 items.`, поэтому patch не создаётся.

## Почему diff сравнивает состояния, а не деревья

Многие фреймворки строят новое дерево узлов при каждом обновлении, а затем сравнивают новое дерево со старым. pavlus так не делает. `diff` получает два **state** и никогда не строит дерево на пути обновления.

- Компилятор знает во время сборки, какой узел читает какое поле. Сравнение деревьев должно выяснять это заново во время выполнения, узел за узлом.
- Поле, которое не читает ни один шаблон, бесплатно. В следующем демо в state есть поле `theme`, но шаблон читает только `name`.

::demo other-field open=module

Guard — это `prev.name !== next.name`. Изменение `theme` никогда не заходит в блок, поэтому ответ — `[]`, без сравнения ни одной строки.

- `render` не вызывается при обновлении. Только когда появляется новая часть (ветка `if`, новый элемент `for`), эта часть рендерится, и только она.
- Результат — обычные данные. Вы можете вызвать `diff` в тесте, вывести patches или отправить их по сети. Браузер не нужен.

## Откуда берутся guard

Компилятор вычисляет для каждого узла набор **свободных имён**, которые тот читает: корневые поля state и переменные охватывающих циклов. Это *набор зависимостей*. Вы можете увидеть его в разделе AST каждого демо (*reads: name*) и в комментарии `(reads: ...)` сгенерированного кода.

Зависимость — это всегда **корень** выражения. `{user.name}` зависит от `user`, а не от `user.name`, а `{items[page]}` зависит от `items` и `page`.

::demo member open=module

В шаге `user` — новый объект с тем же `name`. Guard `prev.user !== next.user` пройден, текст строится заново, строки равны, и результат — `[]`. Guard дёшев и груб; сравнение строк внутри точно.

> [!WARNING] State должен быть неизменяемым
> `diff` доверяет `!==`. Если вы меняете `state.user.name` на месте, `prev.user` и `next.user` — один и тот же объект, guard не пройден, и patch не создаётся. Всегда давайте изменённому значению новую идентичность: стройте новый объект или новый массив. Plugin store делает это за вас.

## Операции patch

Patch — это объект с полем `op`. Бывает восемь видов. Первые четыре меняют один существующий узел, последние четыре меняют структуру.

| Операция | Поля | Значение |
| --- | --- | --- |
| `text` | `id`, `text` | Задать текстовое содержимое узла `id`. |
| `attr` | `id`, `name`, `value` | Задать атрибут `name` элемента `id`. |
| `rmAttr` | `id`, `name` | Удалить атрибут `name` элемента `id`. |
| `handler` | `id`, `event`, `msg` | Заменить message, которое отправляет событие `event` элемента `id`. |
| `insert` | `before`, `nodes` | Создать vnodes `nodes` и вставить их перед существующим узлом `before`. |
| `clear` | `from`, `to` | Удалить всё строго между маркерами `from` и `to`. |
| `remove` | `from`, `to` | Удалить диапазон соседних узлов от `from` до `to`, оба включены. |
| `move` | `from`, `to`, `before` | Переместить диапазон соседних узлов от `from` до `to` так, чтобы он стоял перед узлом `before`. |

Эта страница посвящена первым четырём. Остальные четыре — тема [следующей страницы](page:compiler-control-flow), потому что они относятся к `if`, `for` и embed.

Каждый `id` — это строка. Узел можно патчить, только если у него есть id, поэтому компилятор даёт id узлу **только тогда, когда patch может его адресовать**: текстовый узел, в котором есть `{выражения}`, элемент с динамическим атрибутом, переключателем класса или событием с аргументами. У статического узла id нет вообще. Plugin для DOM хранит карту из id в узел DOM, которая заполняется, пока он строит узлы, и применяет patch, ища id в ней. Если id неизвестен, он выбрасывает `pavlus/dom: unknown node id`.

Id — это номер узла в шаблоне (парсер считает узлы в порядке чтения), за которым идёт **суффикс** экземпляра. У шаблона верхнего уровня суффикс `""`, поэтому его id выглядят как `"1"`. Суффикс длиннее внутри элемента `for` или встроенного (embed) дочернего компонента, и именно так один и тот же шаблон может встречаться на странице много раз, без того чтобы два узла делили один id.

## Patch текста

Вы видели patch `text`. Когда в шаблоне несколько текстовых узлов, у каждого свой id и свой guard, так что изменение затрагивает только тот узел, который его читает.

::demo guards open=module

`div` читает `title` и `author`, поэтому его guard — объединение guard его дочерних узлов. Внутри него у `h2` и `p` по своему guard. Статическая строка `Static line` ничего не читает и вообще не имеет кода в `diff`. Четвёртый шаг передаёт `title`, который сначала является строкой `"1"`, а затем числом `1`: guard пройден, текст с обеих сторон `"1"`, и patch не выходит.

Вот часть сгенерированного кода, которая показывает вложенность:

```ts
  // line 1: <div.card> (reads: title, author)
  if (prev.title !== next.title || prev.author !== next.author) {
    // line 2: <h2> (reads: title)
    if (prev.title !== next.title) {
      // line 2: text
      const prevText = "" + toText(prev.title);
      const nextText = "" + toText(next.title);
      if (prevText !== nextText) patches.push({ op: "text", id: "2" + idSuffix, text: nextText });
    }
    // line 3: <p.muted> (reads: author)
    if (prev.author !== next.author) {
      // line 3: text
      const prevText = "by " + toText(prev.author);
      const nextText = "by " + toText(next.author);
      if (prevText !== nextText) patches.push({ op: "text", id: "4" + idSuffix, text: nextText });
    }
  }
```

Внешний guard — только короткий путь: когда ни одно поле не изменилось, одна проверка заменяет две. Дочерний узел, зависимости которого совпадают с зависимостями родителя, не получает собственного guard, потому что проверка родителя уже покрывает его. Вы можете увидеть это в следующем демо, где элемент и его текст оба читают поле `text`.

::demo redundant open=module

Атрибут `title` и текст оба находятся внутри одного guard, `if (prev.text !== next.text)`. У комментария `// line 1: text` нет собственного `if`.

## Patch атрибутов

Атрибут, значение которого — выражение или строка с `{дырками}`, может измениться. Для каждого такого атрибута компилятор пишет одни и те же четыре строки: вычислить значение с обеих сторон, сравнить и добавить `attr` или `rmAttr`.

::demo attributes open=module

Три шага меняют `url`, `name` и оба. Вот код для двух атрибутов:

```ts
    const prevHref = toAttr(prev.url);
    const nextHref = toAttr(next.url);
    if (prevHref !== nextHref) {
      patches.push(nextHref === null
        ? { op: "rmAttr", id: "0" + idSuffix, name: "href" }
        : { op: "attr", id: "0" + idSuffix, name: "href", value: nextHref });
    }
    const prevTitle = "Open " + toText(prev.name);
    const nextTitle = "Open " + toText(next.name);
    if (prevTitle !== nextTitle) {
      patches.push(nextTitle === null
        ? { op: "rmAttr", id: "0" + idSuffix, name: "title" }
        : { op: "attr", id: "0" + idSuffix, name: "title", value: nextTitle });
    }
```

Runtime-хелпер `toAttr` превращает значение state в значение атрибута. `null`, `undefined` и `false` становятся `null`, что означает «нет атрибута». `true` становится пустой строкой, так HTML записывает булев атрибут. Всё остальное становится своей строкой. Строка с дырками, например `"Open {name}"`, — всегда строка, так что для неё ветка `null` никогда не выполнится; компилятор пишет один и тот же код для каждого атрибута, потому что это упрощает генератор.

Следующее демо показывает три исхода: атрибут удалён, задан с пустым значением и задан с текстом.

::demo attribute-removed open=module

- `locked` меняется с `true` на `false`: `toAttr(false)` равно `null`, поэтому patch — `rmAttr`.
- `locked` меняется с `false` на `true`: значение — пустая строка, поэтому patch — `attr` с `value: ""`, и кнопка снова отключена.
- `hint` меняется с `null` на текст и обратно: `attr`, затем `rmAttr`.
- `hint` меняется с текста на пустую строку `""`. Это не `null`, поэтому атрибут остаётся с пустым значением. Только `null`, `undefined` и `false` удаляют атрибут.

## Patch классов

Класс — это такой же атрибут, как другие, с одним отличием: шаблон может построить его из трёх источников — статических классов (`li.item`), переключателей (`class:active=cond`) и атрибута `class`. Когда один из них динамический, компилятор объединяет все через хелпер `joinClasses` и сравнивает весь результат.

::demo classes open=module

```ts
    const prevClass = joinClasses(["item", (prev.active ? "active" : ""), (prev.done ? "done" : "")]);
    const nextClass = joinClasses(["item", (next.active ? "active" : ""), (next.done ? "done" : "")]);
    if (prevClass !== nextClass) {
      patches.push(nextClass === null
        ? { op: "rmAttr", id: "0" + idSuffix, name: "class" }
        : { op: "attr", id: "0" + idSuffix, name: "class", value: nextClass });
    }
```

Так что переключатель не добавляет и не удаляет одно имя класса. Он заменяет весь атрибут `class` новой полной строкой, `item` или `item active done`. Это просто и безопасно: DOM никогда не хранит список классов, которого не знает шаблон. Цена в том, что класс, добавленный вручную через JavaScript, будет перезаписан при следующем изменении. В pavlus атрибутом владеет шаблон.

`joinClasses` возвращает `null`, когда не осталось ни одного класса, например когда в шаблоне только переключатели и все они выключены.

::demo class-removed

Когда `on` становится `false`, список классов пуст, хелпер возвращает `null`, и patch — `rmAttr` для `class`.

## Patch handlers событий

В pavlus handler события — не функция. `@click=pick(id)` — это **данные**: message `{ id: "pick", payload: id }`. Для `diff` из этого следует: handlers можно сравнивать по значению, и handler, который не изменился, ничего не стоит.

Handler может измениться, только если у него есть аргументы. `@click=save` — одно и то же message в любом state, поэтому компилятор считает его статическим и никогда не упоминает в `diff`.

::demo static-handler

С аргументом payload — часть state, и компилятор сравнивает payload.

::demo handler open=module

```ts
    const prevClickPayload = prev.id;
    const nextClickPayload = next.id;
    if (!(prevClickPayload === nextClickPayload)) {
      patches.push({ op: "handler", id: "0" + idSuffix, event: "click", msg: { id: messagePrefix + "pick", payload: nextClickPayload } });
    }
```

Patch `handler` несёт всё новое message. Plugin для DOM не добавляет новый слушатель: у него один слушатель на элемент и событие, и этот слушатель всегда читает последнее message. Так что patch `handler` лишь заменяет значение в карте, а клик после patch отправляет новый payload.

При нескольких аргументах payload — массив, поэтому компилятор использует хелпер `sameValues`, который считает два массива с одинаковыми элементами равными. Новый массив с теми же элементами — не изменение. Модификаторы `.prevent` и `.stop` становятся `prevent: true` и `stop: true` в message.

::demo handler-many open=module

Первый шаг меняет только `kind`, а второй шаг меняет только `title`. Посмотрите, как каждое изменение соответствует ровно одному виду patch: `kind` находится в payload handler, `title` — в тексте, а `url` — в атрибуте. Третий шаг меняет `url` и `id` и создаёт два patch, один `attr` и один `handler`.

Префикс `messagePrefix` для шаблона верхнего уровня пуст. Для шаблона, встроенного (embed) как дочерний, это имя экземпляра плюс точка, и именно так message от дочернего компонента находит дорогу к нужному handler. Embed объясняются на [следующей странице](page:compiler-control-flow).

## Как plugin для DOM применяет patches

Когда state приложения меняется, plugin для DOM вызывает `view.diff(oldState, newState)` для каждого смонтированного view и применяет список по порядку. Для четырёх операций этой страницы работа — это один поиск и один вызов DOM:

- `text` задаёт `textContent` узла.
- `attr` вызывает `setAttribute`. Для `value`, `checked` и `selected` он также задаёт живое свойство, потому что у полей формы атрибут задаёт только начальное значение.
- `rmAttr` вызывает `removeAttribute`.
- `handler` заменяет message, которое отправляет слушатель элемента.

Patches применяются в том порядке, в котором их вернул `diff`. Этот порядок важен для структурных patch на следующей странице, и он стабилен: код `diff` следует порядку шаблона.

## Пример побольше

У этой карточки товара класс строится из двух переключателей, текст с несколькими полями, кнопка с динамическим атрибутом, заголовком и handler, и `if`, показывающий значок. Откройте сгенерированный модуль и найдите guard: один для карточки и по одному для каждого дочернего узла.

::demo product open=module

Прочитайте шаги один за другим и найдите guard, который пропустил каждый из них:

- `stock 3 → 2`: карточка, кнопка и `<p.stock>` читают `stock`, поэтому их guard пройдены. Класс и атрибут `disabled` вычисляются заново, но их значения равны, поэтому выходит только один patch `text`.
- `stock 1 → 0`: класс получает `out`, кнопка получает `disabled`, и текст меняется. Три patch, в порядке шаблона.
- `price 20 → 15, onSale false → true`: класс получает `sale`, текст цены меняется, а `if` вставляет значок. Patch `insert` объясняется на следующей странице.
- `another product`: имя, цена, `title` кнопки и её handler меняются разом. Id `2`, `4` и `8` — это номера узлов в порядке чтения.
- `currency only`: guard карточки пройден, guard `<p.price>` пройден, а всё остальное пропускается своим собственным guard.

Вся функция — это список независимых блоков. Стоимость вызова — это число пройденных guard, умноженное на размер того, что внутри, а не размер шаблона.

> [!TIP] Читайте сгенерированный код
> Когда ожидаемого patch нет, откройте сгенерированный модуль (свёрнутый раздел каждого демо или файл в DevTools вашего браузера) и найдите блок для этой строки шаблона. Комментарий показывает, что блок читает, а guard показывает, какие поля он сравнивает. Большинство неожиданностей — это поле, которое не входит в набор зависимостей, или значение, изменённое на месте.

## Что вы узнали

- `diff(prev, next)` сравнивает два state сгенерированными guard (`!==` по корневым полям, которые читает узел) и возвращает обычные patches; он никогда не строит и не сравнивает деревья.
- Узел может измениться, только если он читает state, поэтому статические узлы ничего не стоят и не получают id. Дочерние узлы с теми же зависимостями, что у родителя, делят guard родителя.
- `text`, `attr`, `rmAttr` и `handler` меняют один узел по id. Переключатель класса заменяет весь атрибут `class`, а `null`, `undefined` и `false` удаляют атрибут.
- Handlers — это данные, поэтому handler с аргументами сравнивается по значению, а `@click=save` без аргументов никогда не патчится.
- State должен быть неизменяемым: изменение, сохраняющее тот же объект, невидимо для guard.
