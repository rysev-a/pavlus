## Изменениям структуры нужен другой вид patch

Прошлая страница показала patches, которые меняют один существующий узел: `text`, `attr`, `rmAttr` и `handler`. Их достаточно, пока форма страницы остаётся той же. Но `if` может показать абзац или скрыть его, `for` может вырасти или уменьшиться, а встроенное дочернее view может быть заменено другим. Для таких изменений странице нужны ещё четыре операции: `insert`, `clear`, `remove` и `move`. Все они работают с **диапазонами соседних узлов**, а диапазоны отмечаются в DOM **маркерами**.

Маркер — это пустой узел-комментарий. Компилятор ставит по одному до и после каждого `if`, каждого `for` и каждого динамического embed, а также по одному до и после каждого элемента `for`. У маркеров есть id, поэтому patch может сказать «всё между маркером `0s` и маркером `0e`». У узла-комментария нет видимого вывода, и ему не нужен элемент-обёртка, поэтому HTML остаётся таким, каким вы его написали.

## if и else

Вот самый маленький `if`.

::demo if-else open=module

Первый шаг переключает `loggedIn`, и ответ — два patch: `clear` и `insert`. Второй шаг сохраняет значение, и ответ — пустой список. Patch `insert` несёт новые vnodes, которые демо показывает только числом (`1 vnodes`). Вот сгенерированный `diff`, сокращённый до важной части:

```ts
  // line 1: if (reads: loggedIn)
  if (prev.loggedIn !== next.loggedIn) {
    const prevBranch = prev.loggedIn ? 0 : 1;
    const nextBranch = next.loggedIn ? 0 : 1;
    if (prevBranch !== nextBranch) {
      // another branch: replace what is between the markers
      if (prevBranch !== -1) patches.push({ op: "clear", from: "0s" + idSuffix, to: "0e" + idSuffix });
      if (nextBranch !== -1) {
        const branchNodes = [];
        if (nextBranch === 0) {
          // line 2: <p>
          ...
        } else if (nextBranch === 1) {
          // line 4: <p>
          ...
        }
        patches.push({ op: "insert", before: "0e" + idSuffix, nodes: branchNodes });
      }
```

Ключевая идея — **индекс ветки**. Компилятор превращает цепочку `if / else if / else` в одно число: `0` для первой ветки, `1` для второй и так далее. Он вычисляет это число для `prev` и для `next` с теми же условиями с обеих сторон.

- Если два числа равны, с обеих сторон показана одна и та же ветка. Тогда компилятор делает diff **внутри** ветки, точно так же, как для любых других узлов.
- Если числа различаются, старая ветка удаляется через `clear` между двумя маркерами, а новая ветка рендерится из `next` и вставляется перед конечным маркером. Попыток превратить одну ветку в другую не делается.

Второе правило — проектное решение. Две ветки — это два разных шаблона, поэтому сравнивать их узел за узлом было бы медленнее, чем заменить, и не дало бы лучшего результата. Первое правило — то, что делает `if` дешёвым, когда он не переключается.

## if без else

Когда `else` нет, у случая «ничего не показано» есть собственное число, `-1`. Поэтому в коде две проверки: `prevBranch !== -1` для `clear` и `nextBranch !== -1` для `insert`.

::demo if-alone open=module

Прочитайте четыре шага как таблицу того, что может случиться с одним `if`:

- Скрыт — показан: один `insert` и никакого `clear`, потому что удалять нечего.
- Показан — показан, с новым значением: структура вообще не меняется. Индекс ветки с обеих сторон `0`, поэтому компилятор делает diff внутри ветки, и выходит один patch `text`.
- Показан — скрыт: один `clear` и никакого `insert`.
- Скрыт — скрыт: ничего. Guard пройден, только если изменилось `error`, а здесь оно не изменилось.

Условие не сравнивается как значение. `error`, меняющееся с `"Oops"` на `"Again"`, меняет поле, но индекс ветки остаётся `0`, и именно он решает.

## Цепочки и что происходит внутри ветки

У большинства настоящих шаблонов есть цепочка. Эта — классический экран загрузки, ошибки и готового результата.

::demo if-chain

Для трёх веток индекс вычисляется цепочкой условий, записанной как вложенные условные выражения:

```ts
      const prevBranch = (prev.status === "loading") ? 0 : (prev.status === "failed") ? 1 : 2;
      const nextBranch = (next.status === "loading") ? 0 : (next.status === "failed") ? 1 : 2;
```

Последнее число — ветка `else`. Без `else` было бы `-1`. Теперь посмотрите на пять шагов:

- `ok → loading` и `loading → failed`: ветка меняется, поэтому вы получаете `clear` и `insert`. `insert` второго шага несёт два vnode, абзац и кнопку.
- `failed, error changes`: ветка та же, и патчится только текст, читающий `error`.
- `loading, error changes`: guard у `if` пройден, потому что он читает `error` (его использует вторая ветка), но ветка по-прежнему `0`, а ветка `0` статична. Ответ — `[]`.
- `ok, items change`: внутренний `for` добавляет элемент; как именно, вы увидите чуть позже.

В коде для случая «внутри» по одному блоку на каждую ветку, и каждый блок выполняется, только когда его ветка показана:

```ts
      } else {
        // the same branch: diff inside it
        if (nextBranch === 1) {
          // line 6: <p.status.status--error> (reads: error)
          if (prev.error !== next.error) {
            // line 6: text
            const prevText = "" + toText(prev.error);
            const nextText = "" + toText(next.error);
            if (prevText !== nextText) patches.push({ op: "text", id: "5" + idSuffix, text: nextText });
          }
        }
```

Ветка, в которой нет ничего динамического, блока не получает. Поэтому у `if` со статическими ветками, как в первом демо этой страницы, в его `diff` нет части `else`.

## Маркеры в render

Маркеры производит `render`, чтобы plugin для DOM мог находить диапазоны. Два `if` подряд показывают, как они нумеруются.

::demo if-markers open=vnodes

Откройте vnodes. Каждый `if` окружён двумя vnode-маркерами, `{ "t": "marker", "id": "1s" }` и `{ "t": "marker", "id": "1e" }`. Число — это номер узла `if` в шаблоне, а `s` и `e` означают начало и конец. Первый шаг вставляет перед `4e`, конечным маркером второго `if`. Второй шаг делает clear от `1s` до `1e`, и затрагивается только первый `if`.

> [!NOTE] Маркеры невидимы
> В HTML, который вы видите в демо, маркеров нет, потому что `toHtml` отбрасывает их, если не попросить иначе. В браузере это пустые узлы-комментарии, `<!---->`. Если вы изучите страницу, то увидите их между своими элементами.

## Циклы: один диапазон на элемент

`for` — это список диапазонов. У каждого элемента свои начальный и конечный маркеры, и у всего цикла тоже есть начальный и конечный маркеры. Id маркеров содержат **key** элемента, поэтому patch может назвать ровно один элемент.

```pavlus
ul.todos
  for todo in todos key todo.id
    li(class:done=todo.done) {todo.title}
```

Часть `render`, которая это делает, коротка:

```ts
  const todoList = (state.todos) || [];
  for (let todoIndex = 0; todoIndex < todoList.length; todoIndex++) {
    const todo = todoList[todoIndex];
    const todoKey = String((todo)?.id);
    const todoSuffix = idSuffix + "#" + todoKey;
    ulChildren.push({ t: "marker", id: "1[" + todoSuffix });
    ...
    ulChildren.push({ t: "marker", id: "1]" + todoSuffix });
  }
```

Key преобразуется в строку. **Суффикс** элемента — это суффикс внешнего шаблона плюс `#` и key. Каждый узел внутри элемента получает свой id из этого суффикса, поэтому у второго `li` списка id `2#2` (узел 2, key 2), а не id первого. Так же цикл внутри цикла остаётся однозначным: внутренний суффикс продолжает внешний.

У конечного маркера элемента id вида `1]#2`. `[` и `]` в id нужны только для того, чтобы отличать маркеры элемента от `s` и `e`, маркеров всего списка.

## Списки без key

Если вы не пишете `key`, key элемента — его индекс. Это простейшая форма, и она хороша, когда список только растёт и сокращается с конца.

::demo for-unkeyed

- Добавление элемента вставляет один диапазон перед конечным маркером списка.
- Удаление последнего элемента удаляет его диапазон.
- Удаление **первого** элемента не удаляет первый диапазон. Keys были `0, 1, 2`, а стали `0, 1`, поэтому диапазон с key `2` уходит, а тексты с key `0` и `1` патчатся новыми значениями. Результат выглядит так же, но работа другая: два patch `text` и `remove`.
- Разворот трёх элементов патчит два текста. Тот, что посередине, остался прежним, поэтому он ничего не стоит.

> [!WARNING] Без key DOM следует за позицией
> Когда key — индекс, узлы DOM остаются на своей позиции и получают новое содержимое. Для текста это нормально. Но если у элемента есть что-то, что знает только DOM (фокус, каретка, текст, введённый в input, который state не хранит), это остаётся на позиции, а не вместе с элементом. Давайте циклу key всегда, когда элементы могут удаляться из середины или переупорядочиваться.

## Списки с key

С `key todo.id` элемент остаётся тем же элементом, пока его key тот же, где бы он ни стоял в списке. Теперь компилятор может сказать, что произошло: элемент добавлен, удалён, перемещён или изменён.

::demo for-keyed

Каждый вид изменения даёт свой вид patch:

- `append D`, `insert D in the middle`: `insert`, где `before` задан начальным маркером элемента, который должен следовать за новым (или конечным маркером списка).
- `remove A`, `remove B`: `remove`, от начального маркера до конечного маркера элемента, оба включены. Patch `remove` удаляет и маркеры тоже. Это отличается от `clear`, который сохраняет маркеры.
- `swap A and B`: один `move`.
- `B done`: структура не меняется. Патчится только атрибут изменившегося элемента, с id этого элемента.
- `all replaced`: два `remove` и два `insert`. Обратите внимание на порядок. Вставки делаются от конца списка к его началу.
- `nothing changed`: демо передаёт новый массив с теми же тремя объектами. Guard цикла пройден, потому что массивы — это два объекта, но каждый элемент с обеих сторон — один и тот же объект, поэтому `common` не находит, что патчить.

## Как согласуются списки

Сгенерированный код сам не решает, что вставить, переместить или удалить. Он вызывает хелпер из runtime, `diffKeyedList`, и передаёт ему четыре маленькие функции, по одной на каждый случай. Вот этот вызов из сгенерированного модуля:

```ts
    diffKeyedList(prevTodoKeys, nextTodoKeys, todoStartId, "1e" + idSuffix, {
      remove(key) { patches.push({ op: "remove", from: todoStartId(key), to: todoEndId(key) }); },
      insert(index, beforeId) {
        ...
        patches.push({ op: "insert", before: beforeId, nodes: todoNodes });
      },
      move(key, beforeId) { patches.push({ op: "move", from: todoStartId(key), to: todoEndId(key), before: beforeId }); },
      common(prevIndex, nextIndex) {
        ...
      },
    });
```

Хелпер работает в три прохода:

1. **Remove.** Каждый key из `prev`, которого нет в `next`, удаляется. Keys, которые остаются, записываются в том порядке, в каком они стоят в DOM.
2. **Insert и move, с конца.** Хелпер идёт по `next` от последнего элемента к первому. Для каждого элемента он знает, какой элемент должен за ним следовать, поэтому знает маркер, перед которым нужно вставить или переместить. Новый key даёт `insert`. Старый key, который ещё не стоит перед своим последователем, даёт `move`. Движение с конца гарантирует, что маркер, на который ссылается patch, существует к моменту применения patch.
3. **Common.** Для каждого key, присутствующего с обеих сторон, `common(prevIndex, nextIndex)` делает diff содержимого элемента. Код внутри `common` — обычный diff тела цикла, где `prevTodo` и `nextTodo` — элемент с двух сторон.

Функция `insert` рендерит новый элемент только со стороны `next`. Функция `common` — то место, где снова используются guard с прошлой страницы, а корнем зависимости служит элемент.

Метод прост, и он не минимален. Перемещение одного элемента далеко может стоить нескольких перемещений, потому что каждый элемент, мимо которого он проходит, проверяется на своего последователя.

::demo for-moves

- Перемещение первого элемента в конец стоит одного `move`.
- Перемещение последнего элемента в начало стоит трёх: хелпер перемещает `c`, затем `b`, затем `a`, вместо того чтобы переместить только `d`.
- Разворот четырёх элементов стоит трёх перемещений.

Это осознанный компромисс. Алгоритм мал и предсказуем, а на практике большинство изменений списка — это добавления, удаления и редкие обмены. Кратчайший скрипт правок потребовал бы наибольшей возрастающей подпоследовательности, а это больше кода ради редкого случая. Если вы часто переупорядочиваете очень длинные списки, смотреть нужно именно сюда, в сгенерированном коде.

## Переменная индекса

Цикл может назвать индекс: `for item, i in items`. Индекс входит в набор зависимостей тела цикла, потому что он может измениться, когда элемент перемещается.

::demo for-index open=module

Удаление первого элемента удаляет его диапазон, а затем патчатся два оставшихся элемента: их номера изменились с `2.` и `3.` на `1.` и `2.`. Сам элемент не изменился, но `common` вызывается для него с новым индексом, и guard `prevIndex !== nextIndex || prevItem !== nextItem` пропускает его.

## Пустые и отсутствующие списки

Выражение списка вычисляется как `(items) || []`. State, в котором `items` отсутствует, равен `null` или `undefined`, — то же самое, что пустой список. Это возможность, но обратите внимание, что она значит для других условий.

::demo for-empty

- `[] → [x, y]`: два patch `insert`, сначала для `y`, потому что хелпер идёт с конца, и `clear` для абзаца «Nothing here».
- `[x, y] → []`: два `remove` и один `insert` абзаца.
- `[] → undefined`: цикл видит пустой список с обеих сторон. Условие `items.length === 0` — это `(items)?.length === 0`, то есть `undefined === 0`, то есть ложь, поэтому абзац очищается. Если вы хотите, чтобы абзац показывался и для отсутствующего списка, запишите условие как `!items || items.length === 0`.

> [!DANGER] Keys должны быть уникальными
> Два элемента с одинаковым key заставляют `diffKeyedList` выбросить исключение, и сообщение называет key: `pavlus: duplicate key 1`. Отсутствующий key даёт key `undefined` для всех элементов, и ошибка — `pavlus: duplicate key undefined`. Ошибка приходит из `diff`. `render` keys не проверяет, поэтому страница может отрендериться один раз и упасть при первом обновлении. Используйте значение, уникальное в списке и не меняющееся для одного и того же элемента, например id с сервера.

## Циклы в циклах

Циклы вкладываются, и каждый уровень продолжает суффикс. Внутренний список группы живёт между маркерами с key группы в их id.

::demo for-nested

Вставка адресована `6e#g2`, конечному маркеру списка участников группы с key `g2`. Первая группа не затрагивается: она один и тот же объект в `prev` и `next`, поэтому её guard сразу не пройден. Вторая группа — новый объект, разделяющий остальные поля, и именно так обновляется неизменяемый state.

## Embed: дочернее view в вашем шаблоне

**Embed** помещает в этот шаблон другой скомпилированный шаблон. Статический embed называет импортированный шаблон, имя экземпляра после `#` и props в круглых скобках.

```pavlus
import Badge from "./badge.pavlus"

li.user
  span.name {name}
  +Badge#badge(label=role hot=admin)
```

Импортированный шаблон — обычный шаблон. Для этой страницы это:

```pavlus
span.badge(class:hot=hot) {label}
```

Дочерний компонент не читает state своего родителя. Он получает объект, и `label=role` означает, что у объекта есть поле `label`, значение которого — `role` родителя.

::demo embed-static open=module

Embed — это не особый patch. Компилятор пишет вызов собственного `diff` дочернего компонента с props из `prev` и props из `next` и кладёт patches в тот же список:

```ts
    // line 5: +Badge#badge (reads: role, admin)
    if (prev.role !== next.role || prev.admin !== next.admin) {
      patches.push(...Badge.diff(
        { "label": prev.role, "hot": prev.admin },
        { "label": next.role, "hot": next.admin },
        idSuffix + "/3",
        messagePrefix + "badge.",
        childEnv(env, "badge", next),
      ));
    }
```

Три аргумента после состояний говорят, кто такой дочерний компонент:

- **Суффикс** `idSuffix + "/3"` делает id дочернего компонента уникальными. `3` — номер узла embed в родителе. В демо у текста дочернего компонента id `1/3`: узел 1 дочернего компонента внутри embed 3 родителя.
- **Префикс** `messagePrefix + "badge."` ставится перед каждым id message, которое отправляет дочерний компонент. Клик в дочернем компоненте отправляет `badge.something`, так что компонент-родитель может направить message нужному дочернему.
- **Окружение** `childEnv(env, "badge", next)` находит компонент за экземпляром, если он есть. Оно нужно дочернему компоненту, у которого есть собственный `+outlet`.

Guard перечисляет props, которые читаются, и только их. Если у родителя меняется `name`, badge даже не вызывается. Если prop записан без state, как `label="Fixed"`, он статичен. Embed, который ничего не читает, пропускается целиком.

Embed часто используются внутри цикла. Вот один внутри цикла с key:

::demo embed-in-loop open=module

Id в patches — `0#2/4` и `1#2/4`. Каждый — это номер узла дочернего компонента (`0` или `1`), за которым идёт его суффикс `#2/4`: элемент с key `2`, затем embed, то есть узел `4` родителя. Для этого и нужен суффикс. Два badge могут иметь один шаблон и никогда не делить id.

Prop со spread, `+Row#row(...item selected=flag)`, копирует все поля `item` в props и затем добавляет `selected`. Props записываются по порядку, поэтому более поздний побеждает.

## Динамические embed

Иногда дочерний компонент неизвестен, когда пишется шаблон. **Динамический embed**, `+{expr}#name(props)`, берёт view из state: значение выражения — скомпилированный шаблон или объект компонента, у которого есть `view`. Имя экземпляра обязательно, потому что компилятор не может его угадать.

```pavlus
section.panel
  h2 {title}
  +{panel}#panel(items=items)
```

Поскольку дочерний компонент с каждой стороны может быть другим шаблоном, компилятору приходится обрабатывать три случая. Хелпер `asView` возвращает view за значением или `null` для `null` и `undefined`.

::demo embed-dynamic open=module

В демо state хранит настоящие скомпилированные view (выводятся как `<view list.pavlus>`). В коде три пути:

```ts
      const prevPanelView = asView(prev.panel);
      const nextPanelView = asView(next.panel);
      if (prevPanelView !== nextPanelView) {
        // another view means another template: replace, never diff across
        if (prevPanelView) patches.push({ op: "clear", from: "3s" + idSuffix, to: "3e" + idSuffix });
        if (nextPanelView) {
          patches.push({ op: "insert", before: "3e" + idSuffix, nodes: nextPanelView.render(
            ...
          ) });
        }
      } else if (nextPanelView) {
        patches.push(...nextPanelView.diff(
          ...
        ));
      }
```

- Одно и то же view с обеих сторон: вызывается собственный `diff` view. На первом шаге view списка добавляет один элемент и возвращает `insert`.
- Другое view: старое содержимое очищается между маркерами, а новое view рендерится из props `next` и вставляется. Diff между списком и таблицей не имел бы смысла.
- View, которое появляется или исчезает (`null`): только `insert` или только `clear`.

Если значение не view и не компонент с view, `asView` выбрасывает `pavlus: +{...} needs a view or a component with a view`. В отличие от статического embed, у динамического есть маркеры, потому что его содержимое может появляться и исчезать.

## Страница маршрута: +outlet

`+outlet` — это динамический embed, view которого приходит от роутера. Компонент объявляет таблицу `routing`, и outlet показывает дочерний компонент, соответствующий `state.route`. О самой таблице см. [маршрутизация](page:concepts-routing). Шаблон — одна строка:

```pavlus
main
  +outlet
```

Его `diff` имеет те же три пути, что и динамический embed, с двумя отличиями:

```ts
  // line 4: <main> (reads: the route and the routed child)
  if (true) {
    // line 5: +outlet
    const prevOutlet = resolveOutlet(env, prev);
    const nextOutlet = resolveOutlet(env, next);
    if (prevOutlet?.view !== nextOutlet?.view || prevOutlet?.name !== nextOutlet?.name) {
      // another page: replace what is between the markers
      if (prevOutlet) patches.push({ op: "clear", from: "4s" + idSuffix, to: "4e" + idSuffix });
      if (nextOutlet) {
        patches.push({ op: "insert", before: "4e" + idSuffix, nodes: nextOutlet.view.render(
          ...
        ) });
      }
    } else if (nextOutlet) {
      ...
    }
  }
```

Во-первых, guard — `if (true)`. То, что показывает outlet, зависит от маршрута и от state дочернего компонента маршрута, и шаблон не может назвать эти поля. Поэтому компилятор отмечает узел как «может измениться, когда что-либо меняется», и каждый родитель outlet проверяется при каждом обновлении. Во-вторых, страница заменяется, когда меняется view **или имя экземпляра**: два маршрута могут использовать один шаблон и всё же быть двумя разными страницами.

Запустить outlet в демо на этой странице нельзя, потому что ему нужен компонент, владеющий таблицей routing. Шаблон с `+outlet`, запущенный без него, останавливается с такой ошибкой:

```text
pavlus: +outlet needs a component with a `routing` table; mount the component, not only its view
```

## Собираем всё вместе

У этой доски есть заголовок, цепочка `if / else if / else`, цикл с key и индексом, переключатель класса, событие с аргументом, статический embed внутри цикла и динамический embed после него. `footer` — это view, хранящееся в state.

::demo everything

Пройдите по шагам и назовите код, который произвёл каждый patch:

- `loading true → false`: ветка меняется с `0` на `2`. Один `clear` и один `insert` строят список со всеми его элементами одним patch.
- `card 1 done, card 2 moves up`: `move`, потому что порядок списка изменился, а затем изменения в элементах: числа (индекс изменился), `class` карточки, которая теперь выполнена, и badge — дочернее view, получающее новый prop `hot`. Заголовок карточки не изменился, поэтому он не патчится.
- `last card removed`: `remove` и текст подвала, `1 cards`. Подвал — динамический embed с тем же view с обеих сторон, поэтому вызывается его собственный `diff` с новым числом.
- `all cards removed`: ветка меняется с `2` на `1`, поэтому весь список очищается и вставляется абзац «No cards». `remove` для элементов не нужен: `clear` удаляет всё между маркерами. Текст подвала меняется на `0 cards`.

## Что вы узнали

- Цепочки `if` компилируются в индекс ветки (`-1`, когда ничего не показано). Тот же индекс означает diff внутри ветки; другой индекс означает `clear` между маркерами и `insert` новой ветки.
- Маркеры — пустые узлы-комментарии вокруг каждого `if`, элемента `for`, цикла и динамического embed. Структурные patches (`insert`, `clear`, `remove`, `move`) работают с диапазонами между ними.
- `for` становится `diffKeyedList` с четырьмя колбэками. Keys должны быть уникальными и стабильными; без key ключом служит индекс, и DOM следует за позицией.
- Статический embed — это вызов `diff` дочернего компонента с props обеих сторон, более длинным суффиксом id и префиксом message. Динамический embed или outlet заменяет содержимое, когда меняется view.
