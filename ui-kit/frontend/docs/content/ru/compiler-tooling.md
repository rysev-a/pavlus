## Компилятор — это функция из текста в текст

Вы видели, что генерирует компилятор. Эта страница о том, как его запускать. В основе компилятор — одна функция: она берёт текст шаблона и возвращает текст JavaScript-модуля. Она не читает файлы, не трогает DOM и не нуждается в браузере. Один и тот же вход всегда даёт один и тот же выход.

Вот самый маленький пример. Откройте сгенерированный модуль и прочитайте его сверху.

::demo smallest open=module

У скомпилированного модуля всегда одни и те же части в одном и том же порядке:

1. Комментарий-заголовок: `// Generated by pavlus from smallest.pavlus. Edit the template, not this file.`
2. Один `import` runtime-хелперов, которые использует модуль (здесь только `toText`). У шаблона, не использующего хелперов, нет import вообще.
3. Один `import` для каждого шаблона, который ваш шаблон импортирует собственной строкой `import`.
4. `const meta`, в котором перечислены имена экземпляров встроенных (embed) дочерних компонентов и сказано, есть ли в шаблоне `+outlet`.
5. Две функции, `render` и `diff`, каждая с комментарием, что она чистая.
6. Два экспорта: имена `render`, `diff` и `meta` и экспорт по умолчанию — объект `{ render, diff, meta }`. Этот объект — **view**, то, что монтирует plugin для DOM.

## compileTemplate

Функция экспортируется из `@service-laboratory/pavlus/compiler`. Она принимает исходник и объект опций и возвращает текст модуля.

```ts
import {
  compileTemplate,
  DEFAULT_RUNTIME,
} from "@service-laboratory/pavlus/compiler";

const source = "p Hello, {name}";
const code = compileTemplate(source, { filename: "src/hello.pavlus" });

console.log(DEFAULT_RUNTIME); // "@service-laboratory/pavlus/runtime"
```

Опций две, и обе необязательны.

| Опция | По умолчанию | Что делает |
| --- | --- | --- |
| `filename` | нет | Ставится перед каждым сообщением об ошибке и используется для комментария-заголовка. В заголовок пишется только последняя часть пути, поэтому результат не зависит от того, где находится ваш проект. |
| `runtime` | `DEFAULT_RUNTIME` | Модуль, из которого импортируются хелперы. |

Опция `runtime` меняет одну строку. С `{ runtime: "/src/runtime/helpers.ts" }` модуль начинается так:

```ts
// Generated by pavlus from a template. Edit the template, not this file.
import { toText } from "/src/runtime/helpers.ts";
```

Хелперы (`toText`, `toAttr`, `joinClasses`, `setAttr`, `sameValues`, `asView`, `diffKeyedList`, `resolveOutlet`, `childEnv`) живут в runtime один раз и не вставляются в каждый шаблон. Компилятор импортирует **только хелперы, которые использует шаблон**, отсортированные по имени. Когда строка получилась бы длиннее 100 символов, она записывается с одним именем на строку.

::demo many-helpers open=module

Посмотрите на первые строки модуля. Используются пять хелперов, поэтому import — это блок. Циклу с key нужен `diffKeyedList`, переключателю класса нужны `joinClasses` и `setAttr`, динамическому атрибуту нужен `toAttr`, а тексту нужен `toText`.

Когда шаблон импортирует другой шаблон, компилятор копирует путь в `import` так, как вы его написали, а бандлер его разрешает.

::demo with-child open=module

Первые две строки после заголовка — `import { childEnv, toText } from ...` и `import Badge from "./badge.pavlus";`. Вторая — из вашего шаблона, первая — от компилятора. Строка `meta` говорит `embeds: ["badge"]`: имена экземпляров дочерних компонентов. Поскольку `./badge.pavlus` — это тоже файл `.pavlus`, он компилируется тем же plugin, когда бандлер до него доходит.

## compileToView

Иногда вам нужно работающее view, а не текст: в тесте, в скрипте или на странице документации вроде этой. `compileToView` компилирует исходник, а затем выполняет код, передавая runtime-хелперы как аргументы, и возвращает view.

```ts
import { compileToView } from "@service-laboratory/pavlus/compiler";

const view = compileToView("p Hello, {name}");
view.render({ name: "Ann" });
view.diff({ name: "Ann" }, { name: "Bob" });
```

Если в шаблоне есть строки `import`, view нужно передавать по их локальному имени:

```ts
const badge = compileToView("span.badge {label}");
const row = compileToView(
  `import Badge from "./badge.pavlus"
li +Badge#badge(label=role)`,
  { components: { Badge: badge } },
);
```

Значение в `components` — это view или объект, у которого есть `view`. Если имени не хватает, вызов останавливается с таким сообщением:

```text
pavlus: template imports "Badge" but no view was given in { components }
```

`compileToView` строит функцию через `new Function`, поэтому ему нужна страница, которая это разрешает. Используйте `compileTemplate` и бандлер для приложения, а `compileToView` — для тестов и инструментов.

## Plugin для Vite

В приложении вы сами не вызываете компилятор. Plugin для Vite вызывает его за вас для каждого шаблона, который импортирует ваш код. Он экспортируется из `@service-laboratory/pavlus/vite` как `pavlus()`.

```ts vite.config.ts
import { defineConfig } from "vite";
import { pavlus } from "@service-laboratory/pavlus/vite";

export default defineConfig({
  plugins: [pavlus()],
});
```

Plugin небольшой, и всё, что он делает, можно сказать в нескольких строках:

- Он запускает `transform` с `enforce: "pre"`, до других plugins.
- Он обрабатывает модуль, когда путь без строки запроса оканчивается на `.pavlus`. Все остальные модули возвращают `null` и остаются нетронутыми. Опция `extension` меняет суффикс (`pavlus({ extension: ".pv" })`).
- Он пропускает запросы `?raw`, `?url` и `?inline`, поэтому `import source from "./card.pavlus?raw"` даёт вам текст шаблона, а не скомпилированный модуль. Так golden-тесты ниже читают свой вход.
- Он вызывает `compileTemplate(code, { filename, runtime })`. `filename` — полный путь файла, а `runtime` — опция, которую вы ему задали.
- Он возвращает модуль с `map: { mappings: "" }`, что означает «нет source map». Это решение, а не пробел: Vite придумал бы карту, которая указывает сгенерированный код на самого себя, она велика и ничего не говорит. Без карты DevTools браузера показывает сгенерированные `render` и `diff`, а это то, что нужно для отладки.
- Когда компилятор выбрасывает исключение, он вызывает `this.error` Vite с сообщением, поэтому сборка останавливается и показывает ошибку с именем файла.

В plugin нет кода для горячих обновлений, а в сгенерированном модуле нет `import.meta.hot`. Сохранённый шаблон преобразуется заново, как любой другой модуль, и Vite применяет своё обычное правило для модулей, которые не принимают обновления.

### Откуда берётся runtime

Скомпилированный модуль импортирует `@service-laboratory/pavlus/runtime`, поэтому пакет должен быть установлен, как для любого другого импорта. Если хелперы находятся в другом месте, например в monorepo, где пакет — это исходники, есть два способа. Используйте опцию `runtime` или алиас Vite. Собственные тесты фреймворка используют алиас:

```ts
export default defineConfig({
  plugins: [pavlus()],
  resolve: {
    alias: {
      "@service-laboratory/pavlus/runtime": "/path/to/src/runtime/helpers.ts",
    },
  },
});
```

### Использование шаблона

Шаблон — это модуль, как любой другой. Импортируйте экспорт по умолчанию, то есть view, и передайте его компоненту.

```pavlus counter.pavlus
section.counter
  h1 {count}
  button(@click=inc) Add one
```

```ts main.ts
import {
  Component,
  createApp,
  type Effect,
  type Message,
} from "@service-laboratory/pavlus";
import { createDomPlugin } from "@service-laboratory/pavlus/plugins/dom";
import {
  createStorePlugin,
  storeEffector as store,
} from "@service-laboratory/pavlus/plugins/store";
import view from "./counter.pavlus";

interface State {
  count: number;
}

class Counter extends Component<State> {
  view = view;
  inc(_msg: Message, state: State): Effect[] {
    return [store.set("count", state.count + 1)];
  }
}

createApp<State>({
  app: new Counter(),
  plugins: [createStorePlugin<State>({ count: 0 }), createDomPlugin()],
  mount: "#app",
});
```

`@click=inc` в шаблоне — это message `inc`. Метод `inc` компонента обрабатывает его и возвращает effect в виде данных. Plugin store меняет state, plugin для DOM вызывает `view.diff` и применяет patches.

### Типы для импортов шаблонов

TypeScript не знает, что такое файл `.pavlus`. Для этого пакет поставляет файл деклараций, `@service-laboratory/pavlus/env`. Подключите его один раз, в файле `.d.ts`, который входит в ваш `tsconfig.json`:

```ts env.d.ts
/// <reference types="vite/client" />
/// <reference types="@service-laboratory/pavlus/env" />
```

После этого у `import view from "./counter.pavlus"` тип `View`, и у именованных экспортов `render`, `diff` и `meta` тоже есть типы. Декларация говорит, что `render(state: any, ...)` и `diff(prev: any, next: any, ...)` принимают любой state, поэтому TypeScript не проверяет state по шаблону. Типы для импортов `?raw` приходят из `vite/client`.

## Ошибки

Шаблон, который нельзя скомпилировать, выбрасывает `TemplateError`. Его сообщение заканчивается позицией, `(line 3, col 5)`, с числами, отсчитываемыми с 1, и у объекта ошибки также есть поля `line` и `col`. Когда вы передаёте `filename` (plugin для Vite делает это всегда), сообщение начинается с имени файла.

Вот ошибки, которые вы будете встречать чаще всего. В каждом блоке показан шаблон и точное сообщение, которое компилятор возвращает для него с именем файла `card.pavlus`.

Табуляция в отступе:

```pavlus-invalid
ul
	li Item
```

```text
card.pavlus: Tabs are not allowed, use spaces (line 2, col 1)
```

Незакрытая фигурная скобка:

```pavlus-invalid
p Hello, {name
```

```text
card.pavlus: Unclosed { (line 1, col 8)
```

Выражение, которое не закончено или содержит символ, не входящий в язык выражений:

```pavlus-invalid
div
  p {total +}
```

```text
card.pavlus: Unexpected end of expression (line 2, col 13)
```

```pavlus-invalid
p {price # 2}
```

```text
card.pavlus: Unexpected character "#" (line 1, col 10)
```

`else`, перед которым нет `if`. Обратите внимание, что `else` также не может идти за `for`:

```pavlus-invalid
div
  p one
else
  p two
```

```text
card.pavlus: `else` without matching `if` (line 3, col 1)
```

Дочерний компонент, который не импортирован. Сообщение подсказывает оба способа исправления:

```pavlus-invalid
div
  +Card#card(title=title)
```

```text
card.pavlus: "Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

Handler, который не является именем message:

```pavlus-invalid
button(@click=1+2) Go
```

```text
card.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

Строка под элементом, у которого не может быть дочерних узлов:

```pavlus-invalid
input(value=x)
  p inside
```

```text
card.pavlus: This line cannot have children (line 2, col 1)
```

Динамический embed без имени экземпляра, поздний `import`, переключатель класса со строкой и `+outlet` с аргументами:

```text
card.pavlus: A dynamic component needs an instance name: +{expr}#name(...) (line 1, col 9)
card.pavlus: `import` lines must be at the top of the file (line 2, col 1)
card.pavlus: "class:on" needs an expression value (line 1, col 4)
card.pavlus: `+outlet` takes nothing after it (line 2, col 10)
```

В сборке Vite сообщение приходит внутри ошибки сборки. Вот что печатает сборка Vite 8, в сокращении, для шаблона со строкой `  li {name`:

```text
Build failed with 1 error:

[plugin pavlus] /project/src/bad.pavlus
RolldownError: /project/src/bad.pavlus: Unclosed { (line 2, col 3)
```

> [!WARNING] Некоторые опечатки — не ошибки
> Компилятор распознаёт `if`, `else`, `for` и `+` по форме всей строки. Строка, которая почти подходит, — обычный элемент. Один `if` без условия — это элемент `<if>`. `for item of items` (с `of` вместо `in`) — это элемент `<for>` с текстом `item of items`. Ни то ни другое не является ошибкой, и страница отрисовывается без блока, который вы хотели. Когда то, что должно быть блоком, появляется как тег, сверьте строку с синтаксисом.

## Golden-файлы

Как авторы компилятора могут менять его уверенно? У набора тестов два слоя.

Первый слой, `output.test.ts`, проверяет **свойства** результата: хелперы импортируются, а не вставляются, импортируются только использованные хелперы, у переменных имена, происходящие из шаблона (`userList`, `prevUserKeys`, `liChildren`), комментарии говорят, какая строка и какие зависимости у блока, а в коде нет очень длинных строк.

Второй слой фиксирует **каждый байт**. В папке `framework/src/compiler/__fixtures__` лежат одиннадцать небольших шаблонов, а в `__goldens__` — точный JavaScript, который компилятор должен произвести для каждого:

| Фикстура | Что проверяет |
| --- | --- |
| `static` | Ничто не зависит от state, поэтому `diff` пуст. |
| `text` | Текстовые строки, интерполяция, экранированные скобки. |
| `element` | Динамические атрибуты, переключатели классов, события с аргументами и модификаторами. |
| `names` | Переменные цикла, названные как ключевые слова JavaScript или сгенерированные имена. |
| `if` | `if`, `else if`, `else`, цикл без key, второй `if`. |
| `for` | Циклы с key и индексом, вложенные циклы, `if` внутри цикла. |
| `embed-static` | Импортированные дочерние компоненты, props, spread, embed внутри цикла. |
| `embed-dynamic` | `+{expr}` под `if`, со spread-props. |
| `outlet` | Узел `+outlet`. |
| `shell`, `dashboard` | Две настоящие страницы: меню с длинным выражением для класса и дашборд. |

Golden-тест читает каждую фикстуру с `?raw` (это работает, потому что plugin пропускает этот запрос), компилирует её через `compileTemplate(source, { filename: "<name>.pavlus" })` и сравнивает результат с файлом через `toMatchFileSnapshot`. Последний тест проверяет, что фикстуры вместе используют каждый вид узла: элементы, текст, `if` с `else if` и `else`, `for` с key и без, статические и динамические embed, `+outlet`, переключатели классов и формы событий `prevent`, `stop` и с несколькими аргументами. Если вы добавите в синтаксис новую возможность, этот тест будет падать, пока её не использует какая-нибудь фикстура.

Если изменение компилятора намеренно меняет результат, вы запускаете тесты с `-u` и читаете diff `__goldens__/` на ревью. Если это был рефакторинг, diff должен быть пустым. В этом смысл фиксации байтов: изменение результата не может пройти незамеченным.

### Как читать golden

Golden-файлы — лучшая документация результата, потому что они всегда верны. Чтобы прочитать один из них, начните с шаблона и найдите эти ориентиры:

- Комментарии `// line N: <tag>` сопоставляют блок со строкой шаблона. Одна и та же строка появляется в `render` и в `diff`.
- В `render` найдите переменные `xChildren` и `xAttrs`. Они строятся первыми, снизу вверх, а элемент добавляется последним.
- В `diff` найдите комментарий с `(reads: ...)`. Следующая строка — его guard.
- Найдите `idSuffix`. Каждый id — это номер узла плюс суффикс, так что вы можете проследить один узел через `render` и `diff`.
- Для цикла найдите `diffKeyedList` и прочитайте его четыре функции.

## Тестирование view

View состоит из двух чистых функций, и тест для view — обычный тест. Для первого вида тестов браузер не нужен.

```pavlus todos.pavlus
ul
  for todo in todos key todo.id
    li(class:done=todo.done @click=toggle(todo.id)) {todo.title}
p {todos.length} todos
```

```ts todos.test.ts
import { expect, test } from "vitest";
import view from "./todos.pavlus";

const write = { id: 1, title: "Write", done: false };

test("finishing a todo changes only its class", () => {
  const patches = view.diff(
    { todos: [write] },
    { todos: [{ ...write, done: true }] },
  );
  expect(patches).toEqual([
    { op: "attr", id: "2#1", name: "class", value: "done" },
  ]);
});

test("nothing changed, nothing to patch", () => {
  expect(view.diff({ todos: [write] }, { todos: [write] })).toEqual([]);
});
```

Эти два теста работают в обычном Node. Запускающему тесты нужен plugin, поэтому в конфигурации Vite или Vitest в `plugins` должен быть `pavlus()`.

Для теста, включающего DOM, в пакете есть `@service-laboratory/pavlus/testing`. Его функция `mountView(viewOrComponent, initialState, document?)` монтирует view в свежий контейнер с настоящим plugin для DOM, без остального приложения. Она возвращает контейнер (`root`), plugin для DOM, список message, которые произвели события пользователя (`messages`), и функции `set(nextState)` и `unmount()`. Монтируйте компонент, а не только его view, когда в шаблоне есть `+outlet`, потому что outlet нужен `routing` компонента.

```ts todos.dom.test.ts
// @vitest-environment jsdom
import { expect, test } from "vitest";
import { mountView } from "@service-laboratory/pavlus/testing";
import view from "./todos.pavlus";

test("the DOM follows the state, and a click sends a message", () => {
  const write = { id: 1, title: "Write", done: false };
  const check = { id: 2, title: "Test", done: false };
  const h = mountView(view, { todos: [write, check] });

  h.set({ todos: [write, { ...check, done: true }] });
  expect(h.root.querySelectorAll("li")[1].className).toBe("done");

  h.root.querySelector("li")!.click();
  expect(h.messages).toMatchObject([{ id: "toggle", payload: 1 }]);

  h.unmount();
  expect(h.root.innerHTML).toBe("");
});
```

Массив `messages` хранит то, что отправил plugin для DOM. Клик по первому элементу произвёл `{ id: "toggle", payload: 1, event: { type: "click" } }`: id message и payload приходят из шаблона, а поле `event` добавляет plugin. `h.root.innerHTML` сразу после `mountView` выглядит так:

```text
<!--pavlus--><ul><!----><!----><li>Write</li><!----><!----><li>Test</li><!----><!----></ul><p>2 todos</p><!--/pavlus-->
```

Это хороший способ увидеть маркеры: каждый элемент находится между двумя пустыми комментариями, а список — между ещё двумя. Комментарии `pavlus` и `/pavlus` ограничивают весь render.

## Что вы узнали

- `compileTemplate(source, { filename, runtime })` возвращает текст ES-модуля с `render`, `diff`, `meta` и view по умолчанию. `compileToView` возвращает работающее view и предназначен для тестов и инструментов. `DEFAULT_RUNTIME` — откуда приходят хелперы.
- Plugin для Vite `pavlus()` компилирует каждый импорт `.pavlus`, пропускает `?raw`, `?url` и `?inline`, намеренно не поставляет source map и сообщает об ошибке шаблона с файлом, строкой и колонкой.
- `@service-laboratory/pavlus/env` даёт импортам `.pavlus` их типы. State типизирован как `any`.
- Ошибки компилятора — это `TemplateError` с позициями, отсчитываемыми с 1, а несколько опечаток создают элементы, а не ошибки.
- Golden-файлы фиксируют точный результат одиннадцати фикстур, поэтому изменение в сгенерированном коде всегда видно на ревью. View можно тестировать как две чистые функции или монтировать через `mountView`.
