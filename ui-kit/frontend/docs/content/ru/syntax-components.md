## Один шаблон, много файлов

Страница растёт. Шапку, карточку, строку таблицы и поле формы хочется написать один раз и использовать во многих местах. В pavlus каждый файл `.pavlus` — это шаблон, и один шаблон может **встроить** (embed) другой. Встроенный шаблон называется *дочерним view* (или просто дочерним), а тот, кто его встраивает, — его родителем.

Встраивание состоит из двух шагов: вы **импортируете** дочерний шаблон в начале файла и **используете** его строкой, которая начинается со знака плюс.

::demo badge

Первая строка, `import Badge from "./badge.pavlus"`, приносит дочерний шаблон под локальным именем `Badge`. Строка `+Badge#status(label=text)` рендерит его в этом месте. `label=text` передаёт **prop**: внутри `badge.pavlus` (здесь: `span.badge {label}`) у state есть поле `label`, а его значение — это `text` родителя.

Больше дочерний шаблон не видит ничего. Он не знает state своего родителя, только props, которые ему дали. Именно это делает дочерний шаблон переиспользуемым: его входные данные перечислены в том месте, где он используется.

Посмотрите на шаг: когда `text` меняется, выходит один patch `text` с id `1/2`. Id собственных узлов дочернего шаблона получают суффикс (`/2`) от строки, которая его встраивает, чтобы два экземпляра одного дочернего шаблона никогда не порождали одинаковый id.

## Строка import

```pavlus
import Card from "./card.pavlus"
import UserList from "../users/view.pavlus"

section
  +Card#intro(title="Welcome")
```

Все строки `import` идут первыми, перед любым элементом, в нулевой колонке. Имя должно начинаться с заглавной буквы. Вот ошибки, о которых сообщает парсер:

```text
"card" cannot be used as a component name (start with a capital letter, not String/Array/Map/Set/Error) (line 1, col 1)
"Card" is imported twice (line 2, col 1)
`import` lines must be at the top of the file (line 2, col 1)
```

По заглавной букве шаблон отличает компонент от тега: `+Card` может быть только импортированным компонентом. `String`, `Array`, `Map`, `Set` и `Error` отклоняются, потому что их использует сам сгенерированный код.

Путь записывается так, как его разрешит ваш бандлер. Компилятор копирует строку в сгенерированный модуль как обычный ES-импорт (`import Badge from "./badge.pavlus";`, откройте модуль демо выше, чтобы увидеть это), а Vite plugin компилирует импортированный файл так же. Дочерний шаблон — это модуль с `render` и `diff`, как и любой шаблон.

Если вы используете имя, которое не импортировано, вы получите сообщение, которое говорит, что делать:

```text
"Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

## Строка embed: +Name#id(props)

Весь синтаксис embed такой:

```text
+Name#instance(prop=value other="text {x}" flag ...spread)
```

- `Name` — импортированное имя.
- `#instance` — **имя экземпляра**. Для статического embed оно необязательно. Без него именем становится импортированное имя с первой буквой в нижнем регистре: `+UserCard` — это `userCard`.
- Скобки с props необязательны.
- Больше ничего на строке быть не может, и у embed не может быть дочерних строк. Текст после него даёт `Unexpected "x" after component`, а строка с отступом под ним — `This line cannot have children`.

Имя экземпляра выполняет три задачи. Оно задаёт префикс **messages** дочернего шаблона (см. ниже). Оно служит ключом дочернего компонента в таблице `children` логики (см. конец страницы). И именно его компилятор перечисляет в `meta.embeds` модуля.

## Props

Prop записывается так же, как атрибут, и допускает те же формы значения. Разница в том, что с ним происходит: он не попадает в HTML, а становится полем state дочернего шаблона.

::demo props

Прочитайте три embed:

| Значение | Пример | Что получает дочерний шаблон |
| --- | --- | --- |
| текст в кавычках | `kind="static"` | строку |
| текст с дырками | `kind="user {user.id}"` | строку, с `toText` для каждой дырки |
| выражение | `label=user.name`, `count=items.length` | само значение, с сохранением его типа |
| голое имя | `active` | `true` |
| spread | `...user` | каждое поле объекта |

**Тип сохраняется** для выражения: `count=items.length` даёт дочернему шаблону число, а `label=user.items` дал бы ему сам массив, а не текст. Строка с дырками и другим текстом — всегда строка. Prop в кавычках, состоящий только из одной дырки, `kind="{x}"`, — то же самое, что `kind=x`: тип сохраняется.

Props записываются по порядку, и более поздний побеждает: в третьем embed `...user` приносит `label` («From spread»), а `count=0` заменяет `count`, который мог быть у spread. Не заданный prop равен `undefined`, поэтому заголовок третьей «фишки» начинается с `: `: `kind` отсутствует, а `toText(undefined)` пуст.

Имена props должны быть обычными идентификаторами. Имя вроде `data-x` — ошибка: `"data-x" is not a valid prop name`. А spread разрешён только в компоненте (`+Name(...x)`); на элементе это `` `...spread` is only allowed in component props ``.

## Когда обновляется дочерний шаблон?

Каждый embed получает собственную защиту в `diff` родителя. Сгенерированный код для embed с двумя props:

```ts
if (prev.noteTitle !== next.noteTitle || prev.noteBody !== next.noteBody) {
  patches.push(...Card.diff(
    { "title": prev.noteTitle, "body": prev.noteBody },
    { "title": next.noteTitle, "body": next.noteBody },
    idSuffix + "/2",
    messagePrefix + "note.",
    childEnv(env, "note", next),
  ));
}
```

Родитель строит старые props и новые props из двух своих state и вызывает с ними собственный `diff` дочернего шаблона. Если ни одно из имён, прочитанных props, не изменилось, дочерний шаблон не вызывается вообще.

::demo child-diff

В первом шаге меняется тело, и `diff` карточки возвращает один patch `text`. Во втором шаге меняется только заголовок, и на карточку даже не смотрят. Дочерний шаблон стоит так же дёшево, как часть шаблона родителя.

## Messages от дочернего шаблона

События дочернего шаблона отправляются с именем экземпляра в качестве префикса. Это объяснялось на [странице о событиях](page:syntax-events): кнопка `reset` счётчика становится `apples.reset` или `pears.reset` в зависимости от экземпляра.

::demo two-instances

У двух экземпляров одного и того же `Counter` два имени, поэтому приложение может их различить. В шаге меняется `pears`. Prop `value` меняется, поэтому выходит patch `text`, а также patch `handler`, потому что изменился и payload `reset(value)`. Id в этом patch уже `pears.reset`:

```text
{"op":"handler","id":"5/1","event":"click","msg":{"id":"pears.reset","payload":6}}
```

Префикс растёт с каждым уровнем: дочерний шаблон дочернего шаблона даёт `apples.cell.reset`. Идентичность внутри цикла — другое дело. Имя экземпляра фиксировано в шаблоне и не может зависеть от элемента, поэтому внутри цикла экземпляры различаются по payload:

::demo in-loop

Каждая строка отправляет message `row.toggle` с id своей задачи в качестве payload. Handler `"row.toggle"` родителя получает этот id. Обратите внимание на id patch класса, `0#2/2`: в нём присутствуют узел строки (`0`), key элемента (`#2`) и embed (`/2`).

## Embed внутри if и for

Embed — такой же узел, как любой другой. Он может быть внутри `if`, `else`, `for` или другого элемента. Его позицию определяют окружающие строки.

::demo in-if

Когда `open` становится истинным, панель рендерится с нуля и вставляется. Когда оно снова становится ложным, она очищается. State дочернего шаблона не остаётся в DOM: в следующий раз он снова рендерится из props.

## Дочерний шаблон, который ничего не рендерит

Дочерний шаблон — обычный шаблон, поэтому ему может быть нечего показывать, например потому что его единственный узел — это `if`, который ложен. Это допустимо. Родитель сохраняет для него место, и остальные строки родителя не сдвигаются.

::demo empty-child

Следите за шагами. В начале уведомления на странице нет, а `After the notice` стоит на правильном месте. Когда `message` становится `Saved`, `if` дочернего шаблона вставляет `p` на место дочернего шаблона (обратите внимание на id маркеров, которые заканчиваются на `/2`). Когда сообщение меняется, меняется только текст. Когда оно становится пустым, уведомление очищается. Родитель не сделал ничего особенного: вся работа выполняется в собственном `diff` дочернего шаблона.

## Динамические embed: +{expr}

Иногда дочерний шаблон неизвестен, когда вы пишете шаблон: панель вкладок, которая показывает свой view для каждой вкладки, виджет, выбранный пользователем. Нельзя импортировать то, что приходит из state, поэтому в pavlus есть вторая форма, где дочерний шаблон — это **значение выражения**:

```pavlus
div.tabs
  +{tab.component}#content(...tab.state)
```

Выражение даёт view или компонент, у которого есть `view`. У динамического embed *должно* быть имя экземпляра (`#content`), потому что нет импортированного имени, откуда его можно было бы взять: `+{tab}(x=1)` — ошибка, `A dynamic component needs an instance name: +{expr}#name(...)`.

Что делает страница, когда значение меняется:

- значение — **тот же view**: запускается его собственный `diff`, как для статического embed;
- значение — **другой view**: старое содержимое очищается между двумя маркерами, а новый view рендерится с нуля. Два шаблона никогда не сравниваются друг с другом;
- значение — `null` или `undefined`: embed ничего не рендерит.

::demo dynamic-empty

Последний случай — дочерний шаблон, которого нет. `h2` и `p` на месте, а между ними ничего нет. Если значение — не view (например, число), `render` выбрасывает `pavlus: +{...} needs a view or a component with a view`.

> [!NOTE] Views в state
> View — это объект с функциями, а не JSON. Store хранит его как есть, но инструмент, который сохраняет или печатает state, его не покажет. Когда вам нужен state, который можно сериализовать, храните в state имя (`tab: "users"`) и выбирайте через `if` и `else if`, импортировав обе ветки. Форма `+{expr}` предназначена для случаев, когда набор дочерних шаблонов открыт.

## +outlet: страница, выбранная маршрутом

В одностраничном приложении есть оболочка (шапка, меню) и посередине страница, которую выбирает адрес. Оболочке нужно место для «страницы». Это `+outlet`.

```pavlus
header.shell
  nav
    a(href="/") Home
    a(href="/about") About
main.page
  +outlet
```

После `+outlet` ничего не принимается: строка вроде `+outlet x` — ошибка. Он рендерит **дочерний компонент маршрута** того компонента, которому принадлежит шаблон. Какой это дочерний компонент, берётся из таблицы `routing` компонента:

```ts shell.ts
class AppShell extends Component<AppState> {
  view = view;
  routing: Routing<AppState> = {
    "/": { component: dashboard, key: "dashboard", name: "dashboard" },
    "/about": { view: aboutView },
    "*": { view: notFoundView },
  };
}
```

Outlet ведёт себя как динамический embed. Когда маршрут меняется на другую страницу, старая страница очищается между маркерами, а новая рендерится. Когда маршрут остаётся на той же странице, запускается только `diff` этой страницы. Её messages получают имя экземпляра в качестве префикса, как у любого дочернего шаблона: страница, зарегистрированная как `dashboard`, отправляет `dashboard.something`. Если ни одна запись не соответствует адресу и записи `"*"` нет, outlet пуст, как null-дочерний шаблон.

Поскольку маршрут — не поле, которое шаблон может видеть, компилятор не может перечислить имена, которые читает outlet. Узлы вокруг него проверяются при каждом изменении state, а страницы внутри по-прежнему пропускают то, что не изменилось. Поэтому в коде `diff` шаблона с outlet сказано `reads: the route and the routed child`.

Outlet нужен компонент, а не только шаблон. Если вы монтируете только view, `render` выбрасывает такую ошибку:

```text
pavlus: +outlet needs a component with a `routing` table; mount the component, not only its view
```

По этой причине демо на этой странице не рендерят outlet. [Маршрутизация](page:concepts-routing) описывает весь механизм.

## Сторона логики дочернего шаблона

Всё выше — о шаблонах. У дочернего шаблона может быть и компонент со своими handlers. Родитель объявляет его в таблице `children` своего компонента с тем же именем, которое шаблон дал экземпляру:

```ts dashboard.ts
class Dashboard extends Component<DashboardState> {
  view = dashboardView;
  children: Children<DashboardState> = {
    users: {
      component: usersList,
      key: "users",
      props: (s) => ({ filter: s.filter }),
    },
  };
}
```

а шаблон говорит `+UsersList#users(...users filter=filter)`. Правило, которое нужно запомнить: `users` в шаблоне, `users` в `children`, `users` в state. Message `users.select` попадает в handler `select` компонента `usersList` с удалённым префиксом. Полную историю рассказывает страница [Компоненты и состояние](page:concepts-components).

## Собираем вместе

Родитель, который использует цикл с key, условие и два вида дочерних шаблонов. Шаблоны `Row` и `Panel` — те, что в демо выше.

```pavlus
import Row from "./row.pavlus"
import Panel from "./panel.pavlus"

section.tasks
  h3 Tasks ({tasks.length})
  ul
    for task in tasks key task.id
      +Row#row(id=task.id title=task.title done=task.done)
  if selected
    +Panel#details(title=selected.title)
  else
    p.muted Select a task
```

Каждый message `row` несёт id своей задачи, а каждый message `details` уходит в логику панели. В шаблоне родителя нет ни одного собственного обработчика событий. Он только решает, какие дочерние шаблоны существуют и что получает каждый.

## Что вы узнали

- `import Name from "./file.pavlus"` в начале, `+Name#id(props)` там, где должен быть дочерний шаблон; дочерний шаблон видит только свои props.
- Props — это текст в кавычках, текст с дырками, выражения (с сохранением типа), голые флаги или `...spread`; более поздний prop побеждает.
- Имя экземпляра задаёт префикс messages дочернего шаблона (`pears.reset`) и связывает дочерний шаблон с `children` его компонента.
- `+{expr}#id` рендерит view, являющийся значением; значение `null`, пустой шаблон и несовпавший outlet ничего не рендерят.
- `+outlet` рендерит дочерний компонент маршрута того компонента, которому принадлежит шаблон.
