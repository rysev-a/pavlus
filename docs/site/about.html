pavlus — an application that is a function

pavlus (npm: @service-laboratory/pavlus) is a TypeScript framework where the whole application is a pure function: app(message, state) → Effect[]. The framework's job is to make that practical — a compiler, a tiny core, and plugins that do the dirty work.

The pieces

The compiler turns .pavlus templates (an indented tree, pug-style) into two pure functions, render(state) and diff(prev, next). Because it records which state roots every subtree reads, diff skips unchanged subtrees with a === check — updates are eight kinds of small patch ops, never a re-render of the world.

The core is a message loop: it calls the app with each message, hands the returned effects to the plugins in order, and notifies every plugin when the state identity changed. That is the entire engine — the six actors around it (browser, dom, store, http, the app island, the core) only talk through data: messages in, effects out.

The plugins own everything impure: DOM, state, network, logs, timers, sockets — and admin-app/ in the repo is a complete real application built this way (dashboard, users CRUD, shop, billing, backed by Postgres). This site is generated: the build compiles every documented example with the real compiler and runs the real runtime.

The six concepts

Message { id, payload?, event? }

The input of the app. Everything that happens outside — a click, an HTTP reply, a timer — arrives as one.

Effect { plugin, type, … }

The output of the app. A request for a plugin to do something. Not a callback — data.

Handler load(msg, state, ctx)

A component method named after the message id it handles. No switch, no registry.

Plugin { name, handle, … }

Owns every side effect and its own state, and turns the outside world into messages.

View { render, diff, meta }

A compiled template. Both functions are pure — the DOM plugin is their only interpreter.

Patch { op: "text", … }

What diff returns: one of eight DOM operations, as data. The DOM effect of a state change.
