part I

Templates: from .pavlus to two pure functions

A template is an indented tree (pug/slim style). The Vite plugin compiles it on import: parser.parse() turns lines into an AST, analyze.nodeDeps() records which state roots every subtree reads, and codegen.generate() emits a readable module with render and diff. Because the compiler knows each node's dependencies, diff skips every subtree whose inputs did not change (=== checks) — that is the whole trick, and each example below shows it on the real generated code.

4. Events

An event attribute (@click=go(page + 1)) is not a function: render evaluates its arguments on the current state and attaches plain message data ({ id: "go", payload: … }). diff compares the data by value — when only a payload changes, one handler patch rebinds the message on the same element; the DOM listener itself is attached once and never changes.

The three views of one template

1 · the pavlus template
ul.pager  li(@click=go(1)) first  li(@click=go(page - 1)) prev  li(@click=go(page + 1)) next  li(@click=go(total)) last
2 · middle data — AST + dependencies
el  ul.pager                                    #0   reads: page, total

    text  first                                     #2   reads: — (reads nothing)

5. A condition

if / else render one branch. The block is delimited by two markers (empty comment nodes with ids), so a change of branch is two patches: clear what is between the markers, insert the new branch, rendered from the new state. Inside the same branch, only the usual small patches.

The three views of one template

1 · the pavlus template
if loading  p.status Loading...else  p.done Loaded {count} items
2 · middle data — AST + dependencies
if  if loading                                  #0   reads: count, loading
  ┌ then loading
  │ el  p.status Loading...                         #1   reads: — (reads nothing)
  │   text  Loading...                                #2   reads: — (reads nothing)
  ┌ else
  │ el  p.done Loaded {count} items                 #3   reads: count
  │   text  Loaded {count} items                      #4   reads: count

6. A loop

Components and slots

A template embeds another component with +Name#instance(props): the props are expressions on the parent's state and become the child template's state; ...expr spreads one. part II · core

Core: an application that is a function

The compiler gives you pure views; the architecture makes the whole application pure. Your handlers never touch the DOM, the network, the clock or randomness: they get a message and the state, and return an array of effects — plain data. The core feeds effects to plugins in order; the store plugin replaces the state immutably; when the state object identity changes, every plugin gets onState(next), and the DOM plugin turns the change into patches for the browser. Purity is a documented contract, not a runtime police: the framework simply gives you nowhere dirty to go.

The whole system

The core, in full

This is the whole engine (from framework/src/core/mod.ts): a queue, one call to the app, effects to plugins, then onState if the state identity changed. Messages that arrive while a tick is running are processed in the same tick.

The purity contract

  • Handlers are pure: no Date.now(), Math.random(), fetch, DOM, logs. Same message + same state ⇒ same effects.
  • Effects and patches are plain data; plugins are the only interpreters.
  • State is immutable (the store does it); diff trusts ===.
  • Keep component instances free of mutable fields — the same instance handles every message.
  • Need the time? time.now(). Need random? A plugin. The app describes, plugins do.

part III · plugins

Plugins: the interpreters of effect data

Every effect names its plugin, and the core routes it by that name — byName.get(effect.plugin); an effect for an unknown plugin throws. The first plugin with getState() is the state source, plugin names must be unique, and mount needs a plugin named dom. The six built-ins cover DOM, state, network, logs, time and sockets — and writing your own is a small interface.

The store plugin: state as data

State lives in one plugin — the first one with getState(). Handlers never mutate it; they return set / merge / remove effects. Updates are pure functions with structural sharing: untouched branches keep their object identity, which is exactly what diff's === checks need. Every change is recorded with its inverse (restoreEffect), so undo and time travel need no snapshots. No-op writes return the same state — and trigger no re-render.

EffectWhat it does
store.set(path, value)Sets the value at path, creating missing parents.
store.merge(path, obj)Shallow-merges into the object at path.
store.remove(path)Removes the value; an array element is spliced out.
store.undo(steps?)Applies the recorded inverse of the last changes.
store.restoreTo(ts)Undoes everything recorded after ts (time travel).

The http plugin: requests are effects, replies are messages

A request carries a required id: sending another request with the same id cancels the previous one (think search-as-you-type), and a cancelled request never dispatches anything. On success or failure the plugin dispatches the onSuccess / onError message — the app never sees a promise. On the server the same plugin answers settled() for rendering after load.

The dom plugin: the only imperative code

Mounting renders the view into the container between two comment markers and registers every node id. Updates interpret the eight patch ops. Events are never inline functions: the template's @click=remove(user.id) is data ({ id: "remove", payload: user.id }); one stable listener per element and event type reads the latest message data and dispatches it — so re-binding is a map write, and diff can compare handlers by value.

Patch opMeaning
textReplace a text node's content.
attr / rmAttrSet or remove an attribute (value/checked mirror properties too).
handlerRebind an event's message data.
insertInsert rendered vnodes before a node (new branch, new list item).
clearEmpty the range between two markers (a branch switch).
remove / moveRemove or reorder a sibling range (keyed list reconciliation).

  function setHandler(el: Element, event: string, msg: EventMsg): void {    let l = listening.get(el);    if (!l) listening.set(el, (l = { msgs: new Map(), fns: new Map() }));    l.msgs.set(event, msg);    if (l.fns.has(event)) return; // listener reads the latest message    const fn: EventListener = (ev) => {      const m = l!.msgs.get(event)!;      if (m.prevent) ev.preventDefault();      if (m.stop) ev.stopPropagation();      ctx?.dispatch({ id: m.id, payload: m.payload, event: snapshot(ev) });    };    l.fns.set(event, fn);    el.addEventListener(event, fn);    listenerCount++;  }

The logger plugin: even logs are effects

A handler that needs to say something returns a log.info(…) effect — plain data, checked by the same tests as everything else. The logger plugin writes it to the console, or to any sink: the frontend tests collect the log lines of an app in an array instead of spying on console.

The time plugin: the clock is a plugin too

time.now() replies with the current time as a message; setTimeout and setInterval are effects keyed by id — starting a timer with a running id replaces it, cancel / cancelAll stop them. The clock itself is injectable (now, setTimeout, …), so the same pure handlers run deterministically in tests. No Date.now() in application code — that is the purity contract, kept honest by giving time an address.

The ws plugin: WebSockets as messages

A connection is identified by id: ws.connect({ id, url, onOpen, onMessage, onClose }) opens it, and every frame arrives as a message — JSON frames parsed, plain text as strings. ws.send is an effect like any other, ws.close closes; connecting again with the same id replaces the old socket. The socket constructor is injectable, so tests drive frames through a fake.

Your own plugin

A plugin is one object: a name and handle(effect, ctx) — with optional init, onState and dispose if you need them. Everything inside a plugin is allowed to be dirty; that is the plugin's whole job. The two types involved:

Plugin — framework/src/core/types.ts
export interface Plugin<E extends EffectLike = Effect, S = unknown> {  readonly name: string;  init?(ctx: PluginContext<S>): void;  handle(effect: E, ctx: PluginContext<S>): void;  /** Called after the application state changed. */  onState?(state: S, ctx: PluginContext<S>): void;  dispose?(): void;}
PluginContext — framework/src/core/types.ts
export interface PluginContext<S = unknown> {  /** Feed a message back into the application. Safe to call from anywhere. */  dispatch(message: Message): void;  /** Current application state (from the store plugin). */  getState(): S;  /**   * Applies an effect directly, without going through the application   * (devtools, tests): the plugin runs, and plugins are notified if the   * state changed.   */  dispatchEffect(effect: Effect): void;}

The rules the core enforces (from framework/src/core/mod.ts): effects route to plugins by name — an effect whose plugin matches nothing throws pavlus: no plugin "…"; duplicate plugin names throw at createApp(); the first plugin with getState() is the state source (that is the store's seat); mount requires a plugin named dom; and ctx.dispatch() feeds a message back into the loop while ctx.dispatchEffect() applies an effect directly (for devtools and tests).

a minimal custom plugin — sample code, not sliced from the repo
import type { Effect, Message, Plugin, PluginContext } from "@service-laboratory/pavlus";export type RandomEffect = Effect & {  plugin: "random";  type: "int";  as: string; // the message id that receives the rolled value  min: number;  max: number;};// the effector — same role as store.set(...) or http.request(...)export function randomInt(e: Omit<RandomEffect, "plugin" | "type">): RandomEffect {  return { plugin: "random", type: "int", ...e };}export function randomPlugin(): Plugin<RandomEffect> {  return {    name: "random", // effects route to plugins by this name    handle(effect: RandomEffect, ctx: PluginContext) {      const span = effect.max - effect.min + 1;      const value = effect.min + Math.floor(Math.random() * span);      // dirty work done — the answer re-enters the loop as a message      ctx.dispatch({ id: effect.as, payload: value });    },  };}

Handlers return its effects like any built-in's, and the plugin answers with a message — the loop stays the loop:

Checklist for a new plugin: pick a unique name (it is the routing key); type your effects as MyEffect = Effect & { plugin: "…", type: … }; export an effector helper per effect type (like store.set); do the dirty work in handle and answer with ctx.dispatch(); use onState to react to state changes and dispose to clean up. Register it in the plugins array of createApp() — order matters only for who owns the state.
