The framework where your code is a pure function

pavlus applications are 100% pure functions: a handler takes a message and the state, and returns effects — plain data. Plugins do every dirty thing (DOM, HTTP, time, storage). Templates compile to two pure functions, render(state) and diff(prev, next) — one click becomes a handful of patches, not a re-render.

One picture: your application as one island (app + core), the plugin column — and, drawn right into the diagram, the toy browser with its store devtools and the server underneath. Every plugin touches exactly two neighbours, the core and the browser; only the browser talks to the server — watch its light flash green. The controls under the diagram walk a tiny admin session step by step; the dots inside the browser's devtools mark the steps — green where the store commits — and clicking one jumps straight there.

why pavlus

Why: the dirty work belongs to plugins, not to you

Handlers stay pure app(message, state) → Effect[]

Same message + same state ⇒ same effects. No Date.now(), no fetch(), no DOM in application code — so every handler is tested by calling it with data.

Effects are data, not callbacks { plugin, type, … }

A handler returns an array of plain effects. Plugins (dom, store, http, time, ws, logger) interpret them. No promise chains, no event spaghetti, no spies.

Templates compile to pure functions render · diff

The compiler records which state roots every subtree reads; diff skips everything whose inputs did not change (=== checks), so a click patches one text node.

SSR falls out for free same render on the server

The same pure render(state) produces HTML on the server; the http plugin answers settled() once data has loaded. One mental model everywhere.
