## Die Idee in einer Minute

Pavlus ist ein Framework zum Bauen von Weboberflächen. Es beruht auf einer Regel: **Der Code, den du schreibst, berührt die Außenwelt nicht.** Er liest nie das DOM, ruft nie `fetch` auf, fragt nie nach der Uhrzeit und schreibt nie in die Konsole. Stattdessen beantwortet er immer wieder eine einzige Frage:

> Welche **Effekte** sollen passieren, wenn diese **Message** und dieser **State** gegeben sind?

Eine *Message* ist ein kleines Stück einfacher Daten, das sagt, was gerade passiert ist: `{ id: "inc" }` bedeutet „der Nutzer hat auf den Plus-Button geklickt". Der *State* ist ein einfaches Objekt, das alles enthält, was der Bildschirm zeigt. Ein *Effekt* ist ebenfalls einfache Daten. Er beschreibt etwas, das getan werden soll, zum Beispiel „setze das Feld `count` auf 3" oder „sende diese HTTP-Anfrage". Dein Code gibt nur die Beschreibung zurück. Er erledigt die Arbeit nicht selbst.

Die Arbeit erledigen **Plugins**. Ein Plugin ist für eine Art von Seiteneffekt zuständig: das DOM, HTTP, Timer, die Adresse des Browsers, den Store, der den State hält. Wenn in der Außenwelt etwas passiert (ein Klick, eine Antwort, ein Timer-Tick), macht ein Plugin daraus eine Message und gibt sie an deinen Code. Wenn dein Code Effekte zurückgibt, reicht der Core jeden Effekt an das Plugin weiter, an das er adressiert ist.

Der dritte Teil ist die **Template-Sprache**. Du schreibst die HTML-Struktur einer Komponente in einer kurzen, einrückungsbasierten `.pavlus`-Datei. Ein Compiler macht daraus zwei einfache Funktionen: `render(state)`, die die anzuzeigenden Knoten zurückgibt, und `diff(prev, next)`, die die kleine Liste der Änderungen (Patches) zurückgibt, die nötig sind, wenn der State von einem Wert zum anderen wechselt.

```text
 click, reply, timer tick
          |   a plugin turns it into a message
          v
 your code:  (message, state)  ->  effects          pure, no side effects
          |   effects are plain data
          v
 plugins:    store, dom, http, time, router, ...    the only code that does things
          |   the store changed the state
          v
 template:   diff(prev, next)  ->  patches           pure, generated by the compiler
          |
          v
 the dom plugin applies the patches to the page
```

Das ist derselbe Kreislauf wie in der Sprache Elm, mit einem Compiler, der die Template-Seite schnell macht. Die nächste Seite dieser Reihe, [Schnellstart](page:quick-start), baut ein lauffähiges Beispiel. Die Seite [Architektur: reiner Code und Effekte](page:concepts-architecture) erklärt den Kreislauf im Detail.

## Warum der Code rein bleiben soll

Eine reine Funktion gibt für dieselbe Eingabe immer dasselbe Ergebnis zurück und verändert nichts außerhalb von sich selbst. Diese eine Eigenschaft gibt dir Dinge, die sonst meist teuer sind:

- **Tests ohne Browser.** Um einen handler zu testen, rufst du ihn mit einer Message und einem State auf und vergleichst die zurückgegebenen Effekte mit einfachen Asserts. Es gibt nichts zu mocken.
- **Derselbe Code auf dem Server.** Das Rendern in einen String braucht kein DOM, also laufen die Komponenten, die du im Browser ausführst, auch in Node. Die Seite [Server-Side-Rendering](page:concepts-ssr) zeigt, wie.
- **Replay und Verlauf.** Ein State sind einfache Daten, und jede Änderung ist ein aufgezeichneter Effekt. Du kannst also eine Änderung rückgängig machen oder zu einem früheren Zeitpunkt zurückgehen. Das Store-Plugin führt diesen Verlauf für dich.
- **Lesbare Fehler.** Wenn etwas schiefgeht, kannst du die Message und die Effekte ausgeben. Beides sind gewöhnliche Objekte.

Der Preis ist eine Regel, die du selbst einhalten musst: **Das Framework prüft nicht, ob dein Code rein ist.** Wenn ein handler trotzdem `Date.now()` aufruft, hindert ihn nichts daran, und du verlierst die oben genannten Vorteile. Die Konvention ist einfach. Wenn ein handler die Uhrzeit braucht, gibt er einen `time`-Effekt zurück und erhält die Antwort als Message.

## Ein winziges ganzes Programm

Hier ist ein vollständiger Zähler in vier Teilen. Zuerst das Template. Es ist die HTML-Struktur der Komponente, wobei `{count}` das Feld `count` des State liest und `@click=inc` sagt, dass ein Klick die Message `inc` sendet.

::demo counter

Die Demo oben wird vom echten Compiler in deinem Browser kompiliert. Die zwei Schritte unten zeigen die Patches, die `diff` zurückgibt, wenn `count` von 2 auf 3 und wieder zurück geht. Nur der Textknoten ändert sich. Der Hinweis-Absatz wird eingefügt, wenn die Bedingung `count > 2` wahr wird, und entfernt, wenn sie falsch wird.

Zweitens die Komponente. Sie ist eine Klasse mit einer Methode pro Message. Jede Methode erhält die Message und den State und gibt eine Liste von Effekten zurück. Hier werden die Effekte mit dem Helfer `store.set(path, value)` des Store-Plugins gebaut, der das einfache Objekt `{ plugin: "store", type: "set", path, value }` zurückgibt.

```ts counter.ts
import { Component, type Message } from "@pavlus/frontend";
import { storeEffector as store } from "@pavlus/frontend/plugins";
import view from "./counter.pavlus";

export interface CounterState {
  count: number;
}

export class Counter extends Component<CounterState> {
  view = view;

  inc(_msg: Message, state: CounterState) {
    return [store.set("count", state.count + 1)];
  }

  dec(_msg: Message, state: CounterState) {
    return [store.set("count", state.count - 1)];
  }
}

export const counter = new Counter();
```

Drittens die Verdrahtung. `createApp` verbindet die Komponente mit ihren Plugins. Das Store-Plugin hält den State, und das DOM-Plugin rendert die view der Komponente in das Element `#app` und meldet Klicks als Messages.

```ts main.ts
import { createApp } from "@pavlus/frontend";
import {
  DomPlugin,
  createStorePlugin,
} from "@pavlus/frontend/plugins";
import { counter, type CounterState } from "./counter.ts";

createApp<CounterState>({
  app: counter,
  plugins: [createStorePlugin<CounterState>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

Viertens gibt es nichts weiter. Kein `useState`, keine Subscriptions, kein `setCount`. Ein Klick wird zu `{ id: "inc" }`, `inc` gibt einen `set`-Effekt zurück, der Store ersetzt den State, `diff` vergleicht den alten und den neuen State und gibt einen `text`-Patch zurück, und das DOM-Plugin wendet ihn an.

> [!NOTE] Der State lebt nicht in der Komponente
> Das `Counter`-Objekt hat keine Felder, die sich ändern. Der State lebt im Store-Plugin und wird an jeden handler übergeben. Die Komponenten-Instanz wird von allen Messages gemeinsam genutzt, deshalb muss sie frei von veränderlichen Daten bleiben. Die Seite [Komponenten und State](page:concepts-components) erklärt, warum.

## Wie pavlus sich zu Virtual-DOM-Frameworks verhält

Viele beliebte Frameworks nutzen ein *Virtual DOM*: Bei jedem Update läuft der Komponenten-Code erneut, baut einen neuen Baum aus leichtgewichtigen Knoten, und das Framework vergleicht ihn mit dem vorherigen Baum, um zu finden, was sich geändert hat. Pavlus geht für den view-Teil einen anderen Weg. Die Tabelle vergleicht den Ansatz im Allgemeinen, nicht ein bestimmtes Produkt, und sie nennt, worauf pavlus verzichtet, genauso wie das, was es gewinnt.

| Frage | Typisches Virtual-DOM-Framework | Pavlus |
| --- | --- | --- |
| Wie wird eine Änderung gefunden? | Das Framework vergleicht den alten und den neuen Baum aus Knoten. | Der Compiler erzeugt ein `diff(prev, next)`, das State-Felder mit `===` vergleicht. Es wird kein Baum verglichen. |
| Wie viel Arbeit macht eine unabhängige Änderung? | Hängt vom Framework ab; oft läuft die Komponentenfunktion erneut. | Ein Teilbaum, der keines der geänderten Felder liest, wird mit einer einzigen Prüfung übersprungen. |
| Wo lebt die Update-Logik? | Im Komponenten-Code, oft mit Hooks oder Settern. | In handlern, die Effekte zurückgeben. Die view enthält keine Update-Logik. |
| Wo leben Seiteneffekte? | Überall im Komponenten-Code. | Nur in Plugins. Anwendungscode gibt Daten zurück. |
| Was ist ein Event-handler? | Eine Funktion. | Daten: `{ id, payload }`. `diff` vergleicht handler nach Wert. |
| State-Änderungen | Oft über Setter, manchmal durch Mutation. | Der Store ersetzt den State. Du darfst ihn nie direkt verändern, weil `diff` auf `===` vertraut. |
| Anwendungslogik testen | Braucht meist einen Renderer oder Mocks. | Rufe den handler auf und vergleiche die Effekte. |
| Sprache der Templates | Oft JSX, in derselben Datei wie der Code. | Eine eigene `.pavlus`-Datei mit eigener kleiner Syntax und Ausdruckssprache. |
| Reife | Große Ökosysteme, viele Bibliotheken, viele Entwickler. | Ein junges Framework mit kleiner Oberfläche. Slots, rekursive Templates und typisierte props gibt es noch nicht. |

> [!WARNING] Ein anderer Kompromiss, nicht in jedem Fall ein besserer
> Kompiliertes Diffing ist schnell für das, was es kennt, aber die Template-Sprache ist kleiner als JavaScript. Ausdrücke sind eine kleine reine Teilmenge — Pfeilfunktionen haben nur einen Ausdruckskörper, Objekt-Literale und Template-Strings gibt es nicht. Abgeleitete Werte, die echten Code brauchen, werden in einem handler berechnet und im State gespeichert. Pavlus verlangt außerdem Disziplin, weil Reinheit eine Konvention ist, die nichts erzwingt.

## Was du gelernt hast

- Anwendungscode ist rein: `(message, state)` hinein, eine Liste von Effekten heraus. Effekte und Messages sind einfache Daten.
- Plugins führen jeden Seiteneffekt aus und machen aus der Außenwelt Messages. Der Core verbindet sie in einer Schleife.
- Ein Template wird zu `render` und `diff` kompiliert. `diff` gibt Patches zurück, indem es die State-Felder vergleicht, die jeder Knoten liest.
- Eine ganze App besteht aus einem Template, einer Komponentenklasse und einem `createApp`-Aufruf mit einem Store-Plugin und einem DOM-Plugin.
- Pavlus tauscht eine kleine Template-Sprache und eine Reinheits-Konvention gegen einfaches Testen und günstige Updates.
