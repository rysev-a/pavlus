## Der Compiler ist eine Funktion von Text zu Text

Du hast gesehen, was der Compiler generiert. Diese Seite handelt davon, wie du ihn ausführst. Im Kern ist der Compiler eine Funktion: Sie nimmt den Text eines Templates und gibt den Text eines JavaScript-Moduls zurück. Sie liest keine Dateien, fasst das DOM nicht an und braucht keinen Browser. Dieselbe Eingabe ergibt immer dieselbe Ausgabe.

Hier das kleinste Beispiel. Öffne das generierte Modul und lies es von oben.

::demo smallest open=module

Ein kompiliertes Modul hat immer dieselben Teile in derselben Reihenfolge:

1. Einen Kopfkommentar: `// Generated by pavlus from smallest.pavlus. Edit the template, not this file.`
2. Einen `import` der Runtime-Helfer, die das Modul benutzt (hier nur `toText`). Ein Template, das keinen Helfer benutzt, hat gar keinen Import.
3. Einen `import` für jedes Template, das dein Template mit einer eigenen `import`-Zeile importiert.
4. `const meta`, das die Instanznamen der eingebetteten Kinder auflistet und angibt, ob das Template ein `+outlet` hat.
5. Die beiden Funktionen `render` und `diff`, jeweils mit einem Kommentar, dass sie rein ist.
6. Zwei Exporte: die Namen `render`, `diff` und `meta` sowie einen Default-Export, ein Objekt `{ render, diff, meta }`. Dieses Objekt ist ein **view**, das, was das DOM-plugin mountet.

## compileTemplate

Die Funktion wird aus `@pavlus/frontend/compiler` exportiert. Sie nimmt den Quelltext und ein Optionsobjekt und gibt den Modultext zurück.

```ts
import {
  compileTemplate,
  DEFAULT_RUNTIME,
} from "@pavlus/frontend/compiler";

const source = "p Hello, {name}";
const code = compileTemplate(source, { filename: "src/hello.pavlus" });

console.log(DEFAULT_RUNTIME); // "@pavlus/frontend/runtime"
```

Es gibt zwei Optionen, und beide sind optional.

| Option | Default | Was sie tut |
| --- | --- | --- |
| `filename` | keiner | Wird jeder Fehlermeldung vorangestellt und für den Kopfkommentar benutzt. Im Kopf wird nur der letzte Teil des Pfads geschrieben, sodass die Ausgabe nicht davon abhängt, wo dein Projekt liegt. |
| `runtime` | `DEFAULT_RUNTIME` | Das Modul, aus dem die Helfer importiert werden. |

Die Option `runtime` ändert eine Zeile. Mit `{ runtime: "/src/runtime/helpers.ts" }` beginnt das Modul mit:

```ts
// Generated by pavlus from a template. Edit the template, not this file.
import { toText } from "/src/runtime/helpers.ts";
```

Die Helfer (`toText`, `toAttr`, `joinClasses`, `setAttr`, `sameValues`, `asView`, `diffKeyedList`, `resolveOutlet`, `childEnv`) liegen einmal in der Runtime und werden nicht in jedes Template kopiert. Der Compiler importiert **nur die Helfer, die ein Template benutzt**, nach Namen sortiert. Wäre die Zeile länger als 100 Zeichen, wird sie mit einem Namen pro Zeile geschrieben.

::demo many-helpers open=module

Sieh dir die ersten Zeilen des Moduls an. Es werden fünf Helfer benutzt, also ist der Import ein Block. Eine Schleife mit key braucht `diffKeyedList`, ein Klassen-Umschalter braucht `joinClasses` und `setAttr`, ein dynamisches Attribut braucht `toAttr`, und der Text braucht `toText`.

Wenn ein Template ein anderes Template importiert, übernimmt der Compiler den Pfad so, wie du ihn geschrieben hast, in einen `import`, und der Bundler löst ihn auf.

::demo with-child open=module

Die ersten beiden Zeilen nach dem Kopf sind `import { childEnv, toText } from ...` und `import Badge from "./badge.pavlus";`. Die zweite stammt aus deinem Template, die erste vom Compiler. Die Zeile `meta` sagt `embeds: ["badge"]`: die Instanznamen der Kinder. Weil `./badge.pavlus` selbst eine `.pavlus`-Datei ist, wird sie vom selben plugin kompiliert, wenn der Bundler sie erreicht.

## compileToView

Manchmal willst du einen funktionierenden view und keinen Text: in einem Test, in einem Skript oder auf einer Dokumentationsseite wie dieser. `compileToView` kompiliert den Quelltext und führt den Code dann aus, wobei die Runtime-Helfer als Argumente übergeben werden, und gibt den view zurück.

```ts
import { compileToView } from "@pavlus/frontend/compiler";

const view = compileToView("p Hello, {name}");
view.render({ name: "Ann" });
view.diff({ name: "Ann" }, { name: "Bob" });
```

Hat das Template `import`-Zeilen, müssen die views unter ihrem lokalen Namen übergeben werden:

```ts
const badge = compileToView("span.badge {label}");
const row = compileToView(
  `import Badge from "./badge.pavlus"
li +Badge#badge(label=role)`,
  { components: { Badge: badge } },
);
```

Ein Wert in `components` ist ein view oder ein Objekt mit einem `view`. Fehlt ein Name, bricht der Aufruf mit dieser Meldung ab:

```text
pavlus: template imports "Badge" but no view was given in { components }
```

`compileToView` baut die Funktion mit `new Function`, braucht also eine Seite, die das erlaubt. Nutze für eine Anwendung `compileTemplate` und einen Bundler, und `compileToView` für Tests und Tools.

## Das Vite-Plugin

In einer Anwendung rufst du den Compiler nicht selbst auf. Ein Vite-Plugin ruft ihn für dich für jedes Template auf, das dein Code importiert. Es wird aus `@pavlus/frontend/vite` als `pavlus()` exportiert.

```ts vite.config.ts
import { defineConfig } from "vite";
import { pavlus } from "@pavlus/frontend/vite";

export default defineConfig({
  plugins: [pavlus()],
});
```

Das plugin ist klein, und alles, was es tut, lässt sich in wenigen Zeilen sagen:

- Es führt `transform` mit `enforce: "pre"` aus, vor den anderen plugins.
- Es behandelt ein Modul, wenn der Pfad ohne seinen Query-String auf `.pavlus` endet. Alle anderen Module geben `null` zurück und bleiben unberührt. Die Option `extension` ändert das Suffix (`pavlus({ extension: ".pv" })`).
- Es überspringt die Queries `?raw`, `?url` und `?inline`, sodass `import source from "./card.pavlus?raw"` dir den Text des Templates gibt und nicht das kompilierte Modul. So lesen die Golden-Tests unten ihre Eingabe.
- Es ruft `compileTemplate(code, { filename, runtime })` auf. Der `filename` ist der vollständige Pfad der Datei, und `runtime` ist die Option, die du angegeben hast.
- Es gibt das Modul mit `map: { mappings: "" }` zurück, was "keine Source Map" bedeutet. Das ist eine Entscheidung und keine Lücke: Vite würde eine Map erfinden, die den generierten Code auf sich selbst verweist, was groß ist und nichts aussagt. Ohne Map zeigen die DevTools des Browsers das generierte `render` und `diff`, und das willst du debuggen.
- Wirft der Compiler einen Fehler, ruft es `this.error` von Vite mit der Meldung auf, sodass der Build stoppt und den Fehler mit dem Dateinamen zeigt.

Das plugin enthält keinen Code für Hot Updates, und das generierte Modul enthält kein `import.meta.hot`. Ein gespeichertes Template wird wie jedes andere Modul erneut transformiert, und Vite wendet seine übliche Regel für Module an, die keine Updates akzeptieren.

### Woher die Runtime kommt

Ein kompiliertes Modul importiert `@pavlus/frontend/runtime`, also muss das Paket installiert sein, wie für jeden anderen Import. Liegen die Helfer woanders, zum Beispiel in einem Monorepo, in dem das Paket der Quelltext ist, hast du zwei Wege. Nutze die Option `runtime` oder einen Vite-Alias. Die eigenen Tests des Frameworks benutzen einen Alias:

```ts
export default defineConfig({
  plugins: [pavlus()],
  resolve: {
    alias: {
      "@pavlus/frontend/runtime": "/path/to/src/runtime/helpers.ts",
    },
  },
});
```

### Ein Template benutzen

Ein Template ist ein Modul wie jedes andere. Importiere den Default-Export, der der view ist, und gib ihn einer Komponente.

```pavlus counter.pavlus
section.counter
  h1 {count}
  button(@click=inc) Add one
```

```ts main.ts
import {
  Component,
  createApp,
  type Effect,
  type Message,
} from "@pavlus/frontend";
import { DomPlugin } from "@pavlus/frontend/plugins/dom";
import {
  createStorePlugin,
  storeEffector as store,
} from "@pavlus/frontend/plugins/store";
import view from "./counter.pavlus";

interface State {
  count: number;
}

class Counter extends Component<State> {
  view = view;
  inc(_msg: Message, state: State): Effect[] {
    return [store.set("count", state.count + 1)];
  }
}

createApp<State>({
  app: new Counter(),
  plugins: [createStorePlugin<State>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

Das `@click=inc` des Templates ist die Nachricht `inc`. Die Methode `inc` der Komponente behandelt sie und gibt einen effect als Daten zurück. Das store-plugin ändert den State, das DOM-plugin ruft `view.diff` auf und wendet die Patches an.

### Typen für Template-Imports

TypeScript weiß nicht, was eine `.pavlus`-Datei ist. Das Paket liefert dafür eine Deklarationsdatei mit, `@pavlus/frontend/env`. Referenziere sie einmal in einer `.d.ts`-Datei, die dein `tsconfig.json` einbindet:

```ts env.d.ts
/// <reference types="vite/client" />
/// <reference types="@pavlus/frontend/env" />
```

Danach hat `import view from "./counter.pavlus"` den Typ `View`, und auch die benannten Exporte `render`, `diff` und `meta` haben Typen. Die Deklaration sagt, dass `render(state: any, ...)` und `diff(prev: any, next: any, ...)` jeden State annehmen, TypeScript prüft den State also nicht gegen das Template. Typen für `?raw`-Imports kommen aus `vite/client`.

## Fehler

Ein Template, das sich nicht kompilieren lässt, wirft einen `TemplateError`. Seine Meldung endet mit der Position, `(line 3, col 5)`, mit 1-basierten Zahlen, und das Fehlerobjekt hat außerdem die Felder `line` und `col`. Wenn du einen `filename` übergibst (das Vite-Plugin tut das immer), beginnt die Meldung mit dem Dateinamen.

Hier sind die Fehler, die dir am häufigsten begegnen. Jeder Block zeigt ein Template und die genaue Meldung, die der Compiler dafür mit dem Dateinamen `card.pavlus` zurückgibt.

Ein Tab in der Einrückung:

```pavlus-invalid
ul
	li Item
```

```text
card.pavlus: Tabs are not allowed, use spaces (line 2, col 1)
```

Eine geschweifte Klammer, die nicht geschlossen wird:

```pavlus-invalid
p Hello, {name
```

```text
card.pavlus: Unclosed { (line 1, col 8)
```

Ein Ausdruck, der nicht fertig ist oder ein Zeichen enthält, das nicht zur Ausdruckssprache gehört:

```pavlus-invalid
div
  p {total +}
```

```text
card.pavlus: Unexpected end of expression (line 2, col 13)
```

```pavlus-invalid
p {price # 2}
```

```text
card.pavlus: Unexpected character "#" (line 1, col 10)
```

Ein `else` ohne ein `if` davor. Beachte, dass `else` auch nicht auf ein `for` folgen kann:

```pavlus-invalid
div
  p one
else
  p two
```

```text
card.pavlus: `else` without matching `if` (line 3, col 1)
```

Ein Kind, das nicht importiert wurde. Die Meldung nennt dir beide Wege, es zu beheben:

```pavlus-invalid
div
  +Card#card(title=title)
```

```text
card.pavlus: "Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

Ein handler, der kein Nachrichtenname ist:

```pavlus-invalid
button(@click=1+2) Go
```

```text
card.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

Eine Zeile unter einem Element, das keine Kinder haben kann:

```pavlus-invalid
input(value=x)
  p inside
```

```text
card.pavlus: This line cannot have children (line 2, col 1)
```

Ein dynamisches Embed ohne Instanznamen, ein spätes `import`, ein Klassen-Umschalter mit einem String und `+outlet` mit Argumenten:

```text
card.pavlus: A dynamic component needs an instance name: +{expr}#name(...) (line 1, col 9)
card.pavlus: `import` lines must be at the top of the file (line 2, col 1)
card.pavlus: "class:on" needs an expression value (line 1, col 4)
card.pavlus: `+outlet` takes nothing after it (line 2, col 10)
```

In einem Vite-Build kommt die Meldung innerhalb des Build-Fehlers an. Das gibt ein Vite-8-Build, gekürzt, für ein Template mit der Zeile `  li {name` aus:

```text
Build failed with 1 error:

[plugin pavlus] /project/src/bad.pavlus
RolldownError: /project/src/bad.pavlus: Unclosed { (line 2, col 3)
```

> [!WARNING] Manche Tippfehler sind keine Fehler
> Der Compiler erkennt `if`, `else`, `for` und `+` an der Form der ganzen Zeile. Eine Zeile, die fast passt, ist ein normales Element. Ein einzelnes `if` ohne Bedingung ist das Element `<if>`. `for item of items` (mit `of` statt `in`) ist das Element `<for>` mit dem Text `item of items`. Keines von beiden ist ein Fehler, und die Seite wird ohne den Block gerendert, den du wolltest. Wenn etwas, das ein Block sein sollte, als Tag erscheint, prüfe die Zeile anhand der Syntax.

## Die Golden Files

Wie können die Autoren des Compilers ihn mit Zuversicht ändern? Die Testsuite hat zwei Ebenen.

Die erste Ebene, `output.test.ts`, prüft **Eigenschaften** der Ausgabe: Die Helfer werden importiert und nicht eingefügt, nur die benutzten Helfer werden importiert, die Variablen haben Namen, die aus dem Template stammen (`userList`, `prevUserKeys`, `liChildren`), die Kommentare sagen, welche Zeile und welche Abhängigkeiten ein Block hat, und der Code hat keine sehr langen Zeilen.

Die zweite Ebene hält **jedes Byte** fest. Im Ordner `framework/src/compiler/__fixtures__` liegen elf kleine Templates, und in `__goldens__` genau das JavaScript, das der Compiler für jedes davon erzeugen muss:

| Fixture | Was es abdeckt |
| --- | --- |
| `static` | Nichts hängt vom State ab, also ist `diff` leer. |
| `text` | Textzeilen, Interpolation, escapte geschweifte Klammern. |
| `element` | Dynamische Attribute, Klassen-Umschalter, Events mit Argumenten und Modifikatoren. |
| `names` | Schleifenvariablen, die wie JavaScript-Schlüsselwörter oder generierte Namen heißen. |
| `if` | `if`, `else if`, `else`, eine Schleife ohne key, ein zweites `if`. |
| `for` | Schleifen mit key und Index, verschachtelte Schleifen, ein `if` in einer Schleife. |
| `embed-static` | Importierte Kinder, Props, Spread, ein Embed in einer Schleife. |
| `embed-dynamic` | `+{expr}` unter einem `if`, mit Spread-Props. |
| `outlet` | Der Knoten `+outlet`. |
| `shell`, `dashboard` | Zwei echte Seiten: ein Menü mit einem langen Klassenausdruck und ein Dashboard. |

Der Golden-Test liest jedes Fixture mit `?raw` (was funktioniert, weil das plugin diese Query überspringt), kompiliert es mit `compileTemplate(source, { filename: "<name>.pavlus" })` und vergleicht das Ergebnis mit der Datei per `toMatchFileSnapshot`. Ein letzter Test prüft, dass die Fixtures zusammen jede Art von Knoten benutzen: Elemente, Text, `if` mit `else if` und `else`, `for` mit und ohne key, statische und dynamische Embeds, `+outlet`, Klassen-Umschalter und die Formen `prevent`, `stop` und mit mehreren Argumenten bei Events. Wenn du der Syntax ein neues Feature hinzufügst, schlägt dieser Test fehl, bis ein Fixture es benutzt.

Ändert eine Änderung am Compiler die Ausgabe absichtlich, führst du die Tests mit `-u` aus und liest im Review das diff von `__goldens__/`. War es ein Refactoring, muss das diff leer sein. Das ist der Sinn davon, die Bytes festzuhalten: Eine Änderung der Ausgabe kann nicht unbemerkt bleiben.

### Wie man ein Golden liest

Die Goldens sind die beste Dokumentation der Ausgabe, weil sie immer korrekt sind. Um eines zu lesen, gehe vom Template aus und suche diese Orientierungspunkte:

- Die Kommentare `// line N: <tag>` ordnen einen Block einer Zeile des Templates zu. Dieselbe Zeile erscheint in `render` und in `diff`.
- Suche in `render` die Variablen `xChildren` und `xAttrs`. Sie werden zuerst gebaut, von unten nach oben, und das Element wird zuletzt gepusht.
- Suche in `diff` den Kommentar mit `(reads: ...)`. Die nächste Zeile ist sein Guard.
- Suche `idSuffix`. Jede id ist die Nummer eines Knotens plus der Suffix, sodass du einen Knoten durch `render` und `diff` verfolgen kannst.
- Suche bei einer Schleife `diffKeyedList` und lies seine vier Funktionen.

## Einen view testen

Ein view besteht aus zwei reinen Funktionen, und ein Test für einen view ist ein normaler Test. Für die erste Art brauchst du keinen Browser.

```pavlus todos.pavlus
ul
  for todo in todos key todo.id
    li(class:done=todo.done @click=toggle(todo.id)) {todo.title}
p {todos.length} todos
```

```ts todos.test.ts
import { expect, test } from "vitest";
import view from "./todos.pavlus";

const write = { id: 1, title: "Write", done: false };

test("finishing a todo changes only its class", () => {
  const patches = view.diff(
    { todos: [write] },
    { todos: [{ ...write, done: true }] },
  );
  expect(patches).toEqual([
    { op: "attr", id: "2#1", name: "class", value: "done" },
  ]);
});

test("nothing changed, nothing to patch", () => {
  expect(view.diff({ todos: [write] }, { todos: [write] })).toEqual([]);
});
```

Diese beiden Tests laufen in reinem Node. Der Test-Runner braucht das plugin, also muss die Konfiguration von Vite oder Vitest `pavlus()` in `plugins` haben.

Für einen Test, der das DOM einschließt, hat das Paket `@pavlus/frontend/testing`. Seine Funktion `mountView(viewOrComponent, initialState, document?)` mountet den view in einem frischen Container mit dem echten DOM-plugin, ohne den Rest der Anwendung. Sie gibt den Container (`root`), das DOM-plugin, die Liste der Nachrichten, die die Events des Benutzers erzeugt haben (`messages`), und die Funktionen `set(nextState)` und `unmount()` zurück. Mounte eine Komponente und nicht nur ihren view, wenn das Template ein `+outlet` hat, weil das outlet das `routing` der Komponente braucht.

```ts todos.dom.test.ts
// @vitest-environment jsdom
import { expect, test } from "vitest";
import { mountView } from "@pavlus/frontend/testing";
import view from "./todos.pavlus";

test("the DOM follows the state, and a click sends a message", () => {
  const write = { id: 1, title: "Write", done: false };
  const check = { id: 2, title: "Test", done: false };
  const h = mountView(view, { todos: [write, check] });

  h.set({ todos: [write, { ...check, done: true }] });
  expect(h.root.querySelectorAll("li")[1].className).toBe("done");

  h.root.querySelector("li")!.click();
  expect(h.messages).toMatchObject([{ id: "toggle", payload: 1 }]);

  h.unmount();
  expect(h.root.innerHTML).toBe("");
});
```

Das Array `messages` enthält, was das DOM-plugin abgeschickt hat. Der Klick auf das erste Element hat `{ id: "toggle", payload: 1, event: { type: "click" } }` erzeugt: Die Nachrichten-id und der Payload stammen aus dem Template, und das Feld `event` fügt das plugin hinzu. `h.root.innerHTML` direkt nach `mountView` ist:

```text
<!--pavlus--><ul><!----><!----><li>Write</li><!----><!----><li>Test</li><!----><!----></ul><p>2 todos</p><!--/pavlus-->
```

So lassen sich die Marker gut sehen: Jedes Element sitzt zwischen zwei leeren Kommentaren und die Liste zwischen zwei weiteren. Die Kommentare `pavlus` und `/pavlus` begrenzen das gesamte render.

## Was du gelernt hast

- `compileTemplate(source, { filename, runtime })` gibt den Text eines ES-Moduls mit `render`, `diff`, `meta` und einem Default-view zurück. `compileToView` gibt einen funktionierenden view zurück und ist für Tests und Tools gedacht. `DEFAULT_RUNTIME` ist die Quelle der Helfer.
- Das Vite-Plugin `pavlus()` kompiliert jeden `.pavlus`-Import, überspringt `?raw`, `?url` und `?inline`, liefert absichtlich keine Source Map mit und meldet einen Template-Fehler mit Datei, Zeile und Spalte.
- `@pavlus/frontend/env` gibt `.pavlus`-Imports ihre Typen. Der State ist als `any` typisiert.
- Compiler-Fehler sind `TemplateError`s mit 1-basierten Positionen, und ein paar Tippfehler ergeben Elemente und keine Fehler.
- Golden Files halten die exakte Ausgabe von elf Fixtures fest, sodass eine Änderung des generierten Codes in einem Review immer sichtbar ist. Ein view lässt sich als zwei reine Funktionen testen oder mit `mountView` mounten.
