## The idea in one minute

A `.pavlus` file is not interpreted at run time. A **compiler** reads it once, at build time, and writes a normal JavaScript module. Your application imports that module like any other. The browser never sees the template text and never needs a template parser.

The module exports three things. Together they are called a **view**:

- `render(state)` returns the whole template for one state, as a list of plain objects. These objects are called **vnodes** (virtual nodes).
- `diff(prev, next)` returns the smallest list of DOM changes that turns the page of `prev` into the page of `next`. These changes are called **patches**.
- `meta` is a small object that says which child views and which `+outlet` the template contains.

Here is the smallest template that has anything to compute. It greets a person by name.

::demo tiny open=module

Read the result from the top. The HTML is what `render` produced. The first step shows `diff` after `name` changed from `Ann` to `Bob`: one patch, `{"op":"text","id":"1","text":"Hello, Bob"}`. The second step shows the same state twice: no patches at all. Open the module: it is about thirty lines, and every line has a reason. The rest of this page explains them.

## The stages

The compiler is a short pipeline. Each stage is a plain function that takes the output of the stage before it.

| Stage | Function | Input | Output |
| --- | --- | --- | --- |
| Parse | `parse` | template text | `TemplateAst`: imports and a tree of nodes |
| Analyze | `nodeDeps` | one node | the set of state fields the node reads |
| Generate | `generate` | the AST | JavaScript source for `meta`, `render` and `diff`, and the list of runtime helpers it uses |
| Assemble | `compileTemplate` | template text | the finished ES module as a string |

The analysis is not a separate pass over the whole tree. The code generator asks `nodeDeps` for the dependencies of each node at the moment it writes the guard for that node (and the result is cached per node). It is still a distinct stage, because its answer decides what `diff` looks like. The pages after this one take the stages in order: [parsing](page:compiler-parser), [dependency analysis](page:compiler-analysis), and the generated [render](page:compiler-render) and [diff](page:compiler-diff).

In the source, `compileTemplate(source, { filename, runtime })` does this:

1. It calls `parse(source)` and `generate(ast)`. If either throws a `TemplateError`, and you gave a `filename`, the message gets the file name in front: `app.pavlus: Unclosed { (line 1, col 8)`.
2. It writes a one-line header comment: `// Generated by pavlus from app.pavlus. Edit the template, not this file.`
3. It writes one `import` line for the runtime helpers the code uses, and one `import` line per `import` line of the template. Child views are imported by the real module system, so your bundler sees them.
4. It writes the generated code, then `export { render, diff, meta };` and `export default { render, diff, meta };`.

> [!NOTE] Two ways to compile
> `compileTemplate` returns the module as text. The Vite plugin uses it, and so does this documentation site when it shows you "the generated module". `compileToView` compiles the same code and runs it at once with `new Function`, giving you a ready view. It is meant for tests and tools. The demos on these pages use both: the module you can unfold, and a live view that produces the HTML and the patches.

## A template with nothing to change

Not every template has a `diff` worth reading. This one reads nothing from the state.

::demo static open=module

The module has no `import` line, because it uses no helper. `render` builds the same vnodes every time. `diff` has no comparisons: only the shortcut `if (prev === next) return patches;` and the final `return patches;`. The compiler saw that no node reads the state, so it wrote nothing else. The vnodes have no `id` either: an id exists only so that a patch can name a node, and nothing here is ever patched.

This is the first big idea of the compiler: **it spends code only where something can change**.

## From text to AST to code

Now a template with one dynamic attribute, one class toggle and one interpolation. We open every section the demo can show: the module, the AST and the vnodes.

::demo stages open=module,ast,vnodes

Go through the three sections in the order the compiler worked.

**The AST** has two nodes: the element `a` (node `#0`) and its text (node `#1`). Beside each node is `reads:`, the set of state fields the node needs. The element reads `active`, `title` and `url`, because its attributes and its children read them. The text reads only `title`. The numbers `#0` and `#1` are **node ids** (`nid`). The parser hands them out in document order.

**The module** has `render` first. It writes the children before the element, so the text is built first and pushed into `aChildren`. Then it builds the attribute object `aAttrs`, one line per dynamic attribute, and pushes the element. Then comes `diff`. For the element it writes a guard, `if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title)`. Inside the guard, each attribute is computed for `prev` and for `next`, and a patch is pushed only if the two values differ. For the text there is a second, smaller guard on `title` alone.

**The vnodes** are what `render` returned. Both the element and the text carry an `id` (`"0"` and `"1"`), the node id as a string. They have ids because `diff` can address them. The patch in the step, `{"op":"attr","id":"0","name":"class","value":"link active"}`, uses the id of the element. Only the `class` is patched: the `href` and the text did not change.

## What you get when you import a .pavlus file

In a Vite project, the `pavlus()` plugin compiles every file that ends with `.pavlus`. The plugin skips an import that ends with `?raw`, `?url` or `?inline`, because those ask for the file itself. For any other import you get the module the compiler wrote.

```ts main.ts
import view from "./counter.pavlus";
import { render, diff, meta } from "./counter.pavlus";

const vnodes = render({ count: 1 });
const patches = diff({ count: 1 }, { count: 2 });
```

The default export and the three named exports are the same objects. The default export is the **view**, and that is what other code expects: the DOM plugin takes a view to mount, and an embedded child (`+Badge#status`) is a view. Both functions are **pure**. They read their arguments and nothing else, change nothing, and give the same answer for the same input. That is why they can run on a server, in a test, or in the browser, and why the demos on this site can run them for you.

A view has these parameters, from the generated code:

```ts
function render(state, idSuffix = "", messagePrefix = "", env)
function diff(prev, next, idSuffix = "", messagePrefix = "", env)
```

A top-level view uses the defaults. The last three parameters exist for **embedding**. When a template contains `+Badge#status`, the parent calls `Badge.render` with a longer `idSuffix` (`"/3"`, so the child's node ids cannot collide with the parent's), a longer `messagePrefix` (`"status."`, so the child's messages are named by its instance), and an `env`, which is the component object that owns the view. Application code never passes them.

## The contract between render, diff and the DOM plugin

The DOM plugin is the only code of the framework that touches the DOM. It relies on three promises that the generated code keeps. They are the reason `render` and `diff` are generated together, from one AST.

1. **The first render makes the map.** When the plugin mounts a view, it calls `render(state)` once and builds real DOM from the vnodes. For every vnode that has an `id`, it remembers the DOM node under that id.
2. **A patch only names ids that render produced.** A patch such as `{ op: "text", id: "1", text: "Hello, Bob" }` is applied as "find the node stored under `1` and set its text". If the id were unknown the plugin would throw `unknown node id`. The compiler makes sure that every node that `diff` can patch has an `id` in `render`.
3. **The next states are diffed, not re-rendered.** When the state changes, the plugin calls `diff(oldState, newState)` and applies the patches in order. A new piece of the page (a new `if` branch, a new list item) arrives inside an `insert` patch as ready-made vnodes, and the plugin registers their ids too.

So the vnodes are not just a picture of the page. They are a picture plus a table of contents. The next demo makes this concrete. A `button` has an event; look at which parts of the vnode carry an id and at the two patches of the step.

::demo events open=vnodes

The `button` has an `id` because its event has an argument that can change (`add(step)`). The patch `{"op":"handler",...}` gives the plugin the new message, so the click will send `{ id: "add", payload: 5 }`. The plugin never removes and re-adds a listener: it keeps one listener per element and event type, and swaps the message that listener reads.

> [!WARNING] The compiler trusts identity
> `diff` compares values with `!==`. A new object with the same content counts as a change. The same object with new content, changed in place, counts as no change. Always give the next state new objects for the parts that changed (spread, `map`, `filter`) and never edit the previous state.

## Why compile at build time

You could write a library that reads the template text at run time and walks it. That is how many template engines work. The pavlus compiler does the work earlier, and the benefits are concrete.

- **`diff` is specific to your template.** The generated `diff` contains the exact comparisons your template needs and no others. There is no generic tree walk and no comparison of two full vnode trees. In the `static` demo it contains none at all.
- **Nothing to ship but your code.** The browser receives plain functions plus a small set of helpers. It receives no parser, no expression interpreter and no template strings.
- **Errors arrive at build time.** A typo in a template stops the build with a file name, a line and a column. It does not wait for a user to open the page.
- **The output is readable.** The generated code has comments with the source line of every node (`// line 1: <a.link>`), names taken from your tags (`aChildren`, `liAttrs`), and one statement per idea. You can read it when something surprises you.
- **Pure functions are easy to use everywhere.** Server rendering calls `view.render(state)` and turns the vnodes into HTML. A unit test calls `diff(a, b)` and checks the patches. No browser is involved.

The price is that a template can only use a small, pure subset of JavaScript in its expressions (see [expressions](page:syntax-expressions)). The compiler must understand every expression to know what it reads. That limit is deliberate.

## The runtime helpers

Look at the first line of the `stages` module: `import { joinClasses, setAttr, toAttr, toText } from "@pavlus/frontend/runtime";`. The generated code does not contain its own copy of these small functions. They live once, in `runtime/helpers.ts`, and the compiler imports exactly the ones a template uses. A template with no dynamic parts imports nothing (see `static`). The import path is the default of the `runtime` option, and you can change it.

Each helper exists to remove one decision from the generated code, so the generated code stays short and every template treats the edge cases the same way.

| Helper | What it does | Used for |
| --- | --- | --- |
| `toText(value)` | `null`, `undefined` and `false` become an empty string, everything else `String(value)` | `{expr}` in text and in strings |
| `toAttr(value)` | `null`, `undefined`, `false` give `null` (no attribute), `true` gives `""`, anything else its string | `attr=expr` |
| `joinClasses(list)` | joins the true-ish names with spaces, gives `null` when nothing is left | the `class` attribute |
| `setAttr(attrs, name, value)` | sets the attribute unless the value is `null` | all dynamic attributes in `render` |
| `sameValues(a, b)` | equal values, or arrays with equal items | event payloads with several arguments |
| `diffKeyedList(...)` | works out removes, inserts and moves for a keyed list | `for ... key` in `diff` |
| `asView(value)` | turns a component or a view in the state into its view, or `null` | `+{expr}#name` embeds |
| `childEnv`, `resolveOutlet` | find the component behind an embed, and the routed child of an `+outlet` | embeds and outlets |

The next demo uses the attribute helpers. Notice how `null`, `false` and `true` behave.

::demo helpers open=module

`checked=done` with `done: true` becomes `checked=""`, which is how HTML writes a boolean attribute. `disabled=locked` with `locked: false` is not written at all. `{note}` with `note: null` is an empty text, not the word `null`. In the step, `done` goes from `true` to `false`, so `checked` disappears (`rmAttr`) and so does the class (`rmAttr`): `joinClasses` returned `null`, because no class name was left.

> [!TIP] You never import helpers yourself
> The comment on the first line of `helpers.ts` says it plainly: application code does not need them. If you ever want to read one, they are short. The tests in `runtime/helpers.test.ts` document their edge cases.

## Child views and the module graph

A template can embed another template. The `import` line becomes a real ES import, and the embed becomes a call of the child's `render` and `diff`.

::demo embed open=module

Three things to see in the module. The line `import Badge from "./badge.pavlus";` comes straight from the template. The value `meta` says `embeds: ["status"]`: the instance names of the children. And the child's text node has the id `1/3`: its own id `1`, followed by the suffix `/3` that the parent added (`3` is the parent's node id of the embed). In the step, the parent's `diff` calls `Badge.diff` with the old and new props, and the answer is one patch for the child's text. The parent did not need to know what is inside `Badge`.

## A bigger template, end to end

Finally, a small to-do list with a title, a conditional and a keyed loop. It uses everything the pipeline knows: static nodes, dynamic text, a class toggle, an event, an `if`/`else`, and a `for`. Open the AST first and read the `reads:` column, then look at the two steps.

::demo todo open=ast

A few things to find in it.

- The `else` branch (`p.empty`) reads nothing, so its nodes have no ids and no code in `diff`.
- The `li` reads `item`, a loop variable. The `for` node reads only `items`, because the compiler removes loop variables from the dependencies of the loop (see [dependency analysis](page:compiler-analysis)).
- Step one marks an item done. The result is a single `attr` patch on the id `6#1`: node `6`, item key `1`. The title, the footer and the other item produce no patches.
- Step two empties the list. The `if` changes branch, so the compiler's answer is `clear` everything between the markers `3s` and `3e`, then `insert` the new branch, plus a `text` patch for the footer.

## What you learned

- The compiler turns a template into a module with `render`, `diff` and `meta`, once, at build time. It can do this because template expressions are a small, pure language.
- The stages are parse, analyze, generate and assemble. The AST says what each node reads, and the generated `diff` only checks what a node reads.
- A view is a pair of pure functions. The DOM plugin renders once, remembers nodes by id, and then applies the patches that `diff` returns.
- Runtime helpers are imported, never copied. A template imports only the ones it uses.
