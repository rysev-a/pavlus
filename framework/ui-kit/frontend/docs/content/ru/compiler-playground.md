## Попробуйте

Ниже два текстовых поля: слева шаблон, справа state, записанный как JSON. Кнопка **Скомпилировать и запустить** отправляет оба настоящему компилятору, в вашем браузере, и показывает результат под полями. На сервер ничего не отправляется. **Сбросить** возвращает пример, с которого вы начали.

::playground

В первый раз нажмите **Скомпилировать и запустить**, ничего не меняя. В начальном примере есть заголовок, предложение с условием внутри текста, список с key и переключателем класса и `if` с `else`. Затем читайте дальше, чтобы узнать, что означают разделы результата, и попробуйте эксперименты ниже.

## Что вы видите после «Скомпилировать и запустить»

В результате те же разделы, что и в демо на других страницах этого раздела:

- **Шаблон** и **Состояние**: то, что вы скомпилировали, и JSON, который был разобран.
- **Результат (HTML от render(state))**: HTML, который `render` вернул для вашего state. Маркеры здесь не показаны.
- **Сгенерированный модуль**: полный текст модуля, который вернул `compileTemplate`, по умолчанию раскрыт.
- **AST и что читает каждый узел**: одна строка на узел, с корневыми именами state, от которых он зависит. Это набор зависимостей, из которого делаются guard в `diff`. По умолчанию раскрыт.
- **vnodes, которые возвращает render(state)**: сырые данные, свёрнуты. Раскройте их, чтобы увидеть id и маркеры.

Если в шаблоне есть ошибка, вы увидите **Компилятор остановился:** и сообщение с именем файла `playground.pavlus`, строкой и колонкой. Если state — не корректный JSON, вы увидите **Состояние — не корректный JSON:** и сообщение парсера.

> [!NOTE] Чего песочница не умеет
> Она выполняет `render` один раз, для state, который вы ей даёте. Второго state нет, поэтому здесь нет списка patch: чтобы увидеть patches, используйте демо на страницах до этой или вызовите `diff` в тесте, как показано на [странице об инструментах](page:compiler-tooling). Вы по-прежнему можете читать функцию `diff` в сгенерированном модуле, и именно это делают эксперименты ниже. Imports, embed `+{expr}` и `+outlet` требуют view и компонентов, которые JSON передать не может, поэтому здесь они останавливаются с ошибкой.

## Семь экспериментов

Для каждого эксперимента вставьте шаблон в левое поле, state в правое поле и нажмите **Скомпилировать и запустить**.

### 1. Шаблон, который ничего не читает

```pavlus
p Hello, world
```

```json
{}
```

Откройте сгенерированный модуль и перейдите к `diff`. В нём только `if (prev === next) return patches;` и `return patches;`. Строки import нет, потому что хелперы не нужны, а у vnodes нет полей `id`. Ничто в этом шаблоне не может измениться, поэтому компилятор ничего для него не написал.

### 2. Чтение одного поля

```pavlus
p Hello, {name}
```

```json
{ "name": "Ann", "theme": "light" }
```

AST говорит *reads: name*, а guard в `diff` сравнивает `prev.name !== next.name`. Поле `theme` есть в state и ни разу не упоминается в модуле. Теперь измените шаблон на `p Hello, {name}, theme {theme}` и скомпилируйте снова: guard вырастет на одно сравнение, и текст тоже.

### 3. Родитель и дочерний узел с одинаковыми зависимостями

```pavlus
p(title=text) {text}
```

```json
{ "text": "Hi" }
```

Найдите guard `if (prev.text !== next.text)`. Внутри вы видите атрибут `title` и ещё текст. У комментария `// line 1: text` нет собственного `if`, потому что guard абзаца уже покрывает его. Измените атрибут на `title=other` и скомпилируйте снова: теперь у текста есть собственный guard.

### 4. Индекс ветки

```pavlus
if n > 1
  p many
else if n === 1
  p one
else
  p none
```

```json
{ "n": 1 }
```

Результат — `<p>one</p>`. В модуле найдите `nextBranch`: цепочку условий, заканчивающуюся номером ветки `else`. Удалите `else` и его строку и скомпилируйте снова: цепочка теперь заканчивается на `-1`, значении «ничего не показано». Откройте vnodes: `if` обёрнут в два узла-маркера с id `0s` и `0e`.

### 5. Циклы с key и без

```pavlus
ul
  for item in items key item.id
    li {item.name}
```

```json
{ "items": [{ "id": 7, "name": "Ann" }, { "id": 9, "name": "Bob" }] }
```

Найдите строку, начинающуюся с `const prevItemKeys`. Она сопоставляет каждому элементу `String((item)?.id)`. Теперь удалите ` key item.id` из шаблона и скомпилируйте снова: строка становится `String(itemIndex)`. Посмотрите на vnodes в обеих версиях: маркеры элементов названы по key, `1[#7` и `1[#9` в первой, `1[#0` и `1[#1` во второй. Именно эти имена используют patches `remove` и `move`.

### 6. Событие с аргументами

```pavlus
button(class:on=on @click=pick(id, kind)) Pick
```

```json
{ "on": true, "id": 1, "kind": "a" }
```

У vnode кнопки есть поле `events` с `"click": { "id": "pick", "payload": [1, "a"] }`: handler — это данные. В `diff` два аргумента сравниваются через `sameValues`, а класс пересобирается через `joinClasses`. Измените `@click=pick(id, kind)` на `@click.prevent=pick(id, kind)` и найдите `prevent: true`. Измените на `@click=pick`, и handler исчезнет из `diff`, потому что handler без аргументов не может измениться. У кнопки остаётся `id`, потому что её класс всё ещё может измениться.

### 7. Ошибки

Намеренно сломайте шаблон. Уберите закрывающую фигурную скобку:

```pavlus-invalid
p Hello, {name
```

Результат заменяется сообщением `playground.pavlus: Unclosed { (line 1, col 8)`. Верните скобку и теперь напишите строку с `if` без условия:

```pavlus
if
  p one
```

Это не ошибка. Результат — `<if><p>one</p></if>`, элемент с именем `if`. Это напоминание, что лучший способ узнать, что понял компилятор, — посмотреть на результат.

## На что смотреть в модуле

Когда вы открываете сгенерированный модуль любого шаблона, проходите по нему в таком порядке:

1. **Строка import** говорит, какие хелперы нужны шаблону. Более длинная строка — больше возможностей.
2. **`meta`** перечисляет встроенные (embed) дочерние компоненты и говорит, есть ли outlet.
3. В **`render`** следуйте комментариям `// line N: ...`. Каждый из них — строка вашего шаблона. Переменные названы по ней: `liChildren` — дочерние узлы `li`, `userList` — список из `for user in ...`.
4. В **`render`** посмотрите, у каких узлов есть `id`. Он есть только у узлов, которые можно патчить.
5. В **`diff`** найдите комментарии `(reads: ...)`. Строка под каждым из них — guard.
6. В **`diff`** найдите вызовы `patches.push`. Каждый из них — одна из восьми операций patch, а его поля — то, что получает plugin для DOM.
7. Посмотрите на **`idSuffix`** и **`messagePrefix`**. Они есть в каждом id и каждом message, поэтому шаблон можно использовать внутри цикла или внутри другого шаблона.

## Что вы узнали

- Песочница запускает `compileTemplate` и `render` в вашем браузере. Она показывает HTML, модуль и набор зависимостей каждого узла, а списка patch в ней нет.
- Менять одну вещь за раз и сравнивать модуль до и после — самый быстрый способ изучить компилятор.
- Шаблон, который ничего не читает, получает пустой `diff`; узел, разделяющий зависимости с родителем, разделяет его guard; key меняет то, как называются элементы.
- Опечатка всё равно может скомпилироваться. Читайте результат, а не только отсутствие ошибки.
