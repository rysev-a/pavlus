## Что делает парсер

Парсер — это первая стадия компилятора. Он берёт текст шаблона и возвращает **дерево**, AST (abstract syntax tree, абстрактное синтаксическое дерево). Он ничего не выполняет, не знает вашего state и не пишет JavaScript. Он отвечает только на вопрос «что говорит этот текст?» и падает с понятным сообщением, когда текст не говорит ничего разумного.

Функция называется `parse(source)`, а результат имеет такую форму:

```ts
interface TemplateAst {
  imports: { local: string; from: string }[];
  nodes: Node[];
}
```

`imports` — это строки `import` в начале файла. `nodes` — узлы верхнего уровня шаблона. Узел бывает одного из шести типов: `element`, `text`, `if`, `for`, `embed` и `outlet`. Всё ниже верхнего уровня висит под `element`, веткой `if` или `for`.

Самый маленький интересный шаблон — один элемент с одной интерполяцией. Демо показывает его AST в формате, который используется на этом сайте (одна строка на узел, с id узла и тем, что он читает).

::demo ids-small open=ast

Здесь два узла: элемент `p` с id узла `#0` и текстовый узел `#1` внутри него. Настоящий объект за этим листингом выглядит так (результат парсера, отформатированный для чтения):

```json
{
  "imports": [],
  "nodes": [
    {
      "type": "element",
      "nid": 0,
      "tag": "p",
      "classes": [],
      "toggles": [],
      "attrs": [],
      "events": [],
      "children": [
        {
          "type": "text",
          "nid": 1,
          "line": 1,
          "parts": ["Hello, ", { "k": "id", "name": "name" }]
        }
      ],
      "pos": { "line": 1, "col": 1 }
    }
  ]
}
```

Стоит держать в голове две детали. Текстовый узел — это список **частей**: часть — это либо обычная строка, либо объект выражения (`k` — вид выражения). А встроенный текст `p Hello, {name}` — это не свойство элемента: парсер превращает его в настоящий дочерний узел. Дальше компилятор видит только дерево узлов.

## Строки и отступы

Парсер работает построчно. Сначала он подготавливает строки:

1. Разбивает исходник по переводам строки и пропускает пустые строки.
2. Символ табуляции в отступе — это ошибка: `Tabs are not allowed, use spaces`.
3. Строка, начинающаяся с `//`, отбрасывается. В остальных строках завершающий `// comment` отрезается, но только если `//` идёт после пробела и находится вне кавычек, круглых и фигурных скобок. Поэтому `href="http://example.com"` безопасен.
4. Каждая оставшаяся строка запоминает свой номер, свой отступ (число ведущих пробелов) и свой обрезанный текст.

Затем он строит дерево со **стеком открытых родителей**. Для каждой строки парсер убирает из стека каждого родителя, отступ которого не меньше отступа строки. То, что остаётся наверху, — родитель строки. Строка добавляется в дочерние узлы этого родителя, а потом сама кладётся в стек.

::demo indent open=ast

В этом шаблоне у `li Two` есть дочерний `b`, потому что `b bold` имеет больший отступ, чем `li Two`. У строки `p After` отступ как у `ul`, поэтому всё вплоть до `li Two` и `b bold` снимается со стека, и `p` становится следующим узлом верхнего уровня.

Два правила не дают дереву лгать.

- **У всех дочерних узлов одного родителя должен быть один и тот же отступ.** Первый дочерний узел задаёт отступ, и любой следующий соседний узел с другим отступом даёт `Inconsistent indentation`. Сколько пробелов использовать — решать вам (по соглашению два); насколько больше, чем у родителя, не фиксировано. Важно, чтобы соседние узлы были согласны.
- **Некоторые строки — листья.** Void-элемент (`br`, `img`, `input` и остальные void-теги HTML), текстовая строка, embed и outlet не могут иметь дочерних узлов. Дочерняя строка под ними даёт `This line cannot have children`.

```pavlus-invalid bad-indent.pavlus
div
  p one
    span child of one
   p two
```

```text
bad-indent.pavlus: Inconsistent indentation (line 4, col 1)
```

Парсер читает строку 4 (`   p two`, три пробела). Её родитель — `div`, у дочерних узлов которого отступ 2, поэтому строка отвергается. Ошибка всегда указывает на колонку 1, потому что проблема в отступе целиком.

## Что это за строка?

Когда отступы определены, парсер смотрит на начало строки и решает, что это. Проверки идут в таком порядке, и выигрывает первое совпадение.

| Строка начинается с | Это | Узел |
| --- | --- | --- |
| `import Name from "path"` | import (только в начале файла) | элемент `imports` |
| `if expr` | условие | `IfNode` |
| `else if expr` или `else` | следующая ветка предыдущего `if` | новая ветка в этом `IfNode` |
| `for item in list` | цикл | `ForNode` |
| символ вертикальной черты и пробел | текстовая строка | `TextNode` |
| `{` | текстовая строка, начинающаяся с выражения | `TextNode` |
| `+outlet` | дочерний компонент маршрута | `OutletNode` |
| `+` | дочернее view | `EmbedNode` |
| всё остальное | элемент | `ElementNode` |

Завершающее двоеточие в `if x:` и `for a in b:` необязательно и игнорируется. `else` должен идти за `if` или `else if` на том же уровне; иначе вы получите ``` `else` without matching `if` ```.

## Элементы

Строка элемента имеет такую форму: необязательный тег, любое число `.class` и `#id`, необязательные `(attributes)` и затем необязательный встроенный текст. Тег по умолчанию — `div`. Разберём строку, которая использует большинство частей.

::demo selector-attrs open=ast

AST показывает только зависимости, поэтому вот настоящий узел, с обрезанными длинными частями:

```json
{
  "type": "element",
  "nid": 0,
  "tag": "a",
  "classes": ["btn"],
  "toggles": [{ "name": "on", "test": { "k": "id", "name": "open" } }],
  "attrs": [
    { "name": "id", "value": ["go"] },
    { "name": "href", "value": [{ "k": "id", "name": "url" }] },
    { "name": "disabled", "value": null }
  ],
  "events": [
    {
      "name": "click",
      "msg": "save",
      "args": [{ "k": "id", "name": "id" }, { "k": "lit", "value": 2 }],
      "prevent": true,
      "stop": false
    }
  ],
  "children": [{ "type": "text", "nid": 1, "line": 1, "parts": ["Go"] }],
  "pos": { "line": 1, "col": 1 }
}
```

Каждая часть строки попадает в своё поле:

- `.btn` попадает в `classes`. `#go` сохраняется как обычный атрибут с именем `id` (он добавляется первым, перед атрибутами в круглых скобках).
- `class:on=open` попадает в `toggles`: имя класса и условие. Это не атрибут.
- `@click.prevent=save(id, 2)` попадает в `events`. Часть после `@` — имя DOM-события, с модификаторами (`prevent`, `stop`), превращёнными в флаги. Выражение должно быть id message, например `save`, `users.remove`, или его вызовом; его аргументы — выражения. Всё остальное — ошибка: `Event handler must be a message id like `save` or `remove(item)``.
- `href=url` — это атрибут, значение которого — список из одного выражения. У `disabled` без значения `value: null`: булев атрибут.

Значение атрибута — всегда список частей, как и у текстового узла. Значение в кавычках без фигурных скобок, такое как `"go"`, — это список из одной строки. Так компилятор отличает статический атрибут (только строки) от динамического (в нём есть выражение). Это различие потом многое определяет.

### Три вида значения атрибута

Значение атрибута можно записать тремя способами, и парсер читает каждый по-своему.

- **В кавычках**: `title="Open {name}"`. Текст между кавычками делится на строки и `{выражения}`, точно как текстовая строка.
- **В фигурных скобках**: `hidden={count === 0}`. Всё между фигурными скобками — одно выражение, поэтому в нём могут быть пробелы.
- **Голое**: `href=url`. Значение заканчивается на первом пробеле, запятой или закрывающей `)`, которые не находятся внутри скобок или кавычек. Оно разбирается как одно выражение.

Именно в голой форме случается самая частая первая ошибка. Выражению с пробелами нужны фигурные скобки:

```pavlus-invalid bare.pavlus
ul
  for link in links
    a(class:current=link.href === page) {link.label}
```

```text
bare.pavlus: Unexpected "=" in attributes (line 3, col 31)
```

Голое значение `link.href` закончилось на пробеле, и тогда парсер встретил `===` там, где ожидал имя атрибута. Исправление — фигурные скобки: `class:current={link.href === page}`.

## Текстовые строки, склейка и экранирование

Строка, начинающаяся с `|`, — это текстовый узел. Парсер убирает вертикальную черту и один пробел после неё. В текстовой строке могут быть выражения в фигурных скобках, а обратный слэш перед скобкой оставляет её буквальным символом.

::demo escapes open=ast

Строка с комментарием исчезла, и завершающий комментарий после `Home` тоже, хотя URL в кавычках сохранил свой `//`. В абзаце `\{` и `\}` стали обычными скобками, а `{n}` стало выражением.

Когда два текстовых узла идут друг за другом, парсер ставит перевод строки перед вторым. В HTML перевод строки между словами показывается как пробел, так что две строки читаются как один абзац, как в языке шаблонов pug.

::demo text-join open=ast

У второго текстового узла части `"\n"`, `"two "` и выражение `x`. Перевод строки виден в HTML: `one` и `two 2` находятся на разных строках исходника. То же правило склеивает встроенный текст элемента (`p Hello`) со строкой `|` под ним.

## Условия и циклы

Строка `if` начинает `IfNode`. У узла есть список `branches`. У каждой ветки есть `test` (выражение или `null` для `else`) и её `children`. Строки `else if` и `else` не создают собственных узлов: они добавляют ветку в узел `if` прямо перед ними.

::demo if-chain open=ast

AST выводит один узел на каждый `if`, а под ним группы `then`, `else if` и `else`. Id узлов показывают то, что стоит запомнить: `if` — это `#0`, три элемента `p` и их тексты — это `#1`–`#6`, а у самих веток id нет. Ветка — это не узел.

Настоящие поля узла, без дочерних узлов:

```json
{
  "type": "if",
  "nid": 0,
  "line": 1,
  "branches": [
    { "test": { "k": "binary", "op": "===", "left": { "k": "id", "name": "status" }, "right": { "k": "lit", "value": "loading" } }, "children": [] },
    { "test": { "k": "binary", "op": "===", "left": { "k": "id", "name": "status" }, "right": { "k": "lit", "value": "error" } }, "children": [] },
    { "test": null, "children": [] }
  ]
}
```

У строки `for` больше частей: имя элемента, необязательное имя индекса, выражение списка и необязательное выражение `key`.

::demo for-index open=ast

```json
{
  "type": "for",
  "nid": 0,
  "line": 1,
  "item": "u",
  "index": "i",
  "of": { "k": "id", "name": "users" },
  "key": { "k": "member", "obj": { "k": "id", "name": "u" }, "prop": "id" },
  "children": []
}
```

Парсер разделяет `users key u.id` по слову `key`. Key — это то, чем цикл различает элементы, когда список меняется; без него key служит позиция в списке. Имена `u` и `i` видны только внутри цикла. Следующая страница, [анализ зависимостей](page:compiler-analysis), показывает, как это использует компилятор.

## Дочерние view и outlet

Строка `import` даёт имя другому шаблону. Строка, начинающаяся с `+`, размещает его. Имя перед `#` — это **имя экземпляра**: оно служит префиксом message дочернего компонента и является ключом его state.

::demo embeds open=ast

```json
{
  "type": "embed",
  "nid": 1,
  "component": "Badge",
  "dynamic": null,
  "name": "first",
  "props": [
    { "name": "label", "value": ["Hi ", { "k": "id", "name": "name" }] },
    { "name": "strong", "value": null }
  ],
  "pos": { "line": 4, "col": 3 }
}
```

AST показывает два embed без их props, но зависимости показывают разницу: `+Badge#first` читает `name`, а `+Badge#second(...extra)` читает `extra`, потому что элемент spread (`{ "spread": expr }`) — тоже prop. Prop без значения (`strong`) означает `true`.

Парсер проверяет эти правила, потому что компилятор не может их обойти:

- Строки `import` разрешены только в начале файла, с отступом 0, перед любым узлом.
- Имя импорта должно начинаться с заглавной буквы и не должно быть одним из `String`, `Array`, `Map`, `Set` или `Error`, которые использует сам сгенерированный код.
- Для `+Name` нужен соответствующий import: `"Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state`.
- У динамического embed, `+{expr}`, нет имени, из которого можно вывести имя экземпляра, поэтому оно нужно явно: `+{view}#page`.
- После `+outlet` ничего не пишется. Он становится `OutletNode` только с `nid` и `line`.

## Выражения

Каждое `{...}`, каждое значение атрибута в фигурных скобках или голое и каждое условие попадает во второй, отдельный парсер в `expr.ts`. Он намеренно обрабатывает небольшое подмножество JavaScript. Шагов три: разбить текст на токены (числа, строки, имена и знаки препинания), затем подняться по уровням приоритета, затем проверить, что ничего не осталось.

Результат — небольшое дерево. У каждого узла есть поле `k` с его видом:

| `k` | Поля | Записывается как |
| --- | --- | --- |
| `lit` | `value` | `1`, `"text"`, `true`, `false`, `null`, `undefined` |
| `id` | `name` | `count` |
| `member` | `obj`, `prop` | `user.name` и `user?.name` |
| `index` | `obj`, `index` | `list[0]` |
| `call` | `callee`, `args` | `format(price, "usd")` |
| `unary` | `op`, `arg` | `!done`, `-n`, `+n` |
| `binary` | `op`, `left`, `right` | `a + b`, `a === b`, `x ?? y` |
| `cond` | `test`, `then`, `else` | `ok ? "yes" : "no"` |
| `array` | `items` | `[1, x]` |

Бинарные операторы и их приоритет, от самого слабого к самому сильному: `??`, затем `||`, затем `&&`, затем операторы равенства (`==`, `!=`, `===`, `!==`), затем сравнения (`<`, `>`, `<=`, `>=`), затем `+` и `-`, затем `*`, `/` и `%`. Тернарный `? :` слабее всех них, а унарные операторы связывают сильнее. Круглые скобки группируют как обычно. Так что `a + b * 2` — это `a + (b * 2)`.

::demo expressions open=ast

AST выводит каждое выражение обратно из его дерева, с добавленными круглыми скобками в `{a + (b * 2)}`: это дерево, а не ваш текст. Также обратите внимание, что `user?.name` выводится как `user.name`. Парсер считает `.` и `?.` одним и тем же, потому что сгенерированный код всё равно читает каждое поле через `?.`. Шаблон не может выбросить «cannot read properties of undefined».

Вот несколько настоящих деревьев. Текст слева — выражение, JSON — то, что возвращает `parseExpr`:

```json
{ "k": "binary", "op": "+",
  "left": { "k": "id", "name": "a" },
  "right": { "k": "binary", "op": "*", "left": { "k": "id", "name": "b" }, "right": { "k": "lit", "value": 2 } } }
```

```json
{ "k": "cond",
  "test": { "k": "unary", "op": "!", "arg": { "k": "id", "name": "ok" } },
  "then": { "k": "id", "name": "n" },
  "else": { "k": "unary", "op": "-", "arg": { "k": "lit", "value": 1 } } }
```

Первое — это `a + b * 2`, второе — `!ok ? n : -1`.

> [!NOTE] Чего выражения не умеют
> Нет присваивания, нет шаблонных строк, нет литералов объектов, нет `typeof`, нет `new` (стрелочные функции есть, но только с телом-выражением). Шаблон читает state, он его не меняет. Каждое из этого даёт понятную ошибку во время сборки, например `{x = 1}` даёт `Unexpected character "="`, а "{`a`}" даёт ``Unexpected character "`"``. Изменения происходят через отправку message из события.

## Id узлов

Каждый узел получает число, свой **nid**, когда парсер его создаёт. Счётчик начинается с 0 для каждого шаблона и растёт на единицу в порядке документа: родитель раньше своих дочерних узлов, узел раньше узлов под ним. Встроенный текст элемента получает следующее число сразу после элемента.

Imports и ветки числа не получают. Ветки — часть узла `if`, а imports не входят в дерево.

::demo tree open=ast

Прочитайте числа в листинге. `section` — это `#0`, затем `h2` — `#1`, а его текст `#2`. `if` — это `#3`, и он занимает id с `#4` по `#9` для всего внутри двух своих веток. После `if` идёт `footer` как `#10`, а его текст как `#11`. Это обычный порядок обхода в глубину.

Эти числа важны для остальной части компилятора. Генератор кода записывает их в строки, которые становятся id в vnodes (`"11"` для текста подвала) и в patches. В списке id узла — это его nid, затем `#` и key элемента (`"7#1"`), а id узла дочернего view дополняется `/` и nid embed (`"1/3"`). У двух узлов одного шаблона никогда не может быть одинаковых id, потому что их nid различаются, а две копии узла в списке различаются по key.

> [!TIP] Id — это не стабильные имена
> Не сохраняйте nid и не пишите его в собственном коде. Добавьте строку в начало шаблона, и каждое число ниже сдвинется на единицу. Числа — это внутреннее соглашение между `render` и `diff` одного и того же скомпилированного модуля.

## Позиции и ошибки

Парсер хранит позиции в исходнике там, где может быть сообщена ошибка. У элемента и embed есть `pos` с `line` и `col`, отсчитываемыми с 1. У других узлов есть `line`. Ошибки несут оба числа и используют одно и то же соглашение на каждой стадии.

```ts
class TemplateError extends Error {
  readonly line: number;
  readonly col: number;
}
```

Сообщение заканчивается позицией в скобках, например `Unclosed { (line 1, col 8)`. Два числа также доступны как `error.line` и `error.col`, так что инструмент, например редактор, может подчеркнуть точное место. `compileTemplate` ставит перед сообщением имя файла, если знает его, и именно его вы видите в логе сборки.

Колонка ошибки выражения точна: парсер передаёт парсеру выражений позицию первого символа выражения, а тот добавляет смещение токена. Одна неточность, которую нужно знать: для `Unclosed {` в тексте колонка считается от начала текста после тега, а не от начала строки. В первом примере ниже `{` стоит в колонке 10 строки, а сообщение говорит 8. Несколько настоящих сообщений, полученных при компиляции плохих шаблонов:

```pavlus-invalid unclosed.pavlus
p Hello, {user.name
```

```text
unclosed.pavlus: Unclosed { (line 1, col 8)
```

```pavlus-invalid expression.pavlus
p Total: {price *}
```

```text
expression.pavlus: Unexpected end of expression (line 1, col 18)
```

```pavlus-invalid branch.pavlus
p one
else
  p two
```

```text
branch.pavlus: `else` without matching `if` (line 2, col 1)
```

```pavlus-invalid event.pavlus
button(@click=a+b) Save
```

```text
event.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

Каждая ошибка останавливает разбор на первой проблеме. Парсер не пытается продолжать, так что исправьте первое сообщение и компилируйте снова.

> [!WARNING] Кавычки определяют, что такое значение
> `class="x"` — это текст `x`. `class=x` — это поле `x` из state. Оба варианта допустимы, поэтому ни один не является ошибкой. Если страница ничего не показывает там, где вы ждёте класс, сначала проверьте кавычки.

## Один AST, три читателя

Теперь вы видели всё, что производит парсер. Это простое дерево из простых объектов без методов, и три следующие стадии читают одно и то же дерево: анализ читает его, чтобы вычислить, что читает каждый узел, генерация `render` читает его, чтобы писать vnodes, а генерация `diff` читает его, чтобы писать сравнения. Поскольку стадии делят одно дерево, они не могут разойтись во мнении о том, что значит шаблон. Взгляните на общую картину ещё раз, на шаблоне со всеми типами узлов, кроме embed:

::demo if-chain

У того же шаблона в AST есть `if` с тремя ветками. В `render` он становится цепочкой `if / else if / else` между двумя маркерами. В `diff` он становится вычислением номера ветки для `prev` и для `next`, а смена ветки становится `clear` и `insert`. Шаг выше показывает именно это. Подробности — на следующих страницах.

## Что вы узнали

- `parse` читает строки и отступы в дерево из шести типов узлов. Отступ задаёт родителя, и все соседние узлы должны быть с ним согласны.
- Встроенный текст становится настоящим текстовым узлом; значения атрибутов и текст — это списки частей (строк и выражений), и так компилятор знает, что статично.
- Выражения разбирает отдельный маленький парсер в девять видов узлов. `.` и `?.` — одно и то же, и шаблон может только читать.
- Id узлов — это порядок создания при обходе в глубину. Они внутренние и становятся id vnodes и patches.
- Ошибка — это `TemplateError` со строкой и колонкой; лог сборки показывает ещё и имя файла.
