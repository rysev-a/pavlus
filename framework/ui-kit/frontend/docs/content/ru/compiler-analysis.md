## Вопрос, на который отвечает анализ

Шаблон — это функция от state. Когда state меняется, большая часть страницы обычно остаётся той же. Чтобы обновить страницу дёшево, `diff` должен быстро знать, на какие узлы это может повлиять. Компилятор отвечает на это один раз, во время сборки, для каждого узла: **какие поля state читает этот узел?**

Этот ответ — **набор зависимостей** узла. Он вычисляется одним небольшим модулем, `analyze.ts`, по AST. Набор используется тремя способами:

- Узел с **пустым** набором никогда не может измениться. Он не получает `id` и кода в `diff`.
- Узел с непустым набором получает в `diff` **guard**: код, обрабатывающий узел, выполняется, только если изменилось одно из полей набора.
- Набор родителя содержит наборы всех его дочерних узлов, поэтому guard на родителе может пропустить целое поддерево сразу.

Начнём с самого маленького случая. Демо открывает раздел AST; колонка `reads:` — это набор зависимостей.

::demo basic open=ast

И элемент, и его текст читают `name`. Шаг один меняет `name`, и ответ — один patch `text`. Шаг два меняет поле, которое шаблон не читает (`n`), и ответ — пустой список: первая строка `diff`, упоминающая `name`, ложна, и функция сразу возвращается.

## Свободные идентификаторы выражения

Основа анализа — функция, которая берёт выражение и собирает его **свободные идентификаторы**: имена, которые приходят снаружи выражения, то есть из state (или из охватывающего цикла). Она обходит дерево выражения и записывает только идентификаторы:

- Литерал (`1`, `"x"`, `true`) ничего не читает.
- Идентификатор (`count`) читает своё имя.
- Доступ к полю (`user.profile.name`) читает идентификатор в корне цепочки: `user`. Имена `profile` и `name` — это свойства, а не поля state.
- Индекс (`items[index]`) читает обе стороны: `items` и `index`.
- Вызов (`fmt(count, unit)`) читает вызываемое и каждый аргумент: `fmt`, `count` и `unit`.
- Унарные, бинарные, условные выражения и выражения-массивы читают всё, что в них находится.

::demo members open=ast

Посмотрите на первый абзац. Он показывает `user.profile.name` и `user.role`, а его зависимость — только `user`. Второй читает `index` и `items`. Третий читает ещё и функцию `fmt`: если функция хранится в state, её замена считается изменением.

> [!NOTE] Единица изменения — поле верхнего уровня
> Компилятор отслеживает `user`, а не `user.profile.name`. Он сравнивает `prev.user !== next.user`, одну проверку по ссылке. Если вы заменяете весь объект `user`, рассматривается каждый узел, читающий любую часть `user`. Следующий шаг, сравнение вычисленного текста, затем находит, что ничего видимого не изменилось, и patch не пишется. Так что цена грубой зависимости — несколько сравнений, но никогда не неверная страница.

## Что читает каждый вид узла

Функция `nodeDeps` возвращает набор зависимостей узла. Её правила следуют типам узлов.

| Узел | Читает |
| --- | --- |
| text | идентификаторы в своих частях |
| element | значения своих атрибутов, условия своих переключателей классов, аргументы своих событий и всё, что читают его дочерние узлы |
| if | тест каждой ветки и всё, что содержат ветки |
| for | выражение списка, плюс то, что читает тело, минус переменные цикла |
| embed | динамическое выражение view, каждое значение prop и каждый spread |
| outlet | всё (см. конец этой страницы) |

Результат для узла запоминается, так что повторный вопрос ничего не стоит. Поскольку элемент включает свои дочерние узлы, у корня шаблона всегда самый большой набор: объединение всего дерева.

## Статические узлы

Узел с пустым набором — **статический**. Компилятор делает для него три вещи.

1. В `render` он пишет vnode без `id`, поскольку ни один patch никогда не назовёт его (единственное исключение — текст вроде `{null}`: это выражение, поэтому он получает id, хотя никогда не может измениться).
2. В `diff` он не пишет ничего. Функция, обрабатывающая узел, начинается с проверки именно этого случая: нет зависимостей — нечего делать.
3. Поскольку набор родителя — объединение наборов его дочерних узлов, статический дочерний узел ничего не добавляет в guard родителя.

::demo static-mix open=ast

Только последний абзац и содержащий его `div` читают `visits`. Заголовок и приглушённый абзац показывают `reads: —`. Сравните со сгенерированным `diff` для этого шаблона:

```ts
function diff(prev, next, idSuffix = "", messagePrefix = "", env) {
  const patches = [];
  if (prev === next) return patches;
  // line 1: <div.card> (reads: visits)
  if (prev.visits !== next.visits) {
    // line 4: <p>
    // line 4: text
    const prevText = "Visits: " + toText(prev.visits);
    const nextText = "Visits: " + toText(next.visits);
    if (prevText !== nextText) patches.push({ op: "text", id: "6" + idSuffix, text: nextText });
  }
  return patches;
}
```

`h3` и первого `p` здесь нет. Для них не написан даже комментарий. На странице с большой статической вёрсткой и несколькими динамическими местами работа `diff` зависит только от динамических мест.

## Guard

Для узла с непустым набором генератор кода пишет комментарий `// line N: <tag> (reads: a, b)` и под ним `if`, сравнивающий каждое поле набора между `prev` и `next`:

```ts
if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title) {
```

Сравнение — это `!==`, идентичность значения. Для числа или строки это сравнение значений. Для объекта или массива это сравнение ссылок. Это дёшево, и именно поэтому state нужно обновлять, создавая новые объекты.

Guard **грубый** намеренно. Он говорит «что-то, что читает этот узел, изменилось», а не «этот атрибут изменился». Внутри guard компилятор вычисляет каждый атрибут, каждый payload события и каждый текст и для `prev`, и для `next` и пишет patch, только если два результата различаются. Два уровня проверок работают вместе: дешёвый guard пропускает большинство узлов, а точное сравнение результатов решает, что на самом деле попадёт в список patch.

::demo parts open=ast

Один элемент читает пять полей: `url`, `active`, `title`, `id` и `label`. На шаге один меняется только `id`. Guard открывается, и `diff` проверяет каждую часть: `href` равен, title равен, класс равен. Различается только payload события, поэтому единственный patch — `handler`. На шаге два меняются и `title`, и `label`, и patches два: атрибут `title` и текст. Обратите внимание, что `href` и класс просматриваются (guard открылся из-за `title`), но patch не дают.

Ещё один взгляд на ту же идею с деревом соседних узлов. У каждого абзаца свой guard, так что изменение одного поля затрагивает один абзац.

::demo two-fields open=ast

На шаге один меняется только `body`. В `section` заходят, guard у `h2` ложен, guard у `body` истинен, guard у `author` ложен. Результат: один patch. На шаге два меняются `title` и `author`, а `body` нет, так что вы получаете два patch, а средний абзац пропускается.

## Один и тот же guard дважды пишется один раз

Часто дочерний узел читает ровно те поля, что и его родитель. Тогда собственный guard дочернего узла избыточен: guard родителя уже доказывает, что изменилось что-то из того, что он читает. Компилятор это обнаруживает (набор дочернего узла равен набору родителя) и не повторяет проверку. Комментарий узла он всё равно пишет, а `if` нет.

::demo same-deps open=ast

Здесь `button` читает `label` через свой атрибут, своё событие и свой текст. Текстовый узел тоже читает `label`. Вот сгенерированный `diff`:

```ts
// line 1: <button> (reads: label)
if (prev.label !== next.label) {
  const prevTitle = toAttr(prev.label);
  const nextTitle = toAttr(next.label);
  if (prevTitle !== nextTitle) {
    patches.push(nextTitle === null
      ? { op: "rmAttr", id: "0" + idSuffix, name: "title" }
      : { op: "attr", id: "0" + idSuffix, name: "title", value: nextTitle });
  }
  const prevClickPayload = prev.label;
  const nextClickPayload = next.label;
  if (!(prevClickPayload === nextClickPayload)) {
    patches.push({ op: "handler", id: "0" + idSuffix, event: "click", msg: { id: messagePrefix + "pick", payload: nextClickPayload } });
  }
  // line 1: text
  const prevText = "Pick " + toText(prev.label);
  const nextText = "Pick " + toText(next.label);
  if (prevText !== nextText) patches.push({ op: "text", id: "1" + idSuffix, text: nextText });
}
```

Есть один `if (prev.label !== next.label)`. У текста, помеченного `// line 1: text`, собственного guard нет, потому что guard кнопки — та же проверка. Patches идут в порядке: атрибуты, событие, дочерние узлы.

Guard не убирается, когда набор дочернего узла меньше набора родителя, даже на одно поле. В следующем примере `footer` читает только `count`, но его родитель читает четыре поля, поэтому у footer остаётся собственный guard.

::demo nested open=ast

`div.panel` читает `body`, `count`, `open` и `title`. Переключатель класса `class:open=open` вычисляется прямо внутри guard у `div`, без собственного guard: он принадлежит элементу. У каждого дочернего узла под ним собственный guard. `if` читает `open` и `body`. На первом шаге меняется только `count`, и результат — один patch текста. На втором меняется только `body`, и patch идёт в текст внутри открытой ветки.

Сгенерированный код показывает, как устроены собственные атрибуты элемента и его дочерние узлы:

```ts
// line 1: <div.panel> (reads: open, title, body, count)
if (prev.open !== next.open || prev.title !== next.title || prev.body !== next.body || prev.count !== next.count) {
  const prevClass = joinClasses(["panel", (prev.open ? "open" : "")]);
  const nextClass = joinClasses(["panel", (next.open ? "open" : "")]);
  if (prevClass !== nextClass) {
    patches.push(nextClass === null
      ? { op: "rmAttr", id: "0" + idSuffix, name: "class" }
      : { op: "attr", id: "0" + idSuffix, name: "class", value: nextClass });
  }
  // line 2: <h2> (reads: title)
  if (prev.title !== next.title) {
    // line 2: text
    ...
  }
  // line 3: if (reads: open, body)
  ...
  // line 5: <footer> (reads: count)
  if (prev.count !== next.count) {
    // line 5: text
    ...
  }
}
```

Тонкость, которую стоит заметить: когда меняется только `count`, guard у `div` истинен, поэтому класс вычисляется для обеих сторон. Результаты совпадают, и patch не создаётся. Атрибуты элемента перепроверяются всякий раз, когда меняется что-либо под ним. Это стоит двух небольших вычислений строк в обмен на простое правило: guard узла покрывает узел и всё внутри него.

## Переменные цикла убираются

Внутри `for` имена элемента и индекса не приходят из state. Они существуют только внутри цикла. Поэтому анализ **убирает** их из набора цикла. Остаётся то, что циклу нужно снаружи.

::demo loop open=ast

Читайте колонку `reads:` снизу вверх. Текст читает `item` и `prefix`. `li` читает то же самое, поскольку его переключатель класса читает `item.hot`. `for` читает `items` (список) и `prefix`, но не `item`: переменная цикла убрана. `ul` выше такой же, как `for`.

Теперь сгенерированный код. Цикл сравнивается с помощью хелпера `diffKeyedList`, который решает, что вставить, удалить и переместить, по key. Для элементов, которые есть с обеих сторон, он вызывает функцию `common(prevIndex, nextIndex)`. В ней переменная цикла — уже не имя из state, а локальная переменная, имеющая одно значение для `prev` и одно для `next`, и guard у `li` сравнивает их:

```ts
common(prevIndex, nextIndex) {
  const prevItem = prevItemList[prevIndex];
  const nextItem = nextItemList[nextIndex];
  const itemSuffix = idSuffix + "#" + nextItemKeys[nextIndex];
  // line 3: <li> (reads: item, prefix)
  if (prevItem !== nextItem || prev.prefix !== next.prefix) {
    ...
  }
},
```

Выражение key (`key item.id`) тоже принадлежит циклу. Оно может использовать переменную цикла; всё, что оно читает снаружи, остаётся в наборе.

В демо шаг один заменяет один элемент списка: элемент с `id` 1 получает `hot: true`. Патчится только `li` этого элемента, с id `2#1` (узел 2, key 1). Демо создаёт новый объект и для второго элемента, поэтому его guard тоже открывается, но его класс и текст оказываются равны, и patch он не даёт. Шаг два меняет `prefix`, который читает каждый элемент, поэтому текст каждого элемента пересчитывается, и здесь патчится один элемент.

Переменная индекса работает так же.

::demo loop-index open=ast

Текст читает `n` и `row`, а цикл читает только `rows`. Индекс участвует в guard у `li` (`prevIndex !== nextIndex`). Это важно в цикле с key: элемент сохраняет свой key при перемещении, но получает новый индекс. В шаге список `a, b` становится `b, a`. Первый patch перемещает элемент `a` в конец. Два других patch меняют числа: `b` теперь `0. b`, а `a` теперь `1. a`.

> [!WARNING] Переменная цикла скрывает поле state с тем же именем
> Внутри цикла имя `name` означает переменную цикла, а не поле state `name`. Анализ убирает её из набора цикла, как и должен, поэтому чтение внешнего `name` внутри цикла невозможно. Выбирайте имена циклов, которые не конфликтуют с вашим state: `user in users`, а не `name in names`, когда `name` — тоже поле.

::demo shadow open=ast

Первый абзац читает поле state `name`. Цикл читает только `names`, а span внутри читает переменную цикла `name`, которая локальна. Два `name` — это разные вещи, которые случайно пишутся одинаково.

## Условия

`if` читает тесты всех своих веток и всё, что содержат ветки. Изменение тестов может сменить ветку; изменение внутри ветки меняет только её содержимое. Генератор кода пишет оба случая и разделяет их.

::demo branches open=ast

`if` читает `user` и `guest`. Посмотрите на сгенерированный `diff`:

```ts
const prevBranch = prev.user ? 0 : prev.guest ? 1 : 2;
const nextBranch = next.user ? 0 : next.guest ? 1 : 2;
if (prevBranch !== nextBranch) {
  // another branch: replace what is between the markers
  if (prevBranch !== -1) patches.push({ op: "clear", from: "0s" + idSuffix, to: "0e" + idSuffix });
  if (nextBranch !== -1) {
    ...
    patches.push({ op: "insert", before: "0e" + idSuffix, nodes: branchNodes });
  }
} else {
  // the same branch: diff inside it
  if (nextBranch === 0) {
    // line 2: <p> (reads: user)
    if (prev.user !== next.user) {
      ...
    }
  }
}
```

Компилятор превращает цепочку тестов в число, **индекс ветки**, для обоих состояний (`-1` означает «нет ветки», когда нет `else`). Если число изменилось, он заменяет содержимое между двумя маркерами. Если нет, он смотрит только внутрь этой ветки, и код получают только те ветки, в которых есть на что смотреть (здесь только ветка 0). В демо шаг один — та же ветка (имя изменилось с Ann на Bob) и даёт patch `text`. Шаг два меняет ветку и даёт `clear` и `insert`.

`if`, в ветках которого нет ничего динамического, всё равно читает свои тесты. Ветка, которая ничего не читает, ничего не вносит в набор `if`.

## Дочерние view

Embed читает свои props. Props — это выражения, и анализ собирает их так же, как и везде. Spread (`...extra`) читает выражение после точек.

::demo embed open=ast

Строка `+Badge#state` читает `status`, поэтому родитель вызывает `Badge.diff`, только когда меняется `status` (guard — `if (prev.status !== next.status)`). `p` ниже статичен: он ничего не читает, и дочерний компонент о нём не спрашивается. Верно и обратное: родитель ничего не знает о том, что читает дочерний компонент. `diff` самого дочернего компонента решает это по его собственному анализу, по props, которые он получает.

## Outlet читает всё

`+outlet` показывает дочерний компонент, который выбирает маршрут компонента. То, что он показывает, зависит от маршрута и от части state, которую шаблон не может назвать. Поэтому анализ не может дать ему список полей. Вместо этого он даёт ему особый маркер, пустую строку `""`, которая означает «всегда».

```pavlus layout.pavlus
div.layout
  h1 {title}
  nav Menu
  +outlet
```

AST этого шаблона выводит маркер как `* (an outlet reads everything)`:

```text
el  div.layout                                  #0   reads: * (an outlet reads everything)
  el  h1 {title}                                  #1   reads: title
    text  {title}                                   #2   reads: title
  el  nav Menu                                    #3   reads: — (reads nothing)
    text  Menu                                      #4   reads: — (reads nothing)
  outlet  +outlet                                 #5   reads: * (an outlet reads everything)
```

Маркер поднимается к каждому родителю, поскольку родитель включает наборы своих дочерних узлов. Для такого узла guard не может быть списком сравнений, поэтому сгенерированный код — `if (true) {`, а комментарий говорит `(reads: the route and the routed child)`. Соседние узлы сохраняют свои guard: `h1` по-прежнему читает только `title`, а `nav` по-прежнему статичен. Только сам outlet и его предки имеют всегда включённый guard. Это ещё одна причина располагать outlet ближе к корню вёрстки, а не внутри глубокой, оживлённой структуры.

## Страница побольше

Всё на этой странице работает вместе на реалистичной вёрстке: шапка с навигацией с key, условное flash-сообщение, статья и подвал. Откройте AST и сначала прочитайте колонку `reads:`. Затем посмотрите, что патчат два шага.

::demo big open=ast

Несколько вещей, которые стоит заметить в колонке.

- Корневой `main` читает всё, что нужно странице: `article`, `flash`, `links`, `page` и `site`. Это объединение.
- `nav` читает `links` и `page`. `for` внутри читает те же два, и его переменная цикла `link` из набора ушла, а `a` и его текст читают `link` (и `page`, для переключателя класса).
- Абзац `p.static` ничего не читает. У него нет id, и `diff` его не упоминает.
- `if flash` читает только `flash`. `footer` читает `site`, как и `h1`, хотя используется только часть `year`: единица — это поле.

Шаг один меняет `page` с `/` на `/about`. Затрагиваются только две ссылки, и только их класс: `/` теряет `current` (`rmAttr`), а `/about` получает его (`attr`). Заголовок шапки, статья и подвал не сравниваются, потому что их guard читают другие поля. Шаг два меняет только `article`: один patch `text` для заголовка. Это результат анализа, который можно увидеть.

## Пределы, которые нужно знать

- Анализ следует за именами, а не за значениями. Функция в state, читающая другую часть state (геттер, замыкание), скрывает это чтение от компилятора. Храните производные значения в state или передавайте входные данные как аргументы: `{total(items)}` читает `total` и `items` и работает.
- Единица — это поле верхнего уровня, и оно сравнивается по ссылке. Обновляйте заменой: `{ ...state, user: { ...state.user, name } }`.
- В узел с большим набором (корень, вёрстка, outlet) заходят часто. Это не медленно, потому что проверки внутри — снова guard. Но это повод держать динамические части маленькими и ближе к листьям.

## Что вы узнали

- У каждого узла есть набор зависимостей: поля state верхнего уровня, которые он читает, без переменных его собственных циклов.
- Узел, который ничего не читает, статичен: нет id в `render`, нет кода в `diff`.
- Узел, который что-то читает, получает guard, сравнивающий эти поля через `!==`. Внутри guard каждый атрибут, payload и текст сравниваются по своему результату, поэтому patches создают только настоящие изменения.
- Guard, повторяющий guard своего родителя, не пишется дважды. Outlet читает всё и делает guard над ним всегда истинными.
