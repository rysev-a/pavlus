## Идея за одну минуту

Pavlus — это фреймворк для создания веб-интерфейсов. Он опирается на одно правило: **код, который вы пишете, не касается внешнего мира.** Он никогда не читает DOM, не вызывает `fetch`, не спрашивает время и не пишет в консоль. Вместо этого он снова и снова отвечает на один вопрос:

> Для этого **message** и этого **state**: какие **effects** должны произойти?

*Message* — это небольшой кусок обычных данных, который говорит, что только что случилось: `{ id: "inc" }` значит «пользователь нажал кнопку плюс». *State* — обычный объект, в котором хранится всё, что показывает экран. *Effect* — тоже обычные данные. Он описывает то, что нужно сделать, например «записать в поле `count` значение 3» или «отправить этот HTTP-запрос». Ваш код только возвращает описание. Саму работу он не делает.

Работу делают **plugins**. Каждый plugin отвечает за один вид побочных действий: DOM, HTTP, таймеры, адрес в браузере, store, в котором хранится state. Когда во внешнем мире что-то происходит (клик, ответ сервера, тик таймера), plugin превращает это в message и передаёт его вашему коду. Когда ваш код возвращает effects, ядро передаёт каждый effect тому plugin, которому он адресован.

Третья часть — **язык шаблонов**. HTML-структуру компонента вы пишете в коротком `.pavlus`-файле, где вложенность задаётся отступами. Компилятор превращает его в две обычные функции: `render(state)`, которая возвращает узлы для показа, и `diff(prev, next)`, которая возвращает небольшой список изменений (patches), нужных, когда state переходит от одного значения к другому.

```text
 click, reply, timer tick
          |   a plugin turns it into a message
          v
 your code:  (message, state)  ->  effects          pure, no side effects
          |   effects are plain data
          v
 plugins:    store, dom, http, time, router, ...    the only code that does things
          |   the store changed the state
          v
 template:   diff(prev, next)  ->  patches           pure, generated by the compiler
          |
          v
 the dom plugin applies the patches to the page
```

Это тот же цикл, что и в языке Elm, только с компилятором, который делает сторону шаблонов быстрой. Следующая страница этой серии, [Быстрый старт](page:quick-start), строит работающий пример. Страница [Архитектура: чистый код и эффекты](page:concepts-architecture) подробно объясняет этот цикл.

## Зачем держать код чистым

Чистая функция всегда возвращает один и тот же результат для одних и тех же входных данных и ничего не меняет вне себя. Одно это свойство даёт вам то, что обычно стоит дорого:

- **Тесты без браузера.** Чтобы протестировать handler, вы вызываете его с message и state и сравниваете возвращённые effects обычными assert. Ничего не нужно подменять.
- **Один и тот же код на сервере.** Для рендеринга в строку DOM не нужен, поэтому компоненты, которые работают в браузере, работают и в Node. Страница [Серверный рендеринг](page:concepts-ssr) показывает, как это сделать.
- **Повтор и история.** State — это обычные данные, а каждое изменение — записанный effect, поэтому вы можете отменить изменение или вернуться к более раннему моменту. Историю за вас хранит store plugin.
- **Понятные ошибки.** Когда что-то идёт не так, вы можете вывести message и effects. Оба — обычные объекты.

Цена — правило, которое вы должны соблюдать сами: **фреймворк не проверяет, что ваш код чистый.** Если handler всё же вызовет `Date.now()`, ничто ему не помешает, и вы потеряете перечисленные выше преимущества. Договорённость простая. Если handler нужно время, он возвращает effect `time` и получает ответ в виде message.

## Маленькая программа целиком

Вот законченный счётчик из четырёх частей. Сначала шаблон. Это HTML-структура компонента: `{count}` читает поле `count` из state, а `@click=inc` говорит, что клик отправляет message `inc`.

::demo counter

Демо выше компилируется настоящим компилятором прямо в вашем браузере. Два шага внизу показывают patches, которые возвращает `diff`, когда `count` меняется с 2 на 3 и обратно. Меняется только текстовый узел. Абзац с подсказкой вставляется, когда условие `count > 2` становится истинным, и очищается, когда оно становится ложным.

Вторая часть — компонент. Это класс с одним методом на каждый message. Каждый метод получает message и state и возвращает список effects. Здесь effects строятся помощником store plugin `store.set(path, value)`, который возвращает обычный объект `{ plugin: "store", type: "set", path, value }`.

```ts counter.ts
import { Component, type Message } from "@pavlus/frontend";
import { storeEffector as store } from "@pavlus/frontend/plugins";
import view from "./counter.pavlus";

export interface CounterState {
  count: number;
}

export class Counter extends Component<CounterState> {
  view = view;

  inc(_msg: Message, state: CounterState) {
    return [store.set("count", state.count + 1)];
  }

  dec(_msg: Message, state: CounterState) {
    return [store.set("count", state.count - 1)];
  }
}

export const counter = new Counter();
```

Третья часть — подключение. `createApp` связывает компонент с его plugins. Store plugin хранит state, а DOM plugin рендерит view компонента в элемент `#app` и сообщает о кликах в виде messages.

```ts main.ts
import { createApp } from "@pavlus/frontend";
import {
  DomPlugin,
  createStorePlugin,
} from "@pavlus/frontend/plugins";
import { counter, type CounterState } from "./counter.ts";

createApp<CounterState>({
  app: counter,
  plugins: [createStorePlugin<CounterState>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

Четвёртая часть: больше ничего нет. Нет `useState`, нет подписок, нет `setCount`. Клик превращается в `{ id: "inc" }`, `inc` возвращает effect `set`, store заменяет state, `diff` сравнивает старый и новый state и возвращает один patch `text`, а DOM plugin применяет его.

> [!NOTE] State не живёт в компоненте
> У объекта `Counter` нет изменяемых полей. State живёт в store plugin и передаётся в каждый handler. Экземпляр компонента общий для всех messages, поэтому в нём не должно быть изменяемых данных. Почему так, объясняет страница [Компоненты и состояние](page:concepts-components).

## Как pavlus соотносится с фреймворками на virtual DOM

Многие популярные фреймворки используют *virtual DOM*: при каждом обновлении код компонента запускается снова, строит новое дерево лёгких узлов, и фреймворк сравнивает его с предыдущим деревом, чтобы найти, что изменилось. Для части с view pavlus идёт другим путём. Таблица сравнивает подходы в общем, а не какой-то один продукт, и называет не только то, что pavlus получает, но и то, от чего он отказывается.

| Вопрос | Типичный фреймворк на virtual DOM | Pavlus |
| --- | --- | --- |
| Как находится изменение? | Фреймворк сравнивает старое и новое дерево узлов. | Компилятор генерирует `diff(prev, next)`, который сравнивает поля state через `===`. Никакое дерево не сравнивается. |
| Сколько работы при несвязанном изменении? | Зависит от фреймворка; часто функция компонента запускается снова. | Поддерево, которое не читает ни одного изменившегося поля, пропускается одной проверкой. |
| Где живёт логика обновления? | В коде компонента, часто с hooks или setters. | В handlers, которые возвращают effects. В view нет логики обновления. |
| Где живут побочные действия? | Где угодно в коде компонента. | Только в plugins. Код приложения возвращает данные. |
| Что такое обработчик события? | Функция. | Данные: `{ id, payload }`. `diff` сравнивает handlers по значению. |
| Изменения state | Часто через setters, иногда через мутацию. | Store заменяет state. Мутировать его на месте нельзя, потому что `diff` доверяет `===`. |
| Тестирование логики приложения | Обычно нужен renderer или моки. | Вызвать handler и сравнить effects. |
| Язык шаблонов | Часто JSX, в том же файле, что и код. | Отдельный файл `.pavlus` со своим небольшим синтаксисом и языком выражений. |
| Зрелость | Большие экосистемы, много библиотек, много разработчиков. | Молодой фреймворк с небольшой поверхностью. Slots, рекурсивные шаблоны и типизированные props пока не реализованы. |

> [!WARNING] Другой компромисс, а не лучший во всех случаях
> Компилируемый diffing быстр в том, что он знает, но язык шаблонов меньше, чем JavaScript. Выражения — небольшое чистое подмножество: у стрелочных функций только тело-выражение, а литералов объектов и шаблонных строк нет. Производные значения, которым нужен настоящий код, вычисляются в handler и сохраняются в state. Pavlus также требует дисциплины, потому что чистота — это договорённость, которую ничто не контролирует.

## Что вы узнали

- Код приложения чистый: на входе `(message, state)`, на выходе список effects. Effects и messages — обычные данные.
- Plugins выполняют все побочные действия и превращают внешний мир в messages. Ядро соединяет их в цикл.
- Шаблон компилируется в `render` и `diff`. `diff` возвращает patches, сравнивая поля state, которые читает каждый узел.
- Целое приложение — это шаблон, класс компонента и вызов `createApp` со store plugin и DOM plugin.
- Pavlus обменивает небольшой язык шаблонов и договорённость о чистоте на простое тестирование и дешёвые обновления.
