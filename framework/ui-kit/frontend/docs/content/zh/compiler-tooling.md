## 编译器是一个从文本到文本的函数

你已经看到了编译器生成什么。本页讲的是如何运行它。编译器的核心是一个函数：它接收模板的文本，返回一个 JavaScript 模块的文本。它不读取文件，不接触 DOM，也不需要浏览器。相同的输入总是得到相同的输出。

下面是最小的示例。打开生成的模块，从头开始阅读。

::demo smallest open=module

编译后的模块始终有相同的组成部分，顺序也相同：

1. 一行头部注释：`// Generated by pavlus from smallest.pavlus. Edit the template, not this file.`
2. 一行 `import`，导入模块用到的运行时 helper（这里只有 `toText`）。不使用任何 helper 的模板完全没有 import。
3. 你的模板用它自己的 `import` 行导入的每个模板各有一行 `import`。
4. `const meta`，它列出被 embed 的子级的实例名，并说明模板是否有 `+outlet`。
5. 两个函数 `render` 和 `diff`，每个都带有一条说明它是纯函数的注释。
6. 两种导出：名称 `render`、`diff` 和 `meta`，以及一个默认导出，即对象 `{ render, diff, meta }`。这个对象就是 **view**，DOM plugin 挂载的就是它。

## compileTemplate

这个函数从 `@pavlus/frontend/compiler` 导出。它接收源码和一个选项对象，返回模块文本。

```ts
import {
  compileTemplate,
  DEFAULT_RUNTIME,
} from "@pavlus/frontend/compiler";

const source = "p Hello, {name}";
const code = compileTemplate(source, { filename: "src/hello.pavlus" });

console.log(DEFAULT_RUNTIME); // "@pavlus/frontend/runtime"
```

有两个选项，都是可选的。

| 选项 | 默认值 | 作用 |
| --- | --- | --- |
| `filename` | 无 | 放在每条错误信息前面，也用于头部注释。头部只写路径的最后一部分，所以输出不取决于你的项目在哪里。 |
| `runtime` | `DEFAULT_RUNTIME` | helper 的导入来源模块。 |

`runtime` 选项只改变一行。使用 `{ runtime: "/src/runtime/helpers.ts" }` 时，模块以这样开头：

```ts
// Generated by pavlus from a template. Edit the template, not this file.
import { toText } from "/src/runtime/helpers.ts";
```

helper（`toText`、`toAttr`、`joinClasses`、`setAttr`、`sameValues`、`asView`、`diffKeyedList`、`resolveOutlet`、`childEnv`）只在运行时中存在一份，不会被粘贴到每个模板里。编译器**只导入模板用到的 helper**，并按名称排序。当这一行超过 100 个字符时，会写成每个名称一行。

::demo many-helpers open=module

看一下模块的前几行。用到了五个 helper，所以 import 是一个代码块。带 key 的循环需要 `diffKeyedList`，class 切换需要 `joinClasses` 和 `setAttr`，动态属性需要 `toAttr`，文本需要 `toText`。

当一个模板导入另一个模板时，编译器会把你写的路径原样复制到 `import` 中，由打包器来解析。

::demo with-child open=module

header 之后的前两行是 `import { childEnv, toText } from ...` 和 `import Badge from "./badge.pavlus";`。第二行来自你的模板，第一行来自编译器。`meta` 这一行是 `embeds: ["badge"]`：即子级的实例名。因为 `./badge.pavlus` 本身也是一个 `.pavlus` 文件，所以当打包器处理到它时，会由同一个插件编译它。

## compileToView

有时你想要的是一个能工作的 view，而不是一段文本：在测试里、在脚本里，或者像这样的文档页面里。`compileToView` 编译源码，然后运行这些代码（运行时 helper 作为参数传入），并返回 view。

```ts
import { compileToView } from "@pavlus/frontend/compiler";

const view = compileToView("p Hello, {name}");
view.render({ name: "Ann" });
view.diff({ name: "Ann" }, { name: "Bob" });
```

如果模板有 `import` 行，就必须按本地名称提供这些 view：

```ts
const badge = compileToView("span.badge {label}");
const row = compileToView(
  `import Badge from "./badge.pavlus"
li +Badge#badge(label=role)`,
  { components: { Badge: badge } },
);
```

`components` 中的值是一个 view，或者是带有 `view` 的对象。如果缺少某个名称，调用会以这条信息停止：

```text
pavlus: template imports "Badge" but no view was given in { components }
```

`compileToView` 用 `new Function` 构建函数，所以它需要一个允许这样做的页面。应用请使用 `compileTemplate` 加打包器，测试和工具则使用 `compileToView`。

## Vite 插件

在应用中，你不需要自己调用编译器。Vite 插件会为你的代码导入的每个模板调用它。它从 `@pavlus/frontend/vite` 导出，名为 `pavlus()`。

```ts vite.config.ts
import { defineConfig } from "vite";
import { pavlus } from "@pavlus/frontend/vite";

export default defineConfig({
  plugins: [pavlus()],
});
```

这个插件很小，它所做的一切几句话就能说完：

- 它以 `enforce: "pre"` 运行 `transform`，早于其他插件。
- 当去掉查询字符串后的路径以 `.pavlus` 结尾时，它才处理该模块。所有其他模块返回 `null`，不被触碰。选项 `extension` 可以改变后缀（`pavlus({ extension: ".pv" })`）。
- 它会跳过查询 `?raw`、`?url` 和 `?inline`，所以 `import source from "./card.pavlus?raw"` 给你的是模板的文本，而不是编译后的模块。下面的 golden 测试就是这样读取它们的输入的。
- 它调用 `compileTemplate(code, { filename, runtime })`。`filename` 是文件的完整路径，`runtime` 是你给它的选项。
- 它返回模块时带有 `map: { mappings: "" }`，意思是“没有 source map”。这是一个决定，而不是疏漏：Vite 会编造一个把生成的代码指向它自己的 map，这样的 map 又大又什么都说明不了。没有 map 时，浏览器的 DevTools 显示的是生成的 `render` 和 `diff`，而这正是你调试时想要的。
- 当编译器抛出错误时，它用这条信息调用 Vite 的 `this.error`，所以构建会停止，并显示带有文件名的错误。

插件里没有热更新的代码，生成的模块里也没有 `import.meta.hot`。保存的模板会像其他任何模块一样被再次转换，Vite 对不接受更新的模块应用它通常的规则。

### 运行时从哪里来

编译后的模块会导入 `@pavlus/frontend/runtime`，所以必须像安装其他任何导入一样安装这个包。如果 helper 在别处，例如在以该包为源码的 monorepo 中，你有两种办法。使用 `runtime` 选项，或者使用 Vite 的 alias。框架自己的测试使用的是 alias：

```ts
export default defineConfig({
  plugins: [pavlus()],
  resolve: {
    alias: {
      "@pavlus/frontend/runtime": "/path/to/src/runtime/helpers.ts",
    },
  },
});
```

### 使用模板

模板是和其他模块一样的模块。导入默认导出，即 view，并把它交给一个组件。

```pavlus counter.pavlus
section.counter
  h1 {count}
  button(@click=inc) Add one
```

```ts main.ts
import {
  Component,
  createApp,
  type Effect,
  type Message,
} from "@pavlus/frontend";
import { DomPlugin } from "@pavlus/frontend/plugins/dom";
import {
  createStorePlugin,
  storeEffector as store,
} from "@pavlus/frontend/plugins/store";
import view from "./counter.pavlus";

interface State {
  count: number;
}

class Counter extends Component<State> {
  view = view;
  inc(_msg: Message, state: State): Effect[] {
    return [store.set("count", state.count + 1)];
  }
}

createApp<State>({
  app: new Counter(),
  plugins: [createStorePlugin<State>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

模板中的 `@click=inc` 就是 message `inc`。组件的方法 `inc` 处理它，并以数据的形式返回一个 effect。store plugin 修改 state，DOM plugin 调用 `view.diff` 并应用 patch。

### 模板导入的类型

TypeScript 不知道 `.pavlus` 文件是什么。这个包为此提供了一个声明文件，即 `@pavlus/frontend/env`。在你的 `tsconfig.json` 包含的某个 `.d.ts` 文件中引用它一次：

```ts env.d.ts
/// <reference types="vite/client" />
/// <reference types="@pavlus/frontend/env" />
```

之后，`import view from "./counter.pavlus"` 的类型就是 `View`，具名导出 `render`、`diff` 和 `meta` 也有类型。声明中说，`render(state: any, ...)` 和 `diff(prev: any, next: any, ...)` 接受任何 state，所以 TypeScript 不会根据模板检查 state。`?raw` 导入的类型来自 `vite/client`。

## 错误

无法编译的模板会抛出 `TemplateError`。它的信息以位置结尾，例如 `(line 3, col 5)`，数字从 1 开始，错误对象还有字段 `line` 和 `col`。当你传入 `filename` 时（Vite 插件总是会传），信息以文件名开头。

下面是你最常遇到的错误。每个代码块展示一个模板，以及编译器在文件名为 `card.pavlus` 时为它返回的确切信息。

缩进中有制表符：

```pavlus-invalid
ul
	li Item
```

```text
card.pavlus: Tabs are not allowed, use spaces (line 2, col 1)
```

没有闭合的花括号：

```pavlus-invalid
p Hello, {name
```

```text
card.pavlus: Unclosed { (line 1, col 8)
```

表达式没有写完，或者含有不属于表达式语言的字符：

```pavlus-invalid
div
  p {total +}
```

```text
card.pavlus: Unexpected end of expression (line 2, col 13)
```

```pavlus-invalid
p {price # 2}
```

```text
card.pavlus: Unexpected character "#" (line 1, col 10)
```

前面没有 `if` 的 `else`。注意 `else` 也不能跟在 `for` 后面：

```pavlus-invalid
div
  p one
else
  p two
```

```text
card.pavlus: `else` without matching `if` (line 3, col 1)
```

没有被导入的子级。信息会告诉你两种修复方式：

```pavlus-invalid
div
  +Card#card(title=title)
```

```text
card.pavlus: "Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

不是 message 名称的 handler：

```pavlus-invalid
button(@click=1+2) Go
```

```text
card.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

位于不能有子节点的元素下面的一行：

```pavlus-invalid
input(value=x)
  p inside
```

```text
card.pavlus: This line cannot have children (line 2, col 1)
```

没有实例名的动态 embed、位置靠后的 `import`、给 class 切换写了字符串，以及带参数的 `+outlet`：

```text
card.pavlus: A dynamic component needs an instance name: +{expr}#name(...) (line 1, col 9)
card.pavlus: `import` lines must be at the top of the file (line 2, col 1)
card.pavlus: "class:on" needs an expression value (line 1, col 4)
card.pavlus: `+outlet` takes nothing after it (line 2, col 10)
```

在 Vite 构建中，信息会出现在构建错误里。下面是 Vite 8 构建在模板含有 `  li {name` 这一行时打印的内容（有所缩短）：

```text
Build failed with 1 error:

[plugin pavlus] /project/src/bad.pavlus
RolldownError: /project/src/bad.pavlus: Unclosed { (line 2, col 3)
```

> [!WARNING] 有些拼写错误不是错误
> 编译器通过整行的形式来识别 `if`、`else`、`for` 和 `+`。一个几乎匹配的行就是普通元素。单独的 `if`，没有条件，就是元素 `<if>`。`for item of items`（用 `of` 而不是 `in`）是带有文本 `item of items` 的元素 `<for>`。这两种都不是错误，页面渲染出来时会缺少你想要的块。当本该是块的东西以 tag 的形式出现时，请对照语法检查这一行。

## golden 文件

编译器的作者如何放心地修改它？测试套件有两层。

第一层 `output.test.ts` 检查输出的**属性**：helper 是导入的而不是粘贴的，只导入用到的 helper，变量的名称来自模板（`userList`、`prevUserKeys`、`liChildren`），注释说明代码块位于哪一行、有哪些依赖，并且代码里没有很长的行。

第二层固定**每一个字节**。在文件夹 `framework/src/compiler/__fixtures__` 里有十一个小模板，而在 `__goldens__` 里是编译器必须为每一个模板产生的确切 JavaScript：

| Fixture | 它测试什么 |
| --- | --- |
| `static` | 没有任何东西依赖 state，所以 `diff` 为空。 |
| `text` | 文本行、插值、转义的花括号。 |
| `element` | 动态属性、class 切换、带参数和修饰符的事件。 |
| `names` | 命名得像 JavaScript 关键字或生成名称的循环变量。 |
| `if` | `if`、`else if`、`else`、不带 key 的循环、第二个 `if`。 |
| `for` | 带索引的带 key 循环、嵌套循环、循环内的 `if`。 |
| `embed-static` | 被导入的子级、props、展开、循环中的 embed。 |
| `embed-dynamic` | `if` 之下的 `+{expr}`，带展开的 props。 |
| `outlet` | `+outlet` 节点。 |
| `shell`、`dashboard` | 两个真实的页面：一个带很长 class 表达式的菜单，以及一个仪表盘。 |

golden 测试用 `?raw` 读取每个 fixture（这能行得通，是因为插件会跳过该查询），用 `compileTemplate(source, { filename: "<name>.pavlus" })` 编译它，并用 `toMatchFileSnapshot` 把结果与文件比较。最后一个测试检查这些 fixture 合起来用到了每一种节点：元素、文本、带 `else if` 和 `else` 的 `if`、带 key 和不带 key 的 `for`、静态和动态 embed、`+outlet`、class 切换，以及事件的 `prevent`、`stop` 和多参数形式。如果你给语法添加了新特性，那个测试就会失败，直到某个 fixture 用到它。

如果对编译器的修改有意改变了输出，你就用 `-u` 运行测试，并在评审中阅读 `__goldens__/` 的 diff。如果只是重构，diff 必须为空。这就是固定字节的意义：输出的变化不可能不被注意到。

### 如何阅读 golden

golden 是输出最好的文档，因为它们始终是正确的。阅读时，从模板出发，找这些标志点：

- 注释 `// line N: <tag>` 把一个代码块对应到模板的一行。同一行同时出现在 `render` 和 `diff` 中。
- 在 `render` 中，找变量 `xChildren` 和 `xAttrs`。它们自下而上先被构建，元素最后才被推入。
- 在 `diff` 中，找带有 `(reads: ...)` 的注释。下一行就是它的守卫。
- 找 `idSuffix`。每个 id 都是节点的编号加上后缀，所以你可以在 `render` 和 `diff` 中跟踪同一个节点。
- 对于循环，找 `diffKeyedList`，并阅读它的四个函数。

## 测试 view

view 由两个纯函数组成，对 view 的测试就是普通测试。第一种测试不需要浏览器。

```pavlus todos.pavlus
ul
  for todo in todos key todo.id
    li(class:done=todo.done @click=toggle(todo.id)) {todo.title}
p {todos.length} todos
```

```ts todos.test.ts
import { expect, test } from "vitest";
import view from "./todos.pavlus";

const write = { id: 1, title: "Write", done: false };

test("finishing a todo changes only its class", () => {
  const patches = view.diff(
    { todos: [write] },
    { todos: [{ ...write, done: true }] },
  );
  expect(patches).toEqual([
    { op: "attr", id: "2#1", name: "class", value: "done" },
  ]);
});

test("nothing changed, nothing to patch", () => {
  expect(view.diff({ todos: [write] }, { todos: [write] })).toEqual([]);
});
```

这两个测试在纯 Node 中运行。测试运行器需要这个插件，所以 Vite 或 Vitest 的配置里必须在 `plugins` 中加入 `pavlus()`。

对于包含 DOM 的测试，这个包提供了 `@pavlus/frontend/testing`。它的函数 `mountView(viewOrComponent, initialState, document?)` 用真正的 DOM plugin 把 view 挂载到一个全新的容器中，不带应用的其余部分。它返回容器（`root`）、DOM plugin、用户事件产生的 message 列表（`messages`），以及函数 `set(nextState)` 和 `unmount()`。当模板有 `+outlet` 时，请挂载组件，而不只是它的 view，因为 outlet 需要组件的 `routing`。

```ts todos.dom.test.ts
// @vitest-environment jsdom
import { expect, test } from "vitest";
import { mountView } from "@pavlus/frontend/testing";
import view from "./todos.pavlus";

test("the DOM follows the state, and a click sends a message", () => {
  const write = { id: 1, title: "Write", done: false };
  const check = { id: 2, title: "Test", done: false };
  const h = mountView(view, { todos: [write, check] });

  h.set({ todos: [write, { ...check, done: true }] });
  expect(h.root.querySelectorAll("li")[1].className).toBe("done");

  h.root.querySelector("li")!.click();
  expect(h.messages).toMatchObject([{ id: "toggle", payload: 1 }]);

  h.unmount();
  expect(h.root.innerHTML).toBe("");
});
```

`messages` 数组保存着 DOM plugin 分发的内容。点击第一个条目产生了 `{ id: "toggle", payload: 1, event: { type: "click" } }`：message 的 id 和 payload 来自模板，`event` 字段由 plugin 添加。`mountView` 之后立即得到的 `h.root.innerHTML` 是：

```text
<!--pavlus--><ul><!----><!----><li>Write</li><!----><!----><li>Test</li><!----><!----></ul><p>2 todos</p><!--/pavlus-->
```

这是观察标记的好办法：每个条目位于两个空注释之间，列表位于另外两个之间。注释 `pavlus` 和 `/pavlus` 界定了整个 render。

## 你学到了什么

- `compileTemplate(source, { filename, runtime })` 返回带有 `render`、`diff`、`meta` 和默认 view 的 ES 模块文本。`compileToView` 返回一个可以工作的 view，用于测试和工具。`DEFAULT_RUNTIME` 是 helper 的来源。
- Vite 插件 `pavlus()` 编译每个 `.pavlus` 导入，跳过 `?raw`、`?url` 和 `?inline`，有意不提供 source map，并且在报告模板错误时带上它的文件、行号和列号。
- `@pavlus/frontend/env` 给 `.pavlus` 导入提供类型。state 的类型是 `any`。
- 编译器错误是位置从 1 开始的 `TemplateError`，少数拼写错误会产生元素而不是错误。
- golden 文件固定了十一个 fixture 的确切输出，所以生成代码的变化总能在评审中被看到。view 可以作为两个纯函数来测试，也可以用 `mountView` 挂载。
