## La idea en un minuto

Un archivo `.pavlus` no se interpreta en tiempo de ejecución. Un **compilador** lo lee una sola vez, en el momento del build, y escribe un módulo de JavaScript normal. Tu aplicación importa ese módulo como cualquier otro. El navegador nunca ve el texto del template y nunca necesita un parser de templates.

El módulo exporta tres cosas. Juntas se llaman una **view**:

- `render(state)` devuelve todo el template para un state, como una lista de objetos simples. Estos objetos se llaman **vnodes** (nodos virtuales).
- `diff(prev, next)` devuelve la lista más pequeña de cambios del DOM que convierte la página de `prev` en la página de `next`. Estos cambios se llaman **patches**.
- `meta` es un objeto pequeño que dice qué views hijas y qué `+outlet` contiene el template.

Este es el template más pequeño que tiene algo que calcular. Saluda a una persona por su nombre.

::demo tiny open=module

Lee el resultado desde arriba. El HTML es lo que produjo `render`. El primer paso muestra `diff` después de que `name` cambió de `Ann` a `Bob`: un patch, `{"op":"text","id":"1","text":"Hello, Bob"}`. El segundo paso muestra el mismo state dos veces: ningún patch. Abre el módulo: tiene unas treinta líneas, y cada línea tiene una razón. El resto de esta página las explica.

## Las etapas

El compilador es un pipeline corto. Cada etapa es una función simple que toma la salida de la etapa anterior.

| Etapa | Función | Entrada | Salida |
| --- | --- | --- | --- |
| Parse | `parse` | texto del template | `TemplateAst`: imports y un árbol de nodos |
| Analyze | `nodeDeps` | un nodo | el conjunto de campos del state que lee el nodo |
| Generate | `generate` | el AST | código fuente JavaScript de `meta`, `render` y `diff`, y la lista de helpers del runtime que usa |
| Assemble | `compileTemplate` | texto del template | el módulo ES terminado como una cadena |

El análisis no es una pasada aparte sobre todo el árbol. El generador de código le pide a `nodeDeps` las dependencias de cada nodo en el momento en que escribe la guarda de ese nodo (y el resultado se guarda en caché por nodo). Aun así es una etapa distinta, porque su respuesta decide cómo es `diff`. Las páginas siguientes recorren las etapas en orden: [el parseo](page:compiler-parser), [el análisis de dependencias](page:compiler-analysis), y el [render](page:compiler-render) y el [diff](page:compiler-diff) generados.

En el código fuente, `compileTemplate(source, { filename, runtime })` hace esto:

1. Llama a `parse(source)` y a `generate(ast)`. Si alguna lanza un `TemplateError` y diste un `filename`, el mensaje lleva delante el nombre del archivo: `app.pavlus: Unclosed { (line 1, col 8)`.
2. Escribe un comentario de cabecera de una línea: `// Generated by pavlus from app.pavlus. Edit the template, not this file.`
3. Escribe una línea `import` para los helpers del runtime que usa el código, y una línea `import` por cada línea `import` del template. Las views hijas se importan con el sistema de módulos real, así que tu bundler las ve.
4. Escribe el código generado, y después `export { render, diff, meta };` y `export default { render, diff, meta };`.

> [!NOTE] Dos formas de compilar
> `compileTemplate` devuelve el módulo como texto. Lo usa el plugin de Vite, y también este sitio de documentación cuando te muestra "el módulo generado". `compileToView` compila el mismo código y lo ejecuta al instante con `new Function`, y te da una view lista para usar. Está pensado para tests y herramientas. Las demos de estas páginas usan las dos: el módulo que puedes desplegar, y una view en vivo que produce el HTML y los patches.

## Un template sin nada que cambiar

No todos los templates tienen un `diff` que valga la pena leer. Este no lee nada del state.

::demo static open=module

El módulo no tiene ninguna línea `import`, porque no usa ningún helper. `render` construye los mismos vnodes cada vez. `diff` no tiene comparaciones: solo el atajo `if (prev === next) return patches;` y el `return patches;` final. El compilador vio que ningún nodo lee el state, así que no escribió nada más. Los vnodes tampoco tienen `id`: un id existe solo para que un patch pueda nombrar un nodo, y aquí nunca se hace patch de nada.

Esta es la primera gran idea del compilador: **gasta código solo donde algo puede cambiar**.

## Del texto al AST y al código

Ahora un template con un atributo dinámico, una alternancia de clase y una interpolación. Abrimos todas las secciones que la demo puede mostrar: el módulo, el AST y los vnodes.

::demo stages open=module,ast,vnodes

Recorre las tres secciones en el orden en que trabajó el compilador.

**El AST** tiene dos nodos: el elemento `a` (nodo `#0`) y su texto (nodo `#1`). Junto a cada nodo está `reads:`, el conjunto de campos del state que el nodo necesita. El elemento lee `active`, `title` y `url`, porque sus atributos y sus hijos los leen. El texto lee solo `title`. Los números `#0` y `#1` son **ids de nodo** (`nid`). El parser los reparte en el orden del documento.

**El módulo** tiene `render` primero. Escribe los hijos antes que el elemento, así que el texto se construye primero y se mete en `aChildren`. Después construye el objeto de atributos `aAttrs`, una línea por atributo dinámico, y mete el elemento. Luego viene `diff`. Para el elemento escribe una guarda, `if (prev.url !== next.url || prev.active !== next.active || prev.title !== next.title)`. Dentro de la guarda, cada atributo se calcula para `prev` y para `next`, y solo se añade un patch si los dos valores son distintos. Para el texto hay una segunda guarda, más pequeña, solo sobre `title`.

**Los vnodes** son lo que devolvió `render`. Tanto el elemento como el texto llevan un `id` (`"0"` y `"1"`), el id del nodo como cadena. Tienen ids porque `diff` puede direccionarlos. El patch del paso, `{"op":"attr","id":"0","name":"class","value":"link active"}`, usa el id del elemento. Solo se hace patch de `class`: el `href` y el texto no cambiaron.

## Qué obtienes cuando importas un archivo .pavlus

En un proyecto de Vite, el plugin `pavlus()` compila cada archivo que termina en `.pavlus`. El plugin se salta un import que termina en `?raw`, `?url` o `?inline`, porque esos piden el archivo en sí. Para cualquier otro import obtienes el módulo que escribió el compilador.

```ts main.ts
import view from "./counter.pavlus";
import { render, diff, meta } from "./counter.pavlus";

const vnodes = render({ count: 1 });
const patches = diff({ count: 1 }, { count: 2 });
```

El export por defecto y los tres exports con nombre son los mismos objetos. El export por defecto es la **view**, y eso es lo que espera el resto del código: el plugin del DOM toma una view para montarla, y un hijo embebido (`+Badge#status`) es una view. Las dos funciones son **puras**. Leen sus argumentos y nada más, no cambian nada y dan la misma respuesta para la misma entrada. Por eso pueden ejecutarse en un servidor, en un test o en el navegador, y por eso las demos de este sitio pueden ejecutarlas por ti.

Una view tiene estos parámetros, según el código generado:

```ts
function render(state, idSuffix = "", messagePrefix = "", env)
function diff(prev, next, idSuffix = "", messagePrefix = "", env)
```

Una view de nivel superior usa los valores por defecto. Los tres últimos parámetros existen para el **embedding**. Cuando un template contiene `+Badge#status`, el padre llama a `Badge.render` con un `idSuffix` más largo (`"/3"`, para que los ids de nodo del hijo no choquen con los del padre), un `messagePrefix` más largo (`"status."`, para que los messages del hijo se nombren por su instancia), y un `env`, que es el objeto del componente dueño de la view. El código de la aplicación nunca los pasa.

## El contrato entre render, diff y el plugin del DOM

El plugin del DOM es el único código del framework que toca el DOM. Se apoya en tres promesas que cumple el código generado. Son la razón por la que `render` y `diff` se generan juntos, a partir de un solo AST.

1. **El primer render crea el mapa.** Cuando el plugin monta una view, llama a `render(state)` una vez y construye DOM real a partir de los vnodes. Por cada vnode que tiene un `id`, recuerda el nodo del DOM bajo ese id.
2. **Un patch solo nombra ids que produjo render.** Un patch como `{ op: "text", id: "1", text: "Hello, Bob" }` se aplica como "busca el nodo guardado bajo `1` y cambia su texto". Si el id fuera desconocido, el plugin lanzaría `unknown node id`. El compilador se asegura de que todo nodo al que `diff` pueda hacer patch tenga un `id` en `render`.
3. **Los states siguientes se comparan con diff, no se vuelven a renderizar.** Cuando el state cambia, el plugin llama a `diff(oldState, newState)` y aplica los patches en orden. Un trozo nuevo de la página (una rama `if` nueva, un elemento de lista nuevo) llega dentro de un patch `insert` como vnodes ya hechos, y el plugin registra también sus ids.

Así que los vnodes no son solo una imagen de la página. Son una imagen más un índice. La siguiente demo lo hace concreto. Un `button` tiene un evento; mira qué partes del vnode llevan un id y los dos patches del paso.

::demo events open=vnodes

El `button` tiene un `id` porque su evento tiene un argumento que puede cambiar (`add(step)`). El patch `{"op":"handler",...}` le da al plugin el nuevo message, así que el click enviará `{ id: "add", payload: 5 }`. El plugin nunca quita y vuelve a añadir un listener: mantiene un listener por elemento y tipo de evento, y cambia el message que lee ese listener.

> [!WARNING] El compilador confía en la identidad
> `diff` compara valores con `!==`. Un objeto nuevo con el mismo contenido cuenta como un cambio. El mismo objeto con contenido nuevo, cambiado en el sitio, cuenta como ningún cambio. Dale siempre al state siguiente objetos nuevos para las partes que cambiaron (spread, `map`, `filter`) y nunca edites el state anterior.

## Por qué compilar en el momento del build

Podrías escribir una librería que lea el texto del template en tiempo de ejecución y lo recorra. Así funcionan muchos motores de templates. El compilador de pavlus hace el trabajo antes, y los beneficios son concretos.

- **`diff` es específico de tu template.** El `diff` generado contiene las comparaciones exactas que necesita tu template y ninguna otra. No hay un recorrido genérico del árbol ni una comparación de dos árboles de vnodes completos. En la demo `static` no contiene ninguna.
- **Nada que enviar salvo tu código.** El navegador recibe funciones simples más un pequeño conjunto de helpers. No recibe un parser, ni un intérprete de expresiones, ni cadenas de template.
- **Los errores llegan en el momento del build.** Un error tipográfico en un template detiene el build con un nombre de archivo, una línea y una columna. No espera a que un usuario abra la página.
- **La salida es legible.** El código generado tiene comentarios con la línea de código fuente de cada nodo (`// line 1: <a.link>`), nombres tomados de tus tags (`aChildren`, `liAttrs`), y una sentencia por idea. Puedes leerlo cuando algo te sorprenda.
- **Las funciones puras son fáciles de usar en cualquier sitio.** El renderizado en servidor llama a `view.render(state)` y convierte los vnodes en HTML. Un test unitario llama a `diff(a, b)` y comprueba los patches. No interviene ningún navegador.

El precio es que un template solo puede usar en sus expresiones un subconjunto pequeño y puro de JavaScript (consulta [expresiones](page:syntax-expressions)). El compilador debe entender cada expresión para saber qué lee. Ese límite es deliberado.

## Los helpers del runtime

Mira la primera línea del módulo de `stages`: `import { joinClasses, setAttr, toAttr, toText } from "@pavlus/frontend/runtime";`. El código generado no contiene su propia copia de estas funciones pequeñas. Viven una sola vez, en `runtime/helpers.ts`, y el compilador importa exactamente las que usa un template. Un template sin partes dinámicas no importa nada (consulta `static`). La ruta del import es el valor por defecto de la opción `runtime`, y puedes cambiarla.

Cada helper existe para quitarle una decisión al código generado, de modo que el código generado se mantenga corto y todos los templates traten los casos límite de la misma manera.

| Helper | Qué hace | Se usa para |
| --- | --- | --- |
| `toText(value)` | `null`, `undefined` y `false` pasan a ser una cadena vacía, todo lo demás `String(value)` | `{expr}` en texto y en cadenas |
| `toAttr(value)` | `null`, `undefined`, `false` dan `null` (sin atributo), `true` da `""`, cualquier otra cosa su cadena | `attr=expr` |
| `joinClasses(list)` | une con espacios los nombres truthy, da `null` cuando no queda nada | el atributo `class` |
| `setAttr(attrs, name, value)` | establece el atributo salvo que el valor sea `null` | todos los atributos dinámicos en `render` |
| `sameValues(a, b)` | valores iguales, o arrays con elementos iguales | payloads de eventos con varios argumentos |
| `diffKeyedList(...)` | calcula los removes, inserts y moves de una lista con key | `for ... key` en `diff` |
| `asView(value)` | convierte un componente o una view del state en su view, o en `null` | embeds `+{expr}#name` |
| `childEnv`, `resolveOutlet` | encuentran el componente detrás de un embed, y el hijo de la ruta de un `+outlet` | embeds y outlets |

La siguiente demo usa los helpers de atributos. Fíjate en cómo se comportan `null`, `false` y `true`.

::demo helpers open=module

`checked=done` con `done: true` se convierte en `checked=""`, que es como HTML escribe un atributo booleano. `disabled=locked` con `locked: false` no se escribe en absoluto. `{note}` con `note: null` es un texto vacío, no la palabra `null`. En el paso, `done` pasa de `true` a `false`, así que `checked` desaparece (`rmAttr`) y también la clase (`rmAttr`): `joinClasses` devolvió `null`, porque no quedó ningún nombre de clase.

> [!TIP] Nunca importas los helpers tú mismo
> El comentario de la primera línea de `helpers.ts` lo dice claramente: el código de la aplicación no los necesita. Si alguna vez quieres leer uno, son cortos. Los tests de `runtime/helpers.test.ts` documentan sus casos límite.

## Views hijas y el grafo de módulos

Un template puede embeber otro template. La línea `import` se convierte en un import ES real, y el embed se convierte en una llamada al `render` y al `diff` del hijo.

::demo embed open=module

Tres cosas que ver en el módulo. La línea `import Badge from "./badge.pavlus";` viene directa del template. El valor `meta` dice `embeds: ["status"]`: los nombres de instancia de los hijos. Y el nodo de texto del hijo tiene el id `1/3`: su propio id `1`, seguido del sufijo `/3` que añadió el padre (`3` es el id de nodo del embed en el padre). En el paso, el `diff` del padre llama a `Badge.diff` con las props antiguas y nuevas, y la respuesta es un patch para el texto del hijo. El padre no necesitó saber qué hay dentro de `Badge`.

## Un template más grande, de principio a fin

Por último, una pequeña lista de tareas con un título, un condicional y un bucle con key. Usa todo lo que conoce el pipeline: nodos estáticos, texto dinámico, una alternancia de clase, un evento, un `if`/`else` y un `for`. Abre primero el AST y lee la columna `reads:`, y después mira los dos pasos.

::demo todo open=ast

Algunas cosas que encontrar en él.

- La rama `else` (`p.empty`) no lee nada, así que sus nodos no tienen ids ni código en `diff`.
- El `li` lee `item`, una variable de bucle. El nodo `for` lee solo `items`, porque el compilador quita las variables de bucle de las dependencias del bucle (consulta [el análisis de dependencias](page:compiler-analysis)).
- El paso uno marca un elemento como hecho. El resultado es un único patch `attr` sobre el id `6#1`: nodo `6`, key de elemento `1`. El título, el pie y el otro elemento no producen patches.
- El paso dos vacía la lista. El `if` cambia de rama, así que la respuesta del compilador es `clear` de todo lo que hay entre los marcadores `3s` y `3e`, luego `insert` de la rama nueva, más un patch `text` para el pie.

## Lo que aprendiste

- El compilador convierte un template en un módulo con `render`, `diff` y `meta`, una sola vez, en el momento del build. Puede hacerlo porque las expresiones del template son un lenguaje pequeño y puro.
- Las etapas son parse, analyze, generate y assemble. El AST dice qué lee cada nodo, y el `diff` generado solo comprueba lo que lee un nodo.
- Una view es un par de funciones puras. El plugin del DOM hace render una vez, recuerda los nodos por id y después aplica los patches que devuelve `diff`.
- Los helpers del runtime se importan, nunca se copian. Un template importa solo los que usa.
