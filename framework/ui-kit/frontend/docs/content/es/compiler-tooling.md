## El compilador es una función de texto a texto

Ya has visto lo que genera el compilador. Esta página trata de cómo ejecutarlo. En su núcleo el compilador es una función: toma el texto de un template y devuelve el texto de un módulo de JavaScript. No lee archivos, no toca el DOM y no necesita un navegador. La misma entrada siempre da la misma salida.

Este es el ejemplo más pequeño. Abre el módulo generado y léelo desde arriba.

::demo smallest open=module

Un módulo compilado siempre tiene las mismas partes, en el mismo orden:

1. Un comentario de cabecera: `// Generated by pavlus from smallest.pavlus. Edit the template, not this file.`
2. Un `import` de los helpers del runtime que usa el módulo (aquí solo `toText`). Un template que no usa ningún helper no tiene ningún import.
3. Un `import` por cada template que tu template importa con su propia línea `import`.
4. `const meta`, que lista los nombres de instancia de los hijos embebidos e indica si el template tiene un `+outlet`.
5. Las dos funciones, `render` y `diff`, cada una con un comentario que dice que es pura.
6. Dos exports: los nombres `render`, `diff` y `meta`, y un export por defecto, un objeto `{ render, diff, meta }`. Ese objeto es una **view**, lo que monta el plugin del DOM.

## compileTemplate

La función se exporta desde `@pavlus/frontend/compiler`. Toma el código fuente y un objeto de opciones, y devuelve el texto del módulo.

```ts
import {
  compileTemplate,
  DEFAULT_RUNTIME,
} from "@pavlus/frontend/compiler";

const source = "p Hello, {name}";
const code = compileTemplate(source, { filename: "src/hello.pavlus" });

console.log(DEFAULT_RUNTIME); // "@pavlus/frontend/runtime"
```

Hay dos opciones, y las dos son opcionales.

| Opción | Valor por defecto | Qué hace |
| --- | --- | --- |
| `filename` | ninguno | Se pone delante de cada mensaje de error, y se usa para el comentario de cabecera. En la cabecera solo se escribe la última parte de la ruta, de modo que la salida no depende de dónde esté tu proyecto. |
| `runtime` | `DEFAULT_RUNTIME` | El módulo desde el que se importan los helpers. |

La opción `runtime` cambia una línea. Con `{ runtime: "/src/runtime/helpers.ts" }` el módulo empieza con:

```ts
// Generated by pavlus from a template. Edit the template, not this file.
import { toText } from "/src/runtime/helpers.ts";
```

Los helpers (`toText`, `toAttr`, `joinClasses`, `setAttr`, `sameValues`, `asView`, `diffKeyedList`, `resolveOutlet`, `childEnv`) viven en el runtime, una sola vez, y no se pegan en cada template. El compilador importa **solo los helpers que usa un template**, ordenados por nombre. Cuando la línea sería más larga de 100 caracteres, se escribe con un nombre por línea.

::demo many-helpers open=module

Mira las primeras líneas del módulo. Se usan cinco helpers, así que el import es un bloque. Un bucle con key necesita `diffKeyedList`, una alternancia de clase necesita `joinClasses` y `setAttr`, un atributo dinámico necesita `toAttr`, y el texto necesita `toText`.

Cuando un template importa otro template, el compilador copia la ruta tal como la escribiste en un `import`, y el bundler la resuelve.

::demo with-child open=module

Las dos primeras líneas después de la cabecera son `import { childEnv, toText } from ...` y `import Badge from "./badge.pavlus";`. La segunda viene de tu template, la primera viene del compilador. La línea `meta` dice `embeds: ["badge"]`: los nombres de instancia de los hijos. Como `./badge.pavlus` es a su vez un archivo `.pavlus`, el mismo plugin lo compila cuando el bundler llega a él.

## compileToView

A veces quieres una view que funcione y no un texto: en un test, en un script, o en una página de documentación como esta. `compileToView` compila el código fuente y luego ejecuta el código, con los helpers del runtime pasados como argumentos, y devuelve la view.

```ts
import { compileToView } from "@pavlus/frontend/compiler";

const view = compileToView("p Hello, {name}");
view.render({ name: "Ann" });
view.diff({ name: "Ann" }, { name: "Bob" });
```

Si el template tiene líneas `import`, las views deben darse por su nombre local:

```ts
const badge = compileToView("span.badge {label}");
const row = compileToView(
  `import Badge from "./badge.pavlus"
li +Badge#badge(label=role)`,
  { components: { Badge: badge } },
);
```

Un valor de `components` es una view, o un objeto que tiene una `view`. Si falta un nombre, la llamada se detiene con este mensaje:

```text
pavlus: template imports "Badge" but no view was given in { components }
```

`compileToView` construye la función con `new Function`, así que necesita una página que lo permita. Usa `compileTemplate` y un bundler para una aplicación, y `compileToView` para tests y herramientas.

## El plugin de Vite

En una aplicación no llamas tú mismo al compilador. Un plugin de Vite lo llama por ti para cada template que importa tu código. Se exporta desde `@pavlus/frontend/vite` como `pavlus()`.

```ts vite.config.ts
import { defineConfig } from "vite";
import { pavlus } from "@pavlus/frontend/vite";

export default defineConfig({
  plugins: [pavlus()],
});
```

El plugin es pequeño, y todo lo que hace se puede decir en pocas líneas:

- Ejecuta `transform` con `enforce: "pre"`, antes que los demás plugins.
- Maneja un módulo cuando la ruta, sin su query string, termina en `.pavlus`. Todos los demás módulos devuelven `null` y se dejan en paz. La opción `extension` cambia el sufijo (`pavlus({ extension: ".pv" })`).
- Se salta las queries `?raw`, `?url` y `?inline`, así que `import source from "./card.pavlus?raw"` te da el texto del template y no el módulo compilado. Así leen su entrada los tests golden de abajo.
- Llama a `compileTemplate(code, { filename, runtime })`. El `filename` es la ruta completa del archivo, y `runtime` es la opción que le diste.
- Devuelve el módulo con `map: { mappings: "" }`, que significa "sin source map". Es una decisión y no una carencia: Vite inventaría un mapa que apunta el código generado a sí mismo, que es grande y no dice nada. Sin un mapa, las DevTools del navegador muestran el `render` y el `diff` generados, y eso es lo que quieres depurar.
- Cuando el compilador lanza un error, llama a `this.error` de Vite con el mensaje, de modo que el build se detiene y muestra el error con el nombre del archivo.

El plugin no tiene código para las actualizaciones en caliente y el módulo generado no tiene `import.meta.hot`. Un template guardado se transforma de nuevo, como cualquier otro módulo, y Vite aplica su regla habitual para los módulos que no aceptan actualizaciones.

### De dónde viene el runtime

Un módulo compilado importa `@pavlus/frontend/runtime`, así que el paquete debe estar instalado, como para cualquier otro import. Si los helpers están en otro sitio, por ejemplo en un monorepo donde el paquete es el código fuente, tienes dos formas. Usa la opción `runtime`, o usa un alias de Vite. Los tests del propio framework usan un alias:

```ts
export default defineConfig({
  plugins: [pavlus()],
  resolve: {
    alias: {
      "@pavlus/frontend/runtime": "/path/to/src/runtime/helpers.ts",
    },
  },
});
```

### Usar un template

Un template es un módulo como cualquier otro. Importa el export por defecto, que es la view, y dásela a un componente.

```pavlus counter.pavlus
section.counter
  h1 {count}
  button(@click=inc) Add one
```

```ts main.ts
import {
  Component,
  createApp,
  type Effect,
  type Message,
} from "@pavlus/frontend";
import { DomPlugin } from "@pavlus/frontend/plugins/dom";
import {
  createStorePlugin,
  storeEffector as store,
} from "@pavlus/frontend/plugins/store";
import view from "./counter.pavlus";

interface State {
  count: number;
}

class Counter extends Component<State> {
  view = view;
  inc(_msg: Message, state: State): Effect[] {
    return [store.set("count", state.count + 1)];
  }
}

createApp<State>({
  app: new Counter(),
  plugins: [createStorePlugin<State>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

El `@click=inc` del template es el message `inc`. El método `inc` del componente lo maneja y devuelve un effect como datos. El plugin store cambia el state, el plugin del DOM llama a `view.diff` y aplica los patches.

### Tipos para los imports de templates

TypeScript no sabe qué es un archivo `.pavlus`. El paquete incluye un archivo de declaración para eso, `@pavlus/frontend/env`. Haz referencia a él una vez, en un archivo `.d.ts` que incluya tu `tsconfig.json`:

```ts env.d.ts
/// <reference types="vite/client" />
/// <reference types="@pavlus/frontend/env" />
```

Después de eso, `import view from "./counter.pavlus"` tiene el tipo `View`, y los exports con nombre `render`, `diff` y `meta` también tienen tipos. La declaración dice que `render(state: any, ...)` y `diff(prev: any, next: any, ...)` aceptan cualquier state, así que TypeScript no comprueba el state contra el template. Los tipos para los imports `?raw` vienen de `vite/client`.

## Errores

Un template que no se puede compilar lanza un `TemplateError`. Su mensaje termina con la posición, `(line 3, col 5)`, con números que empiezan en 1, y el objeto de error tiene además los campos `line` y `col`. Cuando pasas un `filename` (el plugin de Vite siempre lo hace) el mensaje empieza con el nombre del archivo.

Estos son los errores que encontrarás con más frecuencia. Cada bloque muestra un template y el mensaje exacto que devuelve el compilador para él con el nombre de archivo `card.pavlus`.

Un tabulador en la indentación:

```pavlus-invalid
ul
	li Item
```

```text
card.pavlus: Tabs are not allowed, use spaces (line 2, col 1)
```

Una llave que no está cerrada:

```pavlus-invalid
p Hello, {name
```

```text
card.pavlus: Unclosed { (line 1, col 8)
```

Una expresión que no está terminada, o que tiene un carácter que no forma parte del lenguaje de expresiones:

```pavlus-invalid
div
  p {total +}
```

```text
card.pavlus: Unexpected end of expression (line 2, col 13)
```

```pavlus-invalid
p {price # 2}
```

```text
card.pavlus: Unexpected character "#" (line 1, col 10)
```

Un `else` que no tiene un `if` antes. Fíjate en que `else` tampoco puede ir después de un `for`:

```pavlus-invalid
div
  p one
else
  p two
```

```text
card.pavlus: `else` without matching `if` (line 3, col 1)
```

Un hijo que no se importó. El mensaje te dice las dos formas de arreglarlo:

```pavlus-invalid
div
  +Card#card(title=title)
```

```text
card.pavlus: "Card" is not imported. Add `import Card from "..."` or use +{Card} for a component that comes from the state (line 2, col 4)
```

Un handler que no es un nombre de message:

```pavlus-invalid
button(@click=1+2) Go
```

```text
card.pavlus: Event handler must be a message id like `save` or `remove(item)` (line 1, col 8)
```

Una línea debajo de un elemento que no puede tener hijos:

```pavlus-invalid
input(value=x)
  p inside
```

```text
card.pavlus: This line cannot have children (line 2, col 1)
```

Un embed dinámico sin nombre de instancia, un `import` tardío, una alternancia de clase con una cadena, y `+outlet` con argumentos:

```text
card.pavlus: A dynamic component needs an instance name: +{expr}#name(...) (line 1, col 9)
card.pavlus: `import` lines must be at the top of the file (line 2, col 1)
card.pavlus: "class:on" needs an expression value (line 1, col 4)
card.pavlus: `+outlet` takes nothing after it (line 2, col 10)
```

En un build de Vite, el mensaje llega dentro del error del build. Esto es lo que imprime un build de Vite 8, abreviado, para un template que tiene la línea `  li {name`:

```text
Build failed with 1 error:

[plugin pavlus] /project/src/bad.pavlus
RolldownError: /project/src/bad.pavlus: Unclosed { (line 2, col 3)
```

> [!WARNING] Algunos errores tipográficos no son errores
> El compilador reconoce `if`, `else`, `for` y `+` por la forma de la línea completa. Una línea que casi coincide es un elemento normal. `if` solo, sin condición, es el elemento `<if>`. `for item of items` (con `of` en lugar de `in`) es el elemento `<for>` con el texto `item of items`. Ninguno de los dos es un error, y la página se renderiza sin el bloque que querías. Cuando algo que debería ser un bloque aparece como un tag, comprueba la línea con la sintaxis.

## Los archivos golden

¿Cómo pueden los autores del compilador cambiarlo con confianza? La suite de tests tiene dos capas.

La primera capa, `output.test.ts`, comprueba **propiedades** de la salida: los helpers se importan y no se pegan, solo se importan los helpers usados, las variables tienen nombres que vienen del template (`userList`, `prevUserKeys`, `liChildren`), los comentarios dicen qué línea y qué dependencias tiene un bloque, y el código no tiene líneas muy largas.

La segunda capa fija **cada byte**. En la carpeta `framework/src/compiler/__fixtures__` hay once templates pequeños, y en `__goldens__` el JavaScript exacto que el compilador debe producir para cada uno:

| Fixture | Qué ejercita |
| --- | --- |
| `static` | Nada depende del state, así que `diff` está vacío. |
| `text` | Líneas de texto, interpolación, llaves escapadas. |
| `element` | Atributos dinámicos, alternancias de clase, eventos con argumentos y modificadores. |
| `names` | Variables de bucle con nombres como palabras clave de JavaScript o nombres generados. |
| `if` | `if`, `else if`, `else`, un bucle sin key, un segundo `if`. |
| `for` | Bucles con key y un índice, bucles anidados, un `if` dentro de un bucle. |
| `embed-static` | Hijos importados, props, spread, un embed dentro de un bucle. |
| `embed-dynamic` | `+{expr}` debajo de un `if`, con props spread. |
| `outlet` | El nodo `+outlet`. |
| `shell`, `dashboard` | Dos páginas reales: un menú con una expresión de clase larga, y un dashboard. |

El test golden lee cada fixture con `?raw` (lo cual funciona porque el plugin se salta esa query), lo compila con `compileTemplate(source, { filename: "<name>.pavlus" })` y compara el resultado con el archivo usando `toMatchFileSnapshot`. Un último test comprueba que los fixtures juntos usan todos los tipos de nodo: elementos, texto, `if` con `else if` y `else`, `for` con key y sin ella, embeds estáticos y dinámicos, `+outlet`, alternancias de clase, y las formas `prevent`, `stop` y de muchos argumentos de los eventos. Si añades una característica nueva a la sintaxis, ese test falla hasta que un fixture la use.

Si un cambio del compilador altera la salida a propósito, ejecutas los tests con `-u` y lees el diff de `__goldens__/` en la revisión. Si fue un refactor, el diff debe estar vacío. Ese es el sentido de fijar los bytes: un cambio en la salida no puede pasar desapercibido.

### Cómo leer un golden

Los goldens son la mejor documentación de la salida, porque siempre son correctos. Para leer uno, parte del template y busca estos puntos de referencia:

- Los comentarios `// line N: <tag>` asocian un bloque con una línea del template. La misma línea aparece en `render` y en `diff`.
- En `render`, busca las variables `xChildren` y `xAttrs`. Se construyen primero, de abajo arriba, y el elemento se mete al final.
- En `diff`, busca el comentario con `(reads: ...)`. La línea siguiente es su guarda.
- Busca `idSuffix`. Cada id es el número de un nodo más el sufijo, así que puedes seguir un nodo a través de `render` y `diff`.
- Para un bucle, busca `diffKeyedList` y lee sus cuatro funciones.

## Hacer tests de una view

Una view está hecha de dos funciones puras, y un test de una view es un test normal. No necesitas un navegador para el primer tipo.

```pavlus todos.pavlus
ul
  for todo in todos key todo.id
    li(class:done=todo.done @click=toggle(todo.id)) {todo.title}
p {todos.length} todos
```

```ts todos.test.ts
import { expect, test } from "vitest";
import view from "./todos.pavlus";

const write = { id: 1, title: "Write", done: false };

test("finishing a todo changes only its class", () => {
  const patches = view.diff(
    { todos: [write] },
    { todos: [{ ...write, done: true }] },
  );
  expect(patches).toEqual([
    { op: "attr", id: "2#1", name: "class", value: "done" },
  ]);
});

test("nothing changed, nothing to patch", () => {
  expect(view.diff({ todos: [write] }, { todos: [write] })).toEqual([]);
});
```

Estos dos tests se ejecutan en Node normal. El test runner necesita el plugin, así que la configuración de Vite o de Vitest debe tener `pavlus()` en `plugins`.

Para un test que incluya el DOM, el paquete tiene `@pavlus/frontend/testing`. Su función `mountView(viewOrComponent, initialState, document?)` monta la view en un contenedor nuevo con el plugin del DOM real, sin el resto de la aplicación. Devuelve el contenedor (`root`), el plugin del DOM, la lista de messages que produjeron los eventos del usuario (`messages`) y las funciones `set(nextState)` y `unmount()`. Monta un componente, y no solo su view, cuando el template tiene un `+outlet`, porque el outlet necesita el `routing` del componente.

```ts todos.dom.test.ts
// @vitest-environment jsdom
import { expect, test } from "vitest";
import { mountView } from "@pavlus/frontend/testing";
import view from "./todos.pavlus";

test("the DOM follows the state, and a click sends a message", () => {
  const write = { id: 1, title: "Write", done: false };
  const check = { id: 2, title: "Test", done: false };
  const h = mountView(view, { todos: [write, check] });

  h.set({ todos: [write, { ...check, done: true }] });
  expect(h.root.querySelectorAll("li")[1].className).toBe("done");

  h.root.querySelector("li")!.click();
  expect(h.messages).toMatchObject([{ id: "toggle", payload: 1 }]);

  h.unmount();
  expect(h.root.innerHTML).toBe("");
});
```

El array `messages` contiene lo que despachó el plugin del DOM. El click en el primer elemento produjo `{ id: "toggle", payload: 1, event: { type: "click" } }`: el id del message y el payload vienen del template, y el campo `event` lo añade el plugin. `h.root.innerHTML` justo después de `mountView` es:

```text
<!--pavlus--><ul><!----><!----><li>Write</li><!----><!----><li>Test</li><!----><!----></ul><p>2 todos</p><!--/pavlus-->
```

Es una buena forma de ver los markers: cada elemento está entre dos comentarios vacíos, y la lista entre otros dos. Los comentarios `pavlus` y `/pavlus` delimitan todo el render.

## Lo que aprendiste

- `compileTemplate(source, { filename, runtime })` devuelve el texto de un módulo ES con `render`, `diff`, `meta` y una view por defecto. `compileToView` devuelve una view que funciona y está pensada para tests y herramientas. `DEFAULT_RUNTIME` es de donde vienen los helpers.
- El plugin de Vite `pavlus()` compila cada import `.pavlus`, se salta `?raw`, `?url` y `?inline`, no entrega un source map a propósito, y reporta un error de template con su archivo, línea y columna.
- `@pavlus/frontend/env` da tipos a los imports `.pavlus`. El state se tipa como `any`.
- Los errores del compilador son `TemplateError` con posiciones que empiezan en 1, y unos pocos errores tipográficos producen elementos y no errores.
- Los archivos golden fijan la salida exacta de once fixtures, de modo que un cambio en el código generado siempre es visible en una revisión. Una view se puede probar como dos funciones puras, o montar con `mountView`.
