## La idea en un minuto

Pavlus es un framework para construir interfaces web. Se apoya en una sola regla: **el código que escribes no toca el mundo exterior.** Nunca lee el DOM, no llama a `fetch`, no pregunta la hora ni escribe en la consola. En su lugar responde una pregunta, una y otra vez:

> Dado este **message** y este **state**, ¿qué **effects** deben ocurrir?

Un *message* es un pequeño dato plano que dice lo que acaba de pasar: `{ id: "inc" }` significa "el usuario hizo clic en el botón de más". El *state* es un objeto plano que contiene todo lo que muestra la pantalla. Un *effect* también es un dato plano. Describe algo que debe hacerse, como "poner el campo `count` en 3" o "enviar esta petición HTTP". Tu código solo devuelve la descripción. No hace el trabajo.

El trabajo lo hacen los **plugins**. Un plugin es dueño de un tipo de efecto secundario: el DOM, HTTP, los temporizadores, la ubicación del navegador, el store que guarda el state. Cuando algo ocurre en el mundo exterior (un clic, una respuesta, un tick de un temporizador), un plugin lo convierte en un message y se lo entrega a tu código. Cuando tu código devuelve effects, el core entrega cada effect al plugin al que va dirigido.

La tercera parte es el **lenguaje de templates**. Escribes la estructura HTML de un componente en un archivo `.pavlus` corto, basado en la indentación. Un compilador lo convierte en dos funciones simples: `render(state)`, que devuelve los nodos que se muestran, y `diff(prev, next)`, que devuelve la pequeña lista de cambios (patches) necesarios cuando el state pasa de un valor a otro.

```text
 click, reply, timer tick
          |   a plugin turns it into a message
          v
 your code:  (message, state)  ->  effects          pure, no side effects
          |   effects are plain data
          v
 plugins:    store, dom, http, time, router, ...    the only code that does things
          |   the store changed the state
          v
 template:   diff(prev, next)  ->  patches           pure, generated by the compiler
          |
          v
 the dom plugin applies the patches to the page
```

Es el mismo bucle que en el lenguaje Elm, con un compilador que hace rápida la parte del template. La siguiente página de esta serie, [Inicio rápido](page:quick-start), construye un ejemplo que funciona. La página [Arquitectura: código puro y efectos](page:concepts-architecture) explica el bucle en detalle.

## Por qué mantener el código puro

Una función pura siempre devuelve el mismo resultado para la misma entrada y no cambia nada fuera de sí misma. Esa única propiedad te da cosas que normalmente son caras:

- **Tests sin navegador.** Para probar un handler lo llamas con un message y un state y comparas los effects devueltos con asserts simples. No hay nada que simular.
- **El mismo código en el servidor.** Renderizar a una cadena no necesita DOM, así que los componentes que ejecutas en el navegador también se ejecutan en Node. La página [Renderizado en servidor](page:concepts-ssr) muestra cómo.
- **Repetición e historial.** Un state es un dato plano y cada cambio es un effect registrado, así que puedes deshacer un cambio o volver a un momento anterior. El plugin store guarda ese historial por ti.
- **Errores legibles.** Cuando algo sale mal, puedes imprimir el message y los effects. Ambos son objetos normales.

El precio es una regla que debes cumplir tú mismo: **el framework no comprueba que tu código sea puro.** Si un handler llama a `Date.now()` de todas formas, nada se lo impide, y pierdes las ventajas anteriores. La convención es simple. Si un handler necesita la hora, devuelve un effect `time` y recibe la respuesta como un message.

## Un programa completo y pequeño

Aquí tienes un contador completo, en cuatro partes. Primero el template. Es la estructura HTML del componente, con `{count}` leyendo el campo `count` del state y `@click=inc` indicando que un clic envía el message `inc`.

::demo counter

La demo de arriba la compila el compilador real en tu navegador. Los dos pasos de abajo muestran los patches que devuelve `diff` cuando `count` pasa de 2 a 3 y vuelve. Solo cambia el nodo de texto. El párrafo de la pista se inserta cuando la condición `count > 2` se vuelve verdadera, y se limpia cuando se vuelve falsa.

Segundo, el componente. Es una clase con un método por message. Cada método recibe el message y el state y devuelve una lista de effects. Aquí los effects se construyen con el helper del plugin store, `store.set(path, value)`, que devuelve el objeto plano `{ plugin: "store", type: "set", path, value }`.

```ts counter.ts
import { Component, type Message } from "@pavlus/frontend";
import { storeEffector as store } from "@pavlus/frontend/plugins";
import view from "./counter.pavlus";

export interface CounterState {
  count: number;
}

export class Counter extends Component<CounterState> {
  view = view;

  inc(_msg: Message, state: CounterState) {
    return [store.set("count", state.count + 1)];
  }

  dec(_msg: Message, state: CounterState) {
    return [store.set("count", state.count - 1)];
  }
}

export const counter = new Counter();
```

Tercero, la conexión. `createApp` conecta el componente con sus plugins. El plugin store guarda el state, y el plugin DOM renderiza la view del componente en el elemento `#app` y notifica los clics como messages.

```ts main.ts
import { createApp } from "@pavlus/frontend";
import {
  DomPlugin,
  createStorePlugin,
} from "@pavlus/frontend/plugins";
import { counter, type CounterState } from "./counter.ts";

createApp<CounterState>({
  app: counter,
  plugins: [createStorePlugin<CounterState>({ count: 0 }), new DomPlugin()],
  mount: "#app",
});
```

Cuarto, no hay nada más. Ni `useState`, ni suscripciones, ni `setCount`. Un clic se convierte en `{ id: "inc" }`, `inc` devuelve un effect `set`, el store reemplaza el state, `diff` compara el state anterior con el nuevo y devuelve un patch `text`, y el plugin DOM lo aplica.

> [!NOTE] El state no vive en el componente
> El objeto `Counter` no tiene campos que cambien. El state vive en el plugin store y se pasa a cada handler. La instancia del componente la comparten todos los messages, así que debe quedar libre de datos mutables. La página [Componentes y estado](page:concepts-components) explica por qué.

## Cómo se compara pavlus con los frameworks de DOM virtual

Muchos frameworks populares usan un *DOM virtual*: en cada actualización el código del componente se ejecuta de nuevo, construye un árbol nuevo de nodos ligeros, y el framework lo compara con el árbol anterior para encontrar qué cambió. Pavlus toma un camino distinto para la parte de la view. La tabla compara el enfoque en general, no un producto concreto, e indica lo que pavlus sacrifica además de lo que gana.

| Pregunta | Framework típico de DOM virtual | Pavlus |
| --- | --- | --- |
| ¿Cómo se encuentra un cambio? | El framework compara el árbol de nodos antiguo con el nuevo. | El compilador genera un `diff(prev, next)` que compara los campos del state con `===`. No se compara ningún árbol. |
| ¿Cuánto trabajo cuesta un cambio no relacionado? | Depende del framework; a menudo la función del componente se ejecuta de nuevo. | Un subárbol que no lee ninguno de los campos cambiados se omite con una sola comprobación. |
| ¿Dónde vive la lógica de actualización? | En el código del componente, a menudo con hooks o setters. | En handlers que devuelven effects. La view no tiene lógica sobre cómo actualizarse. |
| ¿Dónde viven los efectos secundarios? | En cualquier parte del código del componente. | Solo en plugins. El código de la aplicación devuelve datos. |
| ¿Qué es un manejador de eventos? | Una función. | Un dato: `{ id, payload }`. `diff` compara los handlers por valor. |
| Cambios de state | A menudo mediante setters, a veces mediante mutación. | El store reemplaza el state. Nunca debes mutarlo en el sitio, porque `diff` confía en `===`. |
| Probar la lógica de la aplicación | Normalmente necesita un renderer o mocks. | Llamas al handler y comparas los effects. |
| Lenguaje de los templates | A menudo JSX, en el mismo archivo que el código. | Un archivo `.pavlus` aparte con su propia sintaxis pequeña y su propio lenguaje de expresiones. |
| Madurez | Ecosistemas grandes, muchas librerías, muchos desarrolladores. | Un framework joven con una superficie pequeña. Los slots, los templates recursivos y los props tipados aún no están construidos. |

> [!WARNING] Un intercambio distinto, no mejor en todos los casos
> El diffing compilado es rápido para lo que conoce, pero el lenguaje de templates es más pequeño que JavaScript. Las expresiones son un subconjunto pequeño y puro — las funciones flecha solo tienen cuerpo de expresión, y no hay literales de objeto ni template strings. Los valores derivados que necesitan código real se calculan en un handler y se guardan en el state. Pavlus también exige disciplina, porque la pureza es una convención que nada hace cumplir.

## Lo que aprendiste

- El código de la aplicación es puro: entra `(message, state)`, sale una lista de effects. Los effects y los messages son datos planos.
- Los plugins hacen todos los efectos secundarios y convierten el mundo exterior en messages. El core los conecta en un bucle.
- Un template se compila a `render` y `diff`. `diff` devuelve patches comparando los campos del state que lee cada nodo.
- Una app completa es un template, una clase de componente y una llamada a `createApp` con un plugin store y un plugin DOM.
- Pavlus cambia un lenguaje de templates pequeño y una convención de pureza por tests simples y actualizaciones baratas.
